## 12. 開発・テスト方針

### 12.1 リポジトリ構成

本プロジェクトは単一の GitHub リポジトリで管理する。履修要項データ(`curricula/**/*.yaml`)と開講年度ファイル(`offerings/<開講年度>/**/*.yaml`)も同一リポジトリ内に置く(§4.4.2)。

将来、履修要項データを別サービスから参照する必要が生じた場合のみ、別リポジトリへの分離を再検討する。

### 12.2 CI

- frontend: 型チェック(`tsc --noEmit`)、Lint(ESLint)、ビルド
- backend: 型チェック(`mypy` または `pyright`)、Lint(`ruff`)、ユニットテスト(`pytest`)
- curricula / offerings: YAML スキーマバリデーション(Pydantic でロード可能かと §4.4.3 の整合性検査を、マージ後のオブジェクトに対して実行する)。加えて以下を検証し、いずれかに違反する PR はマージをブロックする
  - `offerings/<開講年度>/` の `resolved` 全コードが api-clean の当該開講年度に存在すること
  - `curricula` 側の科目名の集合と、対応する `offerings` ファイル(同じ入学年度・同じ課程)の `resolved` のキー・`not_offered` の `title`・`unresolved` の `title` の和集合が**過不足なく一致**すること(取りこぼしと余剰の双方を検出する)
  - **`unresolved` が空であること**。起動時は警告に留める(§4.4.3)が、CI では失敗させる
  - **`duplicate_of` を持つファイルが、複製元と内容一致すること**(ハッシュ比較)。複製元は `curricula/` 起点の実在パスであり、自身を指さないこと。この検査の対象は宣言があるファイルのみとし、**版表記(`curriculum_version` / `liberal_arts_version`)が同じであることを一致の根拠にはしない**(§4.4.1)

**CI は未整備である**(2026-09-09 時点)。ワークフローはまだ置いておらず、上記はいずれも手元での実行にとどまる。このうち YAML のスキーマバリデーションと §4.4.3 の整合性検査は backend の起動時検査と重なるため、ロードが通る時点である程度は担保される。一方、`unresolved` が空であること・`resolved` の api-clean 照合・`duplicate_of` のハッシュ一致の3つは CI にしか無い検査であり、整備するまでは PR レビューで見る。

### 12.3 テスト

- **backend(ユニット)**: `pytest`(`backend/tests/`)。モデル(vllm)と api-clean はモックし、実機を呼ばない。API の応答、履修要項のロード・マージ・要件充足判定、スキーマの検証を対象とする
- **backend(実機)**: `backend/scripts/smoke_*.py` を手で実行し、vllm・api-clean との疎通と、チャット・履修提案の実際の出力を確認する。**pytest の対象外とする。** 実機の応答は非決定的で、1回に数分かかるためである(§6.3.1)。LLM の出力の質は自動テストでは押さえられず、プロンプトの規則(§7.2.1、§7.4.1)についても単体テストで確かめるのは規則がモデルへ渡ることまでとする
- **frontend**: 未整備(コンポーネントテストは Vitest + Testing Library を想定)。PDF解析は `frontend/scripts/parse_grade_report_local.mjs` で手元の成績表サンプルに対して確認する

### 12.4 開発環境

本プロジェクトの開発環境・開発ツールの詳細は、本書の対象外とし、別ドキュメントで管理する。
