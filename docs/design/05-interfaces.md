## 6. API設計

### 6.1 内部 API(frontend ↔ backend)

| メソッド | パス | 用途 | 応答形式 |
|---|---|---|---|
| POST | /api/proposal | 履修提案を生成 | SSE |
| POST | /api/chat/proposal | 履修提案に関するチャット | SSE |
| POST | /api/chat/syllabus | シラバス全体チャット | SSE |
| POST | /api/chat/syllabus/{code} | 講義単位チャット | SSE |
| GET | /api/syllabi | シラバス検索(一覧・絞り込み) | JSON |
| GET | /api/syllabi/{code} | シラバス詳細(講義ページ表示) | JSON |
| GET | /api/masters | 検索絞り込み用の値マスタ | JSON |
| GET | /api/curricula/{program_code}/{admission_year} | 履修要項データ参照(タグ表示用) | JSON |
| GET | /api/course-targets | シラバスコード → 対象課程(タグの履修可否判定用。§6.1.3) | JSON |
| POST | /api/requirements | 卒業要件の充足判定(要件枠ごとの不足単位) | JSON |
| GET | /api/healthz | ヘルスチェック(**公開経路からの死活確認はこちら**。§3.5.1) | JSON |
| GET | /healthz | ヘルスチェック(ネットワーク内から直に叩く用) | JSON |

チャット系(SSE)のリクエストには学生プロファイルと対話履歴を毎回含める(サーバ側で永続化しないため)。

`/healthz` だけがルート直下にあるため、**公開経路(`/syllabel/api/*`)からは到達しない**。`/syllabel/*` は frontend へ振り分けられるためである。外から死活を見るには `/api/healthz` を使う(§3.5.1)。

上表のパスは **backend が受けるパス**である。ブラウザおよびサーバ側描画から呼ぶときの**公開パスは `/syllabel` を前置した `/syllabel/api/...`** となる。ゲートウェイが `/syllabel` を剥がして backend へ渡すためである(§3.5.2)。Next.js の `basePath` はページとアセットの生成先を変えるだけで `fetch()` のパスには前置されないため、**frontend は呼び出し先に `/syllabel` を自分で含める**。

呼び出し元によって宛先が分かれる。backend の配置が決まったため(§3.4.2)、いずれも確定である。

| 呼び出し元 | 宛先 |
|---|---|
| ブラウザ(クライアントコンポーネント) | ゲートウェイと同一オリジンの `/syllabel/api/...`(相対パス)。§3.5.2 の URL 構造から従う |
| サーバ側描画(RSC / `page.tsx` の `async` 関数) | 同一 Podman ネットワーク上の backend コンテナ(`http://syllabel-backend:8000/api/...`)。**ゲートウェイを経由しないため `/syllabel` は付かない**。サーバ側の `fetch` は相対パスを解決できないため、オリジンを環境変数で与える |

いずれもハードコードせず、実行時の環境変数で与える(§3.2.1)。

**`lib/syllabus-api.ts` はサーバコンポーネント(`app/syllabus/page.tsx`、`app/syllabus/[code]/page.tsx`)とクライアントコンポーネント(`SyllabusTagList` 等の `fetchCurricula`)の双方から import される。** 宛先を単一の定数に置くとどちらか一方が必ず壊れるため、**オリジンはモジュール読み込み時に固定せず、呼び出しごとに解決する**(`lib/api_base.ts` の `apiBase()`。`typeof window` で呼び出し元を判別し、サーバ側は `BACKEND_ORIGIN` を読む)。この制約は到達経路の決定によらない。

**開発時はゲートウェイが居ない。** ブラウザからの `/syllabel/api/*` は Next の開発サーバに届いてしまうため、`next.config.ts` の `rewrites()` がゲートウェイと同じ振り分けを代行する(本番では空を返し、振り分けはゲートウェイに委ねる)。

`POST /api/chat/proposal` は、学生プロファイル・生成済みの提案・対話全体を1本の `messages` で受ける。**`messages` の末尾(role: user)が今回の質問、それより前が履歴である。** `proposal` は必須、`messages` は1件以上で末尾は `user` でなければならない。末尾が `assistant`、`messages` が空、`proposal` が無い場合は 422 を返す。提案が §5.3 の検証(コマ重複など)に落ちる場合も 422 となる(`POST /api/proposal` と同じスキーマを使うため)。

```json
{
  "studentProfile": { "grade": 3, "program": "知能情報メディア課程", "completedCourses": [] },
  "proposal": {
    "courses": [
      { "syllabusCode": "B12345", "title": "情報基礎", "day": "月", "period": 3,
        "term": "前期", "credits": 2, "category": "必修", "reason": "情報メディア分野の必修のため。" }
    ],
    "totalCredits": 2,
    "summary": "必修を軸にした構成。"
  },
  "messages": [
    { "role": "user", "content": "前の質問" },
    { "role": "assistant", "content": "前の回答" },
    { "role": "user", "content": "この時間割は何単位?" }
  ]
}
```

`GET /api/syllabi` / `/api/syllabi/{code}` / `/api/masters` は、検索画面(§4.1 の `/syllabus` 一覧・検索および `/syllabus/[code]` 詳細)が使う読み取り専用エンドポイントで、backend は §6.2 の api-clean(`GET /syllabi` / `GET /syllabi/{code}` / `GET /masters`)を中継する。公開経路はゲートウェイの単一オリジンに統一され、`/` は frontend、`/api/*` は backend へ振り分けられる一方、api-clean は公開されない(§1.2)。したがって frontend は api-clean を直接呼べず、検索画面向けにも backend 側の口が必要となる。クエリパラメータは api-clean の `/syllabi`(`q` / `faculty` / `program` / `campus` / `term` / `day` / `period` / `year` / `instructor` / `grade` / `limit` / `offset`)を素通しする。検索結果に付す「必修 / 選択 / 修得済み」タグ(§8)は、この結果と `GET /api/curricula` の履修要項、ブラウザ内の学生プロファイルを frontend 側で突き合わせて生成する。突合はシラバスコードによる結合を第一とし、履修要項側のコードは開講年度ファイルの `resolved`(科目名 → シラバスコード。§5.1.4)から解決する。`not_offered` / `unresolved` の科目はコードを持たないためタグ付けの対象外とする。

**検索画面が扱う開講年度は1年度に固定する。** api-clean は2025年度の開講科目も保持しているが、履修要項側の名寄せ結果(`offerings/<開講年度>/`。§5.1.4)は2026年度分しか無く、教養教育科目の対応が揃っていない。他年度を選べるようにすると、タグ付けの対象外となる結果だけが並ぶ画面になる。したがって **frontend は `year` を定数(`lib/syllabus-api.ts` の `OFFERING_YEAR`)で与え、絞り込み UI から年度の選択肢を外す**(URL に `year` が付いていても見ない)。backend の `/api/syllabi` は引き続き `year` を素通しし、制限は置かない。他年度の `offerings/` が揃えばこの定数を増やすだけで開放できる。

**検索は条件に当たる全件を引き、ページ送りは表示だけの都合とする。** frontend の `searchCourses()` は `MAX_ROWS`(500)ずつページを辿って**全件を集めて返す**(`lib/syllabus-api.ts`)。理由は3つある。

1. **タグでの絞り込みが全件に効かないと使えない。** タグは学生プロファイルとの突合で決まり(§6.1.3)、プロファイルはブラウザにしか無いため api-clean の検索条件にできない。**さらに絞り込んだ結果をサーバへ送ることもできない** — 「修得済みのコード一覧」はその学生の成績そのものである(要件§5)。したがって振り分けはクライアントで閉じるしかなく、取得済みのページしか振り分けられないと**該当の少ないタグではほとんどのページが空になる**。2026年度開講・2024年度入学の知能情報メディア課程では、修得済み 184 コードが 41 ページに散り、**35 ページが「該当なし」**になっていた
2. **総ヒット数がタダで確定する。** `results.length` がそのまま総件数であり、下の数え上げが要らなくなる
3. **安い。** 先端理工学部・2026年度の全 1,219 件で **3リクエスト / 転送 gzip 約 22KB / 実測 0.23 秒**

ページ送りは**絞り込み後の並び**に対して行う。`offset` は URL に持ったまま(詳細画面から戻ったときに位置を保つため。§8)、クライアントがその値で絞り込み後の配列を切る。**絞り込みを変えたら `offset` を消す**(`lib/useFilterControls.ts`) — 絞り込みはクライアント状態、`offset` は URL にあるため、消さないと前の絞り込みでのページ位置が残る。

**総ヒット数はつねに確定する。** 全件を引くため `検索結果 N件以上` という表示は要らなくなった。絞り込みが効いているあいだは**絞り込み後の件数**を出し、絞る前の母数を併記する(「184件（1,219件中）」)。件数とページ数はどちらも絞り込み後の並びで決まるため、**サーバ側描画では描けない**(以前は見出しの件数を `page.tsx` が描いていたため、「1,219件」と出しながら16件しか並ばない食い違いが起きていた。§8)。

**検索ボックスの1語は、科目名 → 教員名の順で引く。** api-clean の `q` と `instructor` は別のパラメータであり、`q` は教員名に当たらない。一方 UI は科目名と教員名を1つの入力で受ける(§8)ため、frontend は `q` で引いて結果が空のときに同じ語を `instructor` で引き直す(`lib/syllabus-api.ts` の `searchCourses()`)。**両者を同時に送ってはならない。** api-clean のパラメータは AND 条件であり、必ず0件になる。教員名として引き直したことは検索結果の見出しに示す。

**教員名は、登録表記を組み立て直して引き直す。** api-clean の `instructor` は**登録された表記のままの部分一致**(`instructor.kanji_name ILIKE`)であり、正規化を持たない。教員名は全角スペース区切りで登録されているため、半角スペースの「山田 太郎」でも区切りなしの「山田太郎」でも1件も引けなかった(**全角スペースを入れない限りフルネームで引けない**)。科目名の突合(§5.1.5 の `normalizeTitle()`)のようにこちら側で正規化して突き合わせることはできない — 照合するのは api-clean であり、**一覧は教員名を返さない**(§6.2)ため、手元で突き合わせるには全件の詳細を引く(1,200 リクエスト)しかない。したがって**入力の側を api-clean の表記に寄せて引き直す**(`lib/instructorName.ts` の `spellInstructorName()`)。

**入力の空白を取り除き、先頭から1文字ずつ伸ばしながら api-clean に当たるかを確かめて組み立てる。** 次の1文字をそのまま繋げて当たらなければ、区切り(全角 → 半角)を挟んで試す。問い合わせは他の検索条件を同じにした `limit=1` で行う。部分一致なので、伸ばしている途中の語も当たる。

| 入力 | 組み立て |
|---|---|
| `山田`(姓のみ) / `山田　太郎`(全角) | 入力どおりで当たる。組み立てない |
| `山田 太郎` / `山田太郎` | `山田` → `山田太`(外れ)→ `山田　太` → `山田　太郎` |
| `オーガスティンジョナサン` | 姓の長さを仮定しないので、7文字の姓でも `オーガスティン　ジョナサン` に至る |
| `ドラグナラルカマリア` | 区切りの数を仮定しないので `ドラグナ　ラルカ　マリア` に至る |

**姓の長さも区切りの数も仮定しない。** 区切りを入れる位置を姓の長さ1〜4文字で決め打ちすると、姓が5文字以上の教員(2026年度ではオーガスティン・ヘルナンデス・ナットチー)と区切りが2つある教員(ドラグナ ラルカ マリア)を区切りなしで引けない。組み立てた語は api-clean に実在する表記の一部なので、当て推量の語の結果を束ねることもない。偶然当たる寄り道(別の教員の名前の一部)で行き止まったら戻って区切りを試し、問い合わせは1回の組み立てにつき64回で打ち切る(登録表記は最長14文字で、まっすぐ伸ばせば1文字につき高々3回)。2026年度・先端理工学部の全教員 317 名を、登録どおり・半角区切り・区切りなしの3通りで引き、担当する全科目が結果に入ることを確かめた(最も問い合わせの多い名前で 16 リクエスト)。

**組み立てるのは入力どおりの語が空振りしたときだけとする。** 姓のみ・全角区切りのフルネームは1回で当たるため、従来と同じ1リクエストで済む。**問い合わせのどれかが失敗したら例外をそのまま送出する** — 失敗を「外れ」と扱うと、当たるはずだった語で「見つからない」と誤答する。

**同じ規則を frontend と backend の双方に置く。** 検索画面は frontend が引き(`lib/instructorName.ts`)、シラバスチャット(§7.4)のエージェントは backend が引く(`app/agents/instructor_name.py` と `app/agents/tools.py` の `search_syllabi_by_instructor()`)。**両者は同じ規則に保つこと** — 食い違うと「検索画面では出るのに、チャットでは “その教員の科目は見つからない” と返る」というねじれが起きる(科目名の `normalize_title()` を frontend と backend の双方に置いているのと同じ理由。§5.1.5)。

**`GET /api/syllabi` では埋めない。** この口は api-clean の `/syllabi` を素通しする(上記)。組み立ては1回の検索を何度もの問い合わせに変えるため、ページ送りの口の中で行うとページを送るたびに組み立て直すことになる。検索画面はこの口をページ送りに使わず全件を引く(§6.2)ため、組み立ては frontend 側で閉じられる。backend で埋めるのは、ページ送りを持たないチャットの検索ツールのほうである。

`GET /api/curricula/{program_code}/{admission_year}` は、このタグ付けが必要とする科目レイヤ(§4.4.3)を返す。**backend は次の3点を解決済みの状態で返し、履修要項の構造をクライアントに持ち込まない。**

- **マージ後の `courses` を返す**(教養教育科目ファイルの取り込み、`not_available_to_programs` による除外、他課程からの専門関連科目の導出。§4.4.3)。検索結果には他課程が開講する科目も現れるため、当該課程の設置科目だけを返すとその大半がタグなしになる
- **各科目にシラバスコードを合成して返す。** コードは `curricula/` 側になく開講年度ファイルの `resolved` が持つ(§4.4.2)ため、解決は backend が行う。frontend が `offerings/` を直接参照することはない。`not_offered` / `unresolved` の科目は空配列とする
- **当該課程の設置科目か、他課程から導出した専門関連科目かを区別するフラグ(`own`)を付す。** 導出科目の用途は §4.4.3 のとおり `related` / `free.faculty` スロットの判定に限られる。**その `type` は導出元の課程にとっての区分である。** 例えば「プログラミング及び実習Ⅱ」(Y001009010)は数理・情報科学課程の専攻科目で、知能情報メディア課程の履修要項には専門関連科目として `選択必修` で載る。これを「選択」と表示すると、その学生にとっての区分ではない値を見せることになる。したがって `own` が false の科目には**導出元の `category` / `type` をそのまま出さない**。実際に出すタグは §8.2 の表が定める(履修可 × 未修得なら `専門関連` のみ)。`buildTagMap()` はタグの候補を作るところまでを担い、履修可否(§6.1.3)と `own` を掛けて最終のタグを決めるのは `resolveTags()` である(`lib/syllabusUI.ts`)。ただし**修得済みだけは `own` を問わず付ける**。修得済みかどうかは学生の成績の事実であり、科目がどの課程の設置かに左右されない

#### 6.1.3 履修可否の判定

**履修要項は「科目」の単位で書かれており、その学生がその開講クラスを履修登録できるかを持たない。** 1科目に複数のクラスが対応し(§5.1.4)、どのクラスを履修できるかは課程ごとに決まっているため、履修要項側のデータだけではタグを正しく出せない。**判定の正本はシラバスの対象課程とする。** 規則は次の3分岐で、検索のタグ表示(frontend)と履修提案の候補抽出(backend)で共通である。

| シラバスの対象課程(`programs` / `faculties`) | 判定 |
|---|---|
| 学生の課程が `programs` に入っている | 履修可 |
| `programs` が空で、`faculties` に `先端理工学部` が入る | 課程指定なし。履修可 |
| それ以外 | 他課程指定のクラス。履修不可 |

**履修できないクラスにはタグを出さず、履修提案の候補にも載せない。** 判定を持たなかったときの実測(2026年度開講・2024年度入学の知能情報メディア課程)は次のとおりだった。

| | 変更前 | 変更後 |
|---|---|---|
| 検索結果でタグが付くコード | 430(うち **126 が誤り**) | 304(誤り 0) |
| 履修提案のプロンプトのクラス行 | 673(うち **189 が履修不可**) | 508(履修不可 0) |

誤タグ126件はすべてクラス指定のある教養教育科目10科目だった(仏教の思想A/B 各8件、英語総合1(A)〜4 各11件、スポーツ技術学A/B 各22件)。例えば「仏教の思想A」は11クラス開講され、火1の3クラスは電子情報通信+機械工学・ロボティクス課程、火2の2クラスは知能情報メディア課程、水1の3クラスは応用化学+環境生態工学課程、水2の2クラスは数理・情報科学課程、木5の1クラスは課程指定なしの後期開講(救済措置)である。履修要項側の対応表(`offerings/`)は科目名 → コードの対応しか持たず課程を区別しないため、11クラス全部に `必修` が付いていた。

**学修プログラムの帰属は持たない。** 履修要項の専門関連科目は「学修プログラムを構成する科目のうち他課程が主体となって開講する科目」であり(履修要項 s04)他課程の全科目ではないが、この帰属を別に持つ必要はない。2026年度開講・2024年度入学コホートで突き合わせると、**学修プログラム含有科目 242 コードは100%が全6課程対象**であり、**非含有の専攻科目 400 コードは97%(389)が主開講課程のみ**で、対象課程が帰属を代理している。加えて、学修プログラムの表(履修要項 s05【8】。PNG画像)に載らないのに複数課程へ開かれている `Y009` 系の共通科目(情報と職業・職業指導・地学概論・生物学概論・地学実験・生物学実験の11コード)は**対象課程でしか判別できない**ため、表を転記するとかえって取りこぼす。

**科目名の突合は正規化してから行う。** `curricula/` の科目名は履修要項の表記のまま転記する規約であり(§5.1.5)、正規化は**突き合わせる側の責務**である。大学のデータ自体が表記を混在させており、「仏教の思想A」は履修要項と api-clean の `course_title` が半角 `A`(U+0041)、Web シラバスの検索ページが**全角 `Ａ`(U+FF21)**である。成績表由来の科目名にも全角英数字や空白が混じるため、完全一致では外れる。規則は **NFKC 正規化 + 空白除去**で、backend は `app/curricula/requirements.py` の `normalize_title()`、frontend は `lib/courseTitle.ts` の `normalizeTitle()` が持つ。**両者を同じ規則に保つこと。** frontend 側に正規化が無かったとき、**卒業要件の残り単位(backend 計算)では修得済みなのに検索のタグ(frontend 計算)には出ない**というねじれが起きていた。

**課程名の比較は改称を吸収する。** 課程コード `06` は入学年度で名称が異なり(2024年度入学: 環境生態工学課程、2025年度入学: 環境科学課程)、api-clean は**両方を別々の課程として持つ**ため、文字列の一致で比べると取り違える(§4.4.2)。frontend は `lib/programs.ts` の `isSameProgram()`、backend は課程ファイルの `program.name_aliases` を使う。

**対象課程の取得経路は frontend と backend で異なる。** api-clean の `GET /syllabi`(一覧)は対象課程を返さない。1科目に複数の課程が対応するため `SELECT DISTINCT` から外されており、対象課程は `GET /syllabi/{code}` にしかない(§6.2)。1件ずつ引くと 1,200 リクエストになるため、どちらも**課程名で絞った一覧を課程ごとに引いて集合演算で組み立てる**。`program` は `cp.name = %s` の完全一致で、対象課程を持たないシラバスは絞り込みから落ちるため、**「どの課程の結果にも現れないコード」が課程指定なしのコード**である。

| | 判定する場所 | 対象課程の取得 |
|---|---|---|
| 検索のタグ | frontend(`lib/eligibility.ts` / `lib/syllabusUI.ts` の `resolveTags()`) | backend の `GET /api/course-targets` から**全件ぶんまとめて**受け取る(下記) |
| 履修提案 | backend(`app/agents/proposal_agent.py` の `fetch_eligibility()`) | 同じ手を backend 内で行う |

**`GET /api/course-targets?year=&faculty=` が、シラバスコード → 対象課程の対応をまとめて返す。** 検索のタグは絞り込みを全件に効かせる必要があり(§6.1)、そのためには**検索結果の全件ぶんの対象課程**が手元に要る。表示中の行だけ詳細を引く方式(担当教員名と同じやり方。§6.2)では足りない。

**対象課程が引けなくても一覧は出す。** タグは検索の付加価値であって前提ではないため、この口の失敗で画面ごと落としてはならない(`fetchCourseTargets()` の失敗は null として扱い、タグを出さずに続ける)。**対象課程が分からないコードに空配列を渡してはならない** — 空配列は「課程指定なし(＝履修可)」を意味するため、引けなかったコードをすべて履修可と扱い、誤タグが戻る。修得済みは成績の事実なのでこの場合も出る。

> **実際に事故が起きた。** frontend だけを入れ替えて backend を古いまま(この口を持たない)にしたとき、404 で検索画面が `error.tsx` に落ちた。**frontend と backend は揃えて入れ替える**必要がある(§3.2)。

**このレスポンスに学生データは1件も含まれない。** (開講年度, 学部)だけで決まるため ETag と `Cache-Control: public, max-age=3600, must-revalidate` を付けて再送を避ける。2026年度・先端理工学部で 1,219 コード / 約 99KB / **gzip 約 4KB** / 組み立て 10 リクエスト・実測 0.9 秒。組み立て結果は backend が (開講年度, 学部) ごとに保持するが、**`/api/curricula` と違い上流(api-clean)の更新で変わり得るため恒久キャッシュにはせず、期限を置く**。

**規則は本節の1か所に置き、実装は2か所に持つ。** 取得経路が違うため実装は分かれるが、判定そのものは上の3分岐だけである。片方だけを直す事故を避けるため、変更はこの節と両実装を必ず揃えて行う。

**対象課程が取れなかったコードにはタグを出さない。** 一覧は表示中のぶんだけ詳細を引いており、その取得が失敗したコードでは可否が判定できない。**履修可否の正本は対象課程である**という原則に従い、判定できないものについては何も主張しない(可否不明のまま「必修」と出すのは、この節が直した誤りと同じことになる)。

**履修提案では、1科目あたりのクラス数を絞る前に履修可否を掛ける。** 順序が逆だと、`MAX_CLASSES_PER_COURSE` が曜日・時限の早い順で切るため、他課程指定のクラスが早い時限に並ぶ科目で**履修できるクラスが1つも候補に載らない**。実測では4科目(英語総合1(A)・英語総合2(A)・スポーツ技術学A/B)がこの状態で、コードだけでなく曜日・時限が丸ごと違うため、コマ重複の判定も誤った前提で行われていた。

あわせて `graduation`(`total_credits` / `excluded_types`)を返す。卒業残り単位の表示(§4.4.5)に必要であり、これを返さないとクライアントは卒業必要単位数を知る手段を持たない。**設置科目の単位数の総和は卒業必要単位数ではない。** 要件枠ごとの不足単位は `POST /api/requirements` で得る。

```json
{
  "programCode": "02", "admissionYear": 2024, "offeringYear": 2026,
  "graduation": { "totalCredits": 124, "excludedTypes": ["随意"] },
  "courses": [
    { "title": "仏教の思想A", "category": "教養教育科目", "subcategory": "「仏教の思想」科目",
      "type": "必修", "credits": 2, "grade": 1, "term": "前期", "quarters": ["1Q", "2Q"],
      "kikan": false, "own": true, "syllabusCodes": ["G260110004", "G260110005"] }
  ]
}
```

`POST /api/requirements` は、学生プロファイル(既修得科目を含む)を本文で受け取り、要件枠ごとの修得済み単位・不足単位を返す。判定規則をクライアントへ渡さないための口であり、その根拠と責務の切り分けは §4.4.5 による。要件枠には公式の区分名 `name`(「教養教育科目(選択)」など。§5.1.2)を付けて返す(v0.9.56。画面に出すのはこちらで、`key` は内部の識別子)。履修提案の画面が卒業要件枠の内訳を出すのに使う(§8.3.5)。

`POST /api/proposal` のリクエストは、学生プロファイルと**課程コード・入学年度を別に**受ける。履修要項を引くキーは (課程コード, 入学年度) である(§4.4.2)一方、`StudentProfile.program` に入るのは成績表から採れる**課程名**であり、課程は改称され得るため識別子には使えない。入学年度もプロファイルには無い(成績表から採れない)ため、frontend が学年から算出して送る。課程名 → 課程コードの解決は frontend が持つ(`lib/programs.ts`。一覧の正本は `curricula/admission-<年度>/` の課程ファイルである)。

```json
{
  "studentProfile": { "grade": 3, "program": "知能情報メディア課程", "completedCourses": [] },
  "programCode": "02", "admissionYear": 2024,
  "preferences": "午前中の科目を多めにしたい",
  "targetTerm": { "year": 2026, "term": "後期", "grade": 3 }
}
```

`targetTerm` は**提案する学期**(次に履修登録する学期)である。`year` は年度、`term` は `前期` / `後期`、`grade` は**その学期の**学年で、年度をまたぐと成績表の作成時点の学年(`studentProfile.grade`)より1つ上になる。frontend が取り込んだ成績表の次の学期(成績表の作成日の月から決める)を送る。学生は画面で確認できるが選び直せない(§5.2.1、§8.3)。backend は候補のクラスをこの学期に登録するものへ絞り、配当年次と CAP の該当セメスターにこの学年を使う(§7.2.1)。省略もできるが、その場合は前期・後期のクラスが混ざり学期の混ざった提案になり得る(旧い呼び出しの互換のためだけに残している)。

`preferences` は任意の自由文で、§7.2.1 のプロンプトの「希望条件」節にそのまま入る(未指定のときは「特になし」)。**(課程コード, 入学年度) に対応する履修要項が無い場合は 404 を返す**(ストリームを開く前の前処理であるため。§6.1.1)。

**この口を叩く契機は学生の送信であり、`/proposal` を開いたことではない。** 希望条件は提案画面の AI履修アシスタントの入力欄で受け取り、その本文がそのまま `preferences` になる(§8.3)。

#### 6.1.1 SSE の書式

SSE を返す4本は、いずれも `data: <JSON>` の1行1イベントで配信する(実体は `app/api/sse.py`)。イベントの種類は用途で2系統に分かれる。

**チャット系(`/api/chat/*`)**

| イベント | 内容 |
|---|---|
| `{"delta": "..."}` | 本文の断片。受け取った順に連結すると回答になる |
| `{"error": "..."}` | 生成中の失敗。表示用の文言のみを載せ、例外の詳細は載せない |
| `{"done": true}` | 終端。エラー時も最後に必ず流れる |

思考(reasoning)とツール呼び出しはクライアントへ流さない。本文が始まる前の空白だけの出力も捨てる(§6.3.1 のとおりチャット系は思考を有効にしており、ツール呼び出しの前に空白だけの本文パートが出ることがある)。

**履修提案(`/api/proposal`)**

| イベント | 内容 |
|---|---|
| `{"snapshot": {...}}` | 組み立て途中の `TimetableProposal`(§5.3)。生成中に何度も流れる |
| `{"result": {...}, "adjustments": [...]}` | 確定版。1度だけ流れる。`adjustments` は backend が外した科目・打ち切りの記録(文字列の配列。§7.2.2)で、**frontend は読まず学生に見せない** |
| `{"error": "..."}` / `{"done": true}` | チャット系と同じ |

`snapshot` は §5.3 のスキーマの**全フィールドを省略可能にした写し**で検証したもので、未到達のフィールドが null になるだけでキーの構成は `result` と同じである。クライアントは両者を同じ描画コードで扱える。写しはスキーマから機械的に作る(手で並べ直すと §5.3 を直したときに snapshot だけが古い形で残る)。まだ JSON として読めない断片と、直前と内容が変わらないものは流さない。コマ重複の検査(§5.3)は写しには引き継がない。途中経過は未確定の値を含むためである。

**SSE を開いたあとは HTTP の状態コードを返せない。** したがって提案の前処理(§7.2.1)はストリームを開く前に済ませ、そこでの失敗は 404(対応課程外)・400(前提不足)・502(上流障害)で返す。開いたあとに起きた失敗は `error` イベントで伝える。

#### 6.1.2 キャッシュの扱い

- `GET /api/curricula/{program_code}/{admission_year}` は本文から作る **ETag** と `Cache-Control: public, max-age=3600, must-revalidate` を付し、`If-None-Match` が一致すれば 304 を返す。内容は `curricula/` / `offerings/` の更新(=デプロイ)でしか変わらず(§4.4.4)、学生データを含まない GET であるため、マージ後の全課程分(2024年度入学コホートで課程あたり568〜577科目、約129KB / gzip 約9KB)の再送を避けられる。本文と ETag は (課程コード, 入学年度) ごとに1度だけ組み立ててメモリに持つ
- `POST /api/requirements` は既修得科目を本文で受けるため `Cache-Control: no-store` を付し、ブラウザにも中間経路にも残させない(§4.4.5)
- SSE には `Cache-Control: no-cache` と `X-Accel-Buffering: no` を付す。後者は中継が応答をバッファリングして逐次配信を潰すのを防ぐためである。現行のゲートウェイは Caddy であり `reverse_proxy` は既定でバッファリングしないため、このヘッダは nginx 系の中継が前段に入った場合の保険として付し続ける(§3.2.1)

### 6.2 既存シラバスバックエンド API の利用

backend から以下の3つを利用する。**これがシラバスバックエンドに対して使う口のすべてである。**

- `GET /syllabi` — 検索(独自シラバス§4.5、シラバスチャット§4.6で使用)
- `GET /syllabi/{code}` — 詳細(講義ページ表示・講義単位チャットで使用)
- `GET /masters` — 値マスタ(検索 UI のドロップダウン候補に利用)

**`GET /syllabi` の検索条件の意味は次のとおり**(api-clean の `clean_api.py` で確認)。条件はすべて AND で結合される。

| パラメータ | 突合 |
|---|---|
| `q` | **科目名のみ**の部分一致(`subject.title ILIKE`)。**教員名には当たらない** |
| `instructor` | 担当教員の漢字名の部分一致(`instructor.kanji_name ILIKE`)。**正規化は無く、登録された表記のまま照合される**(姓名の区切りは全角スペース。§6.1) |
| `faculty` / `program` / `campus` | 名称の完全一致。候補は `/masters` |
| `term` / `day` / `period` | 開講期(名称の完全一致) / 曜日1文字 / 1〜7。**いずれかの開講コマ**と比べる(api-clean 0.3.0 以降。下記)。`day` と `period` は同じコマで満たす必要がある |
| `year` / `grade` | 開講年度 / `grade_min <= x <= grade_max` |

**開講コマは `slots` で受け取る(api-clean 0.3.0 以降)。** 1つのクラスが複数のコマを持つ(「後期　金4・金5」「3Q　金3、4Q　金3」)が、`term` / `day_of_week` / `period` は**1コマ目だけ**である。`GET /syllabi` の各行と `GET /syllabi/{code}` は全コマを `slots: [{term, day, period}]` として原文の順に返す(集中講義は空)。**時間割に置く・重複を判定するときは `slots` を使う**(§5.3)。0.2.0 以前の api-clean は `slots` を返さず、検索の `term` / `day` / `period` も1コマ目としか比べない(`day=金&period=5` で「金4・金5」の科目が出ない)。backend は `slots` が無ければ1コマ目だけで動く(`proposal_agent._read_slots()`)。

**`GET /syllabi` は担当教員を返さない。** 一覧の SELECT は科目1行に畳まれており(`SELECT DISTINCT`)、担当教員は結合こそするものの `instructor` パラメータでの絞り込みにしか使っていない。教員名を持つのは `GET /syllabi/{code}` だけである。したがって**検索結果に教員名を出すには、表示中のページ分だけ詳細を引いて補う**(frontend のサーバ側描画で行う。`lib/syllabus-api.ts` の `fetchInstructorMap()`)。同時実行を抑え、取得した詳細は1日キャッシュし、失敗した科目は教員名なしで並べる。api-clean は無変更で使う前提(§1.1.1、§3.4.4)であり、一覧側に教員名を足す選択肢は取らない。

**`grading`(成績評価)は TEXT 列だが、中身は JSON 文字列である。** `{"評価項目": [{"項目", "割合", "基準", "備考"}], "自由記載": ...}` の形で、シラバスバックエンドが年度間の表記を揃えた結果である。**素のまま描くと画面に JSON が出る**ため、表示側で構造へ戻す(`lib/grading.ts` の `parseGrading()`)。構造化されていない生テキストの行もあり得るので、JSON として読めない値はテキストとして扱う。

**レスポンスの `count` は総ヒット数ではなく、そのページで返した件数**(`len(rows)`)である。api-clean に総件数を返す口は無く、`POST /sql` はゲートウェイが拒否する(§3.4.4)。

**総件数は全件を引いて得る。** かつては `limit=1` の空振り判定で `MAX_ROWS`(500)単位のブロックを特定し、最後のブロックだけを数えていた(検索1回につき余分に3〜4リクエスト)。**タグでの絞り込みを全件に効かせるため全件を引くようにした結果(§6.1)、この数え上げは不要になった** — `results.length` がそのまま総件数である。

**api-clean は DGX Spark 上にあり、この通信はホストを跨ぐ**(§3.4.4)。宛先は教員側のトークンゲートウェイであり、**base_url とトークンを環境変数で与える**(vllm 向けと同じ形。§6.3)。ゲートウェイは**上記3つと `/healthz` だけを通し、`POST /sql` を拒否する**(§3.4.4)。

これに伴う留意点が2つある。

- **ゲートウェイへ到達できないと、ここに挙げた3つの口がすべて失敗する。** 影響範囲と検知の要否は §3.4.4 に置く
- **ホストを跨ぐぶん所要時間が伸びる。** とくに §7.2.4 の一括取得は数百件規模をページ送りするため、`http_timeout`(既定 30 秒)で足りるかを実測する(§13)

**api-clean へ送るのは科目の検索条件のみとし、学生プロファイルは渡さない**(§4.2.3)。

`POST /sql` はエージェントに任意 SQL を書かせるリスクを避けるため使用しない方針とする。**ゲートウェイ側でも拒否するため、backend から到達する手段は無い**(§3.4.4)。

### 6.3 vLLM との連携

**backend は vllm を直接呼ばない。** 教員側が運用するトークンゲートウェイ(OpenAI 互換)を経由する(経路の実測は §3.4.3)。

- base_url はトークンゲートウェイのテキスト用エンドポイント、api_key は発行されたトークン(`Authorization: Bearer <token>` として送られる)
- PydanticAI の `OpenAIChatModel(<モデルID>, provider=OpenAIProvider(base_url=<ゲートウェイのURL>, api_key=<トークン>))` 形式で設定する(base_url / api_key はモデルでなく `OpenAIProvider` に渡す。旧称 `OpenAIModel` は現行 pydantic-ai で `OpenAIChatModel` にリネーム)
- **base_url・api_key・モデル ID はいずれも環境変数で与え、コードにもイメージにも埋め込まない。** トークンは有効期限を持ち、更新時に値が変わる(§3.4.3)
- モデル ID は `GET /v1/models` が返す値を用いる。不一致は `400 model_mismatch` となる
- ツール呼び出しは PydanticAI の `@agent.tool` で定義し、内部で api-clean を HTTP で叩く(ツールの実行は backend 側である。api-clean への到達もトークンゲートウェイ経由となる。§6.2)

**ゲートウェイ固有の応答を扱う必要がある。**

| 応答 | 意味 | backend の扱い |
|---|---|---|
| `503 busy` | 同一トークンで生成が進行中 | **即座に返る(待たされない)。**再送、または待ち行列に入れて待ち時間を提示する。学生に「混雑」として見せる文言を用意する(§3.4.3) |
| `401` | トークンが無い・不正・期限切れ・失効 | 全機能が停止する。運用として検知できるようにする(§13) |
| `400 model_mismatch` | モデル ID が接続先の期待値と異なる | 設定誤り。起動時の疎通確認で検出する |
| `413 payload_too_large` | 本文が上限(既定 16 MiB)を超えた | 履修提案のプロンプトは数万トークン規模であり通常は到達しないが、上限の存在を前提に置く |
| `502 upstream_unavailable` | vllm 側が応答しない | vllm の停止・再起動中。学生には一時的な不調として提示する |

**利用ログが100日間保存される。** プロンプトと応答が記録されるため、プロンプトに載せる学生データを最小化する(要件§5.5、§9、§7.2.1)。

#### 6.3.1 リクエスト単位の推論設定(思考の有無)

Qwen3.8 は思考(reasoning)モデルだが、**Qwen3.6 から思考の制御方法が変わっている。** `config.json` は1行しか違わない(§4.3)のに対し、**チャットテンプレート(`chat_template.jinja`)は変わっている**(2026-09-19 差分確認)。

**`enable_thinking` は思考の ON/OFF スイッチではなくなった。** 3.6 では思考の生成そのものを止めるハードスイッチだったが、3.8 では**システムプロンプトに「よく考えよ」という指示文を挿入するかどうか**の制御に変わっている。思考を出すかどうかは**モデルの裁量**である。

代わりに **`reasoning_effort`** が入った。`enable_thinking` が真(既定)のときだけ効き、`xhigh`(既定) / `medium` / `low` の3値を取る。**3値以外を渡すとテンプレートが例外を投げて失敗する。**

| 値 | 挿入される指示 |
|---|---|
| `xhigh`(既定) | 注意深く考え、前提を検証し、代替案を検討し、正確さ・一貫性・明快さを優先せよ |
| `medium` | 指示なし(テンプレートに文言が定義されていない) |
| `low` | 思考は簡潔に、余計な展開をせず結論へ直行せよ |

**`preserve_thinking` の既定も反転した。** 3.6 は既定 false(過去ターンの思考を履歴に残さない)、3.8 は**既定 true**(残す)である。マルチターンのチャット(§7.3〜§7.5)でコンテキストが伸びる。あわせて、3.6 にあった「`content` から `</think>` を切り出して `reasoning_content` を復元する」フォールバックが 3.8 では削除されている。

**実機では思考の出力を一度も観測できていない**(2026-09-19、数百トークンのプロンプトで5回。`enable_thinking` の真偽、`reasoning_effort` の `xhigh` / `low` を変えても `reasoning_content` は常に空で、`content` への `<think>` の漏れも無い)。**ただし本番条件では未検証である** — 3.6 で問題になったのは候補科目643行・約39,000トークンのプロンプトであり、短い質問で思考しないことと、長大なプロンプトで思考しないことは別である。

**したがって `--reasoning-parser qwen3`(§4.3)が正しく働くかも未確認である。** 思考が出力されていない以上、パーサの出番が無かっただけかもしれず、「`<think>` の漏れが無い」ことは「パーサが動く」ことの証拠にならない。**このオプションは外さずに残す** — 思考が出た場合に分離してくれる保険であり、出ないなら無害だからである。検証は §13 に置く。

| 呼び出し | 思考の指定 | 理由 |
|---|---|---|
| 履修提案(§7.2 / `POST /api/proposal`) | **`enable_thinking: false` を渡し続ける**(暫定) | 3.6 での判断の名残である。**3.8 ではこの指定に思考を止める力は無い**が、指示文が入らない分だけ出力が短くなる方向に働き、害は無い。本番条件での再計測後に、`reasoning_effort: "low"` へ改めるか、指定そのものを外すかを決める(§13) |
| チャット系(§7.3〜§7.5) | 既定のまま | 自由文の対話であり、ツール呼び出しの要否判断を含む |

PydanticAI からは `OpenAIChatModelSettings(extra_body={"chat_template_kwargs": {...}})` を `Agent(model_settings=...)` に渡す形で指定する。

**以下の計測は Qwen3.6 で採ったものであり、Qwen3.8 では取り直す**(§13)。上記のとおり思考の制御方法自体が変わったため、判断の前提から見直す必要がある。

**履修提案で思考を切る理由(2026-09-09 実機計測。DGX Spark + Qwen3.6-27B-FP8)。** 候補科目643行・約39,000トークンのプロンプトに対し、思考を有効にすると900秒経っても提案が返らなかった。このとき vLLM は 7.3 tokens/s で生成を続けており(`GPU KV cache usage` 17.5%、preemption なし)、停止や資源不足ではなく**思考が終わっていなかった**。600トークンで打ち切って観測しても本文には到達していない。`enable_thinking: false` を渡すと `final_result` の生成が即座に始まり、候補科目からの転記・不足要件枠への言及・希望条件の反映を含む提案が得られた。

提案は【候補科目】からの選択と転記が主であり、要件枠ごとの不足単位・開講曜日時限といった判断材料は backend が事前に揃えてプロンプトへ入れる(§7.2)。モデルに長い思考を求める課題ではない。

あわせて `max_tokens` と `timeout` を置く。出力が途中で切れると提案は書き終えた科目までになる(§7.2.2)ためである。

### 6.4 書誌の補足(openBD)

**書影と書誌の詳細は openBD(<https://openbd.jp/>)から引く。** api-clean の書誌(`textbooks`)は書名・著者・出版社・ISBN・価格しか持たず(§6.2)、**その本がどんな本なのかを判断する材料が無い**。ISBN から openBD を引き、書影・内容紹介・目次・ページ数を補う(§8.1)。**本設計で唯一、backend を介さずに参照する外部サービス**である(§1.1)。

| 口 | `GET https://api.openbd.jp/v1/get?isbn=<ISBN>[,<ISBN>...]` |
|---|---|
| 認証 | 無し(公開 API・登録不要) |
| 応答 | **要求した順の配列。** 該当が無い要素は `null` |
| 呼び出す側 | frontend のサーバ側描画(`lib/openbd.ts`)。書影の画像そのものはブラウザが直接引く |

取り出す値は次のとおり。**欠けている項目はその行ごと出さない。**

| 項目 | 場所 | 備考 |
|---|---|---|
| 書影 | `summary.cover` | **無い本は空文字**。`https` 以外は混在コンテンツになるので捨てる |
| 内容紹介 | `onix.CollateralDetail.TextContent` の `TextType` = `03`、無ければ `02` | `03` が長い紹介、`02` が短い紹介。**HTML が混じることがある**ので、素のテキストとして出す(タグは落とす。`dangerouslySetInnerHTML` は使わない) |
| 目次 | 同 `TextType` = `04` | 改行がそのまま入っている |
| ページ数 | `onix.DescriptiveDetail.Extent` のうち `ExtentUnit` = `03`(ページ) | |
| 刊行年月 | `summary.pubdate` | `201806` / `20180709` の形。年月まで出す |
| シリーズ | `summary.series` | **装丁の種別が入っていることがある**(有斐閣の単行本が `単行本` で返る)。そのまま出すと読む側に何も伝わらないので落とす |

**書誌ページへのリンクは版元ドットコム(`https://www.hanmoto.com/bd/isbn/<ISBN-13>`)に出す。** openBD の書誌はここが集めているため、**openBD が書誌を返した本は版元ドットコムにページがある**(洋書を含め実地に確認済み。未登録の ISBN は 404 になる)。したがって**リンクを出すのは openBD が書誌を返した本だけ**に限る。ISBN-13 でしか引けないので、こちらの持つ生値ではなく **openBD が返す `summary.isbn` を使う**(ISBN-10 で問い合わせても13桁に直って返るため、桁の変換を自前で持たずに済む)。

**在庫状況(`ProductSupply.SupplyDetail.ProductAvailability`)は使わない。** 実データでは `99`(不明・その他)しか返っておらず、品切れ・絶版の判断には使えない。

規定は4つある。

- **1科目ぶんを1リクエストにまとめる。** `isbn` はカンマ区切りで複数取れる。書誌は1科目で最大16件あり、1件ずつ引くと講義詳細の描画が16往復ぶん遅くなる
- **引けなかったときは書影なしとして続ける。** 例外・非200・タイムアウト(3秒)はすべて空の対応表に畳み、講義詳細は今までどおり描く。openBD は本サービスの可用性の外にあり、**この口の失敗で講義詳細を落としてはならない**
- **「引けない」ことのほうが多い前提で作る。** openBD の書誌は版元ドットコムに登録されたものが中心で、大学の指定図書(学術書・専門書)は書影も紹介文も欠けることがある。引ける本と引けない本が混ざるため、**枠の大きさは書影の有無で変えず**、**書名を押して開けるのも引けた本だけ**にする(§8.1)
- **ISBN は正規化してから投げる。** 大学のデータはハイフンの有無が揃わず全角で入っている値もある(§8.2 の科目名と同じ事情)。NFKC で寄せて記号を落とし、ISBN-13(13桁)か ISBN-10(9桁＋数字か X)だけを通す。同じ本がテキストと参考文献の両方に載ることがあるため、正規化した値を鍵に重複を畳む

**キャッシュは1週間で再検証する。** 刊行済みの本の書影はまず変わらない。

**学生の情報は一切送らない。** 送るのは ISBN だけであり、誰が見ているかに依存する値を含まない。ブラウザが画像を引く際も `referrerPolicy="no-referrer"` を付け、**閲覧中の講義の URL を openBD へ渡さない**(要件§5、§9)。

### 7.2 履修提案生成

**この流れは学生が希望条件を送った時点で始まる。`/proposal` に到達しただけでは撃たない**(§8.3)。

```mermaid
sequenceDiagram
  participant User as 学生
  participant FE as frontend
  participant BE as backend
  participant API as api-clean
  participant LLM as vllm
  User->>FE: 希望条件を入力して送信(§8.3。書かずに始めることもできる)
  FE->>BE: POST /api/proposal(プロファイル+課程コード+入学年度+希望条件+対象学期)
  BE->>BE: 要件充足判定で要件枠ごとの不足単位を算出(§4.4.5)
  BE->>API: GET /syllabi(候補科目の開講情報を取得)
  API-->>BE: 開講コマ・教室(slots / room)
  BE->>BE: 対象学期のクラスに絞り、先修条件を判定する(§7.2.1)
  BE->>LLM: ChatCompletion(開講情報を含む、下書きの構造化出力スキーマ指定、stream=true)
  LLM-->>BE: 下書き(シラバスコードと理由)の JSON を chunk ストリーム
  BE->>BE: 候補一覧から科目の値を補い、重複・単位超過を外す(§7.2.2)
  BE-->>FE: SSE で時間割を配信(snapshot を逐次、最後に result)
  opt 科目を外した・途中で切れたとき
    BE->>LLM: 説明文の書き直し(§7.2.2)
  end
  FE->>FE: 時間割表を逐次描画
```

**応答時間は出力トークン数でほぼ決まる(2026-09-09 実機計測)。** 生成は約 7.3 tokens/s であり、プロンプト39,000トークンのプリフィルは約20秒で済む一方、全項目を書かせていた頃は CAP いっぱいの11科目の提案(約1,900トークン)に4〜5分かかった。v0.9.48 でモデルに書かせるものを下書き(シラバスコードと理由)に絞り(§7.2.2)、対象学期のクラスだけをプロンプトに載せるようにした(§7.2.1 手順4)後は、公開 VM から Qwen3.8 で試した2回が 81.8秒・68.7秒で成立した(2026-09-23。3回生の後期)。思考(reasoning)は切る(§6.3.1)。frontend はこの待ち時間を前提とし、確定を待たずに SSE の逐次配信で時間割を描く(§8 の `/proposal`)。

時間割(曜日×時限)の組み立てに必要な開講曜日・時限は、履修要項 YAML ではなく api-clean が保持する(§5.1)。backend は LLM 呼び出しの前に候補科目の開講情報を api-clean から取得し、コマ重複のない時間割を生成できるようプロンプトに含める。**この取得はホストを跨ぐ**(公開 VM → トークンゲートウェイ → DGX Spark。§3.4.4)ため、所要時間と失敗時の扱いは §6.2 の留意点に従う。**週複数コマ・複数クォーターの科目は2コマ目以降が見えない**(2025・2026年度のデータを投入した api-clean で確認)。`day_of_week` / `period` / `term` は1組だけで、「後期　月3・月4」は月3、「3Q　金2、4Q　金2」は 3Q・金2 になる(2026年度で「・」を含むもの約180件、「、」を含むもの約40件)。生値の `term_schedule_raw` は `GET /syllabi/{code}` にしか無く、候補は数百コード規模のため1件ずつは引かない。したがって2コマ目との重複は検証(§5.3)でも検出できない。解消には api-clean の一覧に生値を足す改修が要る(本リポジトリでは改修しない。§1.1.1)。

#### 7.2.1 プロンプトの組み立て

**提案エージェントはツールを持たない。** 提案に要る事実(要件枠ごとの不足単位・候補科目・開講情報)は backend が事前に集め、1つのプロンプトに書いて渡す(実体は `app/agents/proposal_agent.py`)。提案は候補科目からの選択と転記が主で対話的な探索を要さず、かつ思考を切っている(§6.3.1)ため、ツールを呼ぶか否かの判断をモデルに委ねると、呼ばれないまま推測で埋められる危険がある。tool calling を伴うのは提案後の対話(§7.3)である。

組み立ては次の5段階を順に行う。各段階は単体テストできるよう関数に分ける。

1. **履修要項の解決** — (課程コード, 入学年度)でマージ済みの履修要項を引く(§4.4.3)。無ければ 404
2. **要件充足判定** — §4.4.5 の純関数を **HTTP を経由せず直接呼ぶ**。要件§4.3.2 の「単位数の最適化」は要件枠ごとの不足単位を要する
3. **候補科目の抽出** — 次のすべてを満たす科目に絞る
   - `type != "随意"`(卒業要件単位に算入されない。§5.1.5)
   - `grade <= 対象学期の学年`(配当年次は「この年次**から**履修可能」の意。§5.1.5)
   - 未修得かつ未登録(合格した科目・登録済みの科目と突合する。不合格・履修辞退の科目は未修得であり候補に残す。登録済み(`registered`。§5.2.1)は成績未確定だが、すでに登録しているので外す)
   - シラバスコードを持つ(`not_offered` / `unresolved` の科目は時間割に置けない。§5.1.4)

   マージ済みの `courses` には他課程から導出した同名の専門関連科目が複数入り得る(§4.4.3)。ここでは科目名で1件に寄せ、当該課程の設置科目(`own`)を優先し、次いで課程コードの小さい出典を採る(§4.4.5 の科目索引と同じ順序)
4. **開講情報の突合** — 候補のシラバスコードに対応する曜日・時限・教室を api-clean から取る。`GET /syllabi?year=<開講年度>` を**ページ送りで一括取得**し、候補のコードだけを索引に残す。1件ずつ `GET /syllabi/{code}` を引かないのは、候補が数百件規模になるためである。あわせて**対象学期の履修登録で登録するクラスだけを残す** — 前期の登録では前期・1Q・2Q・通年・サ集、後期の登録では後期・3Q・4Q。通年科目は前期に登録する(2026年度の通年118件のうち110件は「通年　集中」)。サ集は夏期集中(「サ集　集中」)で後期より前に終わるため前期に含める。api-clean の `term` はマスタの8種(前期 / 後期 / 通年 / 1Q〜4Q / サ集)であり、2025・2026年度のデータを投入した api-clean で確かめた。マスタに無い表記は判定せず落とさない。実データでは、2026年9月作成の成績表(3回生)で候補のクラス行が 426 行から 207 行(後期・3Q・4Q のみ)に減り、プロンプトもほぼ半分になった。この絞り込みも履修可否と同じく、1科目あたりのクラス数を絞る前に掛ける。1クラスも突合できなかった科目は、曜日・時限が分からず時間割に置けないため候補から外す。**したがって api-clean へ到達できない状態では候補が全滅し、提案が成立しない**(§3.4.4)。同名で多数のクラスが開講される科目(「英語総合1(A)」で22クラス、「スポーツ技術学A」で32クラス)はプロンプトを占有するため、曜日・時限・コードの昇順で上位数件に絞り、残りは件数だけを添える
4b. **先修条件の判定** — 開講情報を突き合わせた後の候補(対象学期に実際に選べる科目)に、履修要項の先修制(§5.1.5 `prerequisites`)を掛ける。結果は3つに分け、プロンプトの【先修条件】節に原文(`notes`)とともに書く。
   - **満たしている** — 候補に残し、満たしていると明記する。2026-09-23 の実機では判定材料を渡しておらず、モデルが「先修要件がある場合があり」と一般論で書いた
   - **満たしていない** — 候補から外し、外したと書く
   - **確認が要る** — 原文しか無く機械的に判定できない条件(2024〜2026年度入学のデータでは電子情報通信課程の「応用セミナー」「専門基礎研究」の「研究室に配属されていること」だけ)、または判定時点(`as_of`)が対象学期以降でまだ成績が出ていないもの。候補に残す

   判定は行に直接書いた `min_credits` / `all_of` / `any_of` と `one_of` の AND。`one_of` は選択肢のどれか1つを満たせばよい(OR)。`as_of` があればその学期末までに修得した科目だけで数え、`one_of` の選択肢に `as_of` が無ければ行の `as_of` を使う。`min_credits` は、`from` があれば列挙した科目の修得単位の合計、`accepts` があれば当該区分に当たる修得科目の単位の合計、どちらも無ければ卒業要件総修得単位数(§4.4.5 の `earned_credits`)と比べる。不合格・辞退・登録済みは修得に数えない。

   3つの結果の組み合わせ方は次のとおり。AND(行の条件どうし、同じ科目に複数の行があるとき)は、1つでも「満たしていない」なら満たしていない、そうでなく1つでも「確認が要る」なら確認が要る。OR(`one_of`)は、1つでも「満たしている」なら満たしている、すべて「満たしていない」なら満たしていない、それ以外は確認が要る。

   v0.9.50 までの形式(`min_credits` / `all_of` / `any_of` / `as_of` の AND のみ)では、2026年度入学の英語科目(「英語コミュニケーションⅡ」「Global Understanding in English」「Forum」)の条件を書けず、原文だけで持っていた。指定科目群からの単位数(「英語総合1(A)〜3 のうち4単位以上」)と「または」を表せなかったためで、v0.9.51 で `min_credits[].from` と `one_of` を加えた(§5.1.5)
5. **整形** — 【対象学期】【学生情報】【卒業要件の充足状況】【履修登録単位数の上限】【修得済み科目】【登録済み科目】【先修条件】【候補科目】【希望条件】の9節に並べる。【修得済み科目】には修得済みの科目名と単位数、不合格・履修辞退の科目(再履修の対象)を書く(下記の最小化は未対応)。候補科目は**1行1クラス**とし、`[シラバスコード] 科目名 | 区分 | 履修区分 | 単位 | 配当年次 | 入る枠 | 学期 / 曜日時限 / 教室` の形で、モデルが値を転記するだけで済むようにする。**「入る枠」はその学生がその科目を修得したときに単位が入る要件枠で、backend が計算する**(`slot_destinations()`。下記)。CAP(§5.1.2 `registration_limits`)の節では**対象学期のセメスター**(1年前期を1として `(学年-1)×2+1` が前期、`+2` が後期)にだけ印を付ける。v0.9.46 までは次学期が前期・後期のどちらかをプロファイルから決められず、両方に印を付けてモデルに委ねていたが、その結果モデルは学期を混ぜて提案し得た(時間割表では同じコマの前期・後期の科目が上書きし合い、合計単位も2学期ぶんになる)

**プロンプトに載せる学生データは最小にする(要件§5.5、§9)。** プロンプトと応答はトークンゲートウェイの利用ログに100日間記録されるため(§3.4.3)、次を守る。

- **氏名・学籍番号は渡さない。**もともとブラウザ内の学生プロファイルにも保持していない
- **評語(秀・優・良・可等)と GPA は渡さない。**要件充足判定は合否のみで行う(要件§4.2)
- **修得済み科目の一覧は渡さない。**手順3の抽出条件により候補は未修得科目に限られるため、修得済み科目が提案に現れることはなく、一覧を渡す必要がない。進捗は【卒業要件の充足状況】の集計値で足りる
- **不合格・履修辞退の科目は【再履修の対象】として科目名のみ渡す。**再履修の要否はモデルの判断材料であり、これは落とせない。不合格と履修辞退の別は提案に影響しないため「未修得」に丸める

この措置を講じてもなお、課程・入学年度・学年と未修得科目の組合せから個人が推定される可能性は残る。要件§5.6 で学生に明示する。

**実装は未対応である**(2026-09-13 時点)。`app/agents/proposal_agent.py` の `_format_completed()` は修得済み科目名と単位数を渡しており、上記への変更と、変更後に提案の質が落ちないことの実機スモークによる確認が要る。

役割定義と規則は毎リクエスト同じであり、`Agent(instructions=...)` に固定で持たせる。学生ごとの事実は上記のプロンプトで渡す。

```
あなたは龍谷大学先端理工学部の履修登録を支援するAIアシスタントです。
与えられた学生の状況から、**【対象学期】に履修する時間割**を提案してください。

提案は次の規則に従ってください。
1. 提案してよいのは【候補科目】に挙がっている科目だけである。一覧に無い科目名やシラバスコードを作り出してはならない。
2. courses の各要素には syllabusCode(【候補科目】の行の [ ] 内のコード)と reason だけを書く。科目名・曜日・時限・学期・単位はシステムが候補一覧から補う。同じ科目(同名の別クラスを含む)を2回入れない。
3. 同じ曜日・時限で開講期間が重なる2科目を割り当ててはならない(前期と1Q・2Q、通年と前期・後期は重なる)。「金4・金5」のように複数のコマが書かれたクラスは、そのすべてのコマを占める。曜日・時限が「未定」の科目(集中講義など)はこの制約の対象外とする。
4. 提案する科目の単位の合計は、【履修登録単位数の上限】の「対象学期に登録できる残り単位」を超えてはならない。
5. 【卒業要件の充足状況】で不足している要件枠を優先して埋める。科目がどの要件枠に入るかは【候補科目】の「入る枠」に従い、区分や科目名から推測しない。「入る枠」は科目を1つだけ足したときの値で、同じ枠の科目を不足より多く選ぶと、超えた分は別の枠に回る。不足単位を大きく超える科目数を詰め込まない一方、卒業に必要な単位を取り残さない。過不足のない分量にすること。
6. 【修得済み科目】に挙がっている科目と【登録済み科目】は提案しない。ただし不合格・履修辞退の科目は未修得であり、提案してよい。
7. 【希望条件】がある場合はそれを尊重する。卒業要件と両立しない希望は、summary でその旨を説明する。
8. reason には、その科目を勧める理由(どの要件枠を埋めるか、希望条件のどれに合うか)を40字以内の1文で書く。
9. summary には提案全体の方針と履修上の注意点を2〜4文で書く。【先修条件】で「確認が要る」とされた科目、進級要件・抽選科目など確認が要る点があれば触れる。【先修条件】で満たしているとされた条件について、不確かな書き方をしない。
10. summary に単位数の合計や内訳の計算を書かない。単位数はシステムが計算して画面に表示する。
```

規則1・2は、候補一覧に無い科目名やシラバスコードを作られると履修できない時間割になるためのものである。v0.9.48 からは、規則2のとおりモデルにコードと理由だけを書かせ、コードも下書きの形式で候補のものに限る(§7.2.2)ため、形式の上でも守られる。規則3・4(コマ重複と単位の上限)も書き終えた下書きを backend が確かめて外す(§7.2.2)が、外すと提案が細るのでプロンプト側にも置く。規則4の「残り単位」は、対象学期の上限から対象学期に登録済みの科目の単位を引いた値で、【履修登録単位数の上限】の節に数値で書く。規則5が「過不足のない分量」を求めるのは要件§4.3.2 による。規則10は、2026-09-23 の実機で説明文の単位数の計算が誤っていた(小計14と7を正しく出しながら「合計24単位で上限をちょうど満たします」と書いた。実際は21単位)ためである。単位数は画面の単位バーに backend の計算値が出るので、説明文で繰り返す必要がない。科目を外したときの説明文の書き直し(§7.2.2)にも同じ規則を置く。

**「入る枠」を backend が計算して渡す理由。** 履修要項の科目は区分・履修区分・科目群(`subcategory`)・基幹(`kikan`)を持ち、要件枠は `accepts` でそれを受け入れる(§5.1.5)。しかし v0.9.51 までの候補の行には区分と履修区分しか書いておらず、どの枠に入るかはモデルが推測していた。2026-09-23 の実機では、〈基幹〉でない社会科学系科目(「現代社会と労働」「現代社会とメディア」)で「教養教育科目(選択必修〈基幹〉・社会)」を埋めると説明文に書いた(実際は教養教育科目(選択)とオールフリーゾーンに入り、基幹・社会の不足2単位は残った)。枠は科目の属性だけでは決まらず、**その学生の充足状況で変わる**(満たした枠からは `overflow_to` の先へ回る)ため、属性を並べるだけでは足りない。計算は要件充足判定(§4.4.5 の `judge()`)をそのまま使い、修得済み科目にその科目を1つ足して判定し直し、修得単位が増えた枠を拾う。割り当て・溢れ・算入上限の規則を二重に実装しないためである。1回の判定は1ミリ秒程度で、185科目で0.2秒に収まる。複数の枠に分かれるときは単位数を添えて並べ、どの枠の不足も減らさない科目は「なし(受け入れる枠はすでに満たしている)」と書く

#### 7.2.2 下書きと提案の組み上げ

**モデルには提案の下書き(シラバスコードと理由、全体の説明)だけを書かせ、科目名・曜日・時限・学期・単位・履修区分は backend が候補一覧から補う**(`app/schemas/proposal.py` の `proposal_draft_model()`、`app/agents/proposal_agent.py` の `assemble_proposal()`)。

**経緯(2026-09-23 の実機。Qwen3.8)。** 全項目を書かせる形式で提案を試したところ、次の3点が起きた。

- 同じ科目の並びを繰り返し書き続け、`max_tokens`(4000)で打ち切られて失敗した(620秒)
- シラバスコードを1件も書かなかった(形式が null を許していた)
- 1周目の中身もコマ重複と単位の上限超過を含んでいた

**下書きの形式はリクエストごとに作る。**

- `syllabusCode` は**その回の【候補科目】のコードだけ**の列挙とする。vLLM の構造化出力(`tool_choice: required`)が形式を縛るので、候補に無いコードは書けない
- `courses` の件数に上限を置く。これは**暴走止め**であり、単位の上限そのものではない。単位の合計は JSON Schema で表せないため、書き終えた後に backend が確かめる。上限は「残り単位 ÷ 候補の最小単位 + 3」(最大30件)で、繰り返しが起きても `max_tokens` に届く前に書き終わる。+3 は、上限を超える科目や重なる科目を書いた分(backend が外す)だけ提案が細らないための余裕である

**書き終えた下書きは、作り直させずに backend が整える。** 作り直すと提案1回ぶんの時間(下書きの形式で1分強、以前の形式では4〜5分)がもう一度かかるためである。モデルの書いた順に1件ずつ見て、次のものを外す。

| 外すもの | 調整の記録 |
|---|---|
| 同じ科目の2件目以降(同名の別クラスを含む) | 残さない(情報が失われない) |
| 同じ曜日・時限で開講期間が重なる2科目のうち軽い方(§5.3 と同じ規則。**全コマどうし**で比べ、記録には重なったコマを書く) | 残す |
| 採ると対象学期に登録できる残り単位を超えるもの | 残す |

**重なったら重い方を残す。** 重さは履修区分で、必修 > 選択必修 > 選択 とし、同じ重さなら先に書いた方を残す。後から来た科目の方が重ければ、先に採った方を外して入れ替える(入れ替えると残り単位を超える場合は入れ替えない)。2026-09-23 の実機では、先に書いた方を残す決め方のために、教養の「英語総合4」(1単位)を残して専門応用科目の「アルゴリズム及び演習Ⅰ・Ⅱ」を2つとも外していた。**履修区分は学生にとっての区分**とし、他課程から導出した専門関連科目は開講元での区分(例: 環境の課程で必修の「地球環境概論A」)ではなく「選択」とする(プロンプトの【候補科目】の表示も同じ)。

記録は科目名ごとに1件とし、同名の別クラスを後で採った科目には残さない。件数では打ち切らない。

**調整の記録は学生に見せない。** summary は画面の吹き出しにそのまま出るため、記録を summary に混ぜると backend の都合が学生に見える。記録は `result` イベントの `adjustments`(文字列の配列。§6.1.1)に載せ、frontend は読まない。確認用のスクリプト(`backend/scripts/smoke_proposal.py`)が表示する。

**科目を外したときは、説明文だけを書き直させる。** summary はモデルが外す前の並びを見て書くため、外した科目に触れていることがある(2026-09-23 の実機では「アルゴリズム及び演習Ⅰ・Ⅱで4単位確保」と書かれたが、2科目とも外されていた)。外した科目か打ち切りがあったときだけ、確定した時間割・元の説明文・【卒業要件の充足状況】を渡し(時間割の各科目には、**確定した科目をすべて修得したときに**単位が入る要件枠を添える。`placed_slots()`。科目どうしの取り合いまで反映するので、同じ枠の科目を不足より多く選んだ分が下流の枠に入ることも正しく書ける)、ツールを持たない別のエージェント(`build_summary_agent()`)に2〜4文で書き直させる。出力が数文なので提案本体より短く済み、何も外していなければ呼ばない。書き直しに失敗したら元の説明文を使う(提案は成立しているのでエラーにしない)。

**作り直しはさせない(`OUTPUT_RETRIES = 0`)。** 下書きの形式は vLLM が縛るため、検証に落ちるのは実質的に**出力の上限で途中で切れたとき**だけである。pydantic-ai は切れた下書きも「JSON が不正」として作り直しを頼み、上限に達したと分かるのは作り直しを使い切った後になる(2回なら所要時間が3倍)。0 にすると切れた時点で例外になる。その場合でも、**理由まで書き終えた科目が1つでもあれば、そこまでで確定版(`result`)にし**、打ち切ったことを調整の記録に残す。summary を書き終える前に切れた場合は定型文を入れる。1つも無ければ `error` とする。

**途中経過(`snapshot`)も同じ組み上げを通す。** 書きかけの下書きから理由まで書き終えた科目を取り出し、候補一覧の値を補って流す。途中経過と確定版で科目の値が食い違わない。

回答内容は LLM 依存で非決定的なため、単体テストで確かめるのは各段階の関数の入出力と、規則がプロンプトに載ることまでとし、提案が実際に成立するかは実機スモーク(`backend/scripts/smoke_proposal.py`)で確認する(§12.3)。

#### 7.3.1 システムプロンプト

backend は毎リクエスト、次のプロンプトを `instructions` としてエージェントに渡し、末尾に提案を camelCase の JSON のまま【現在の提案】として連結する(実体は `app/api/chat_proposal.py` の `_PROPOSAL_PROMPT`)。

```
あなたは龍谷大学の履修登録を支援するAIアシスタントです。
学生に提示済みの履修提案(時間割)についての質問に日本語で答えてください。
講義の内容を問われたときは、ツールでシラバスを検索・参照してください。

回答は次の規則に従ってください。
1. 提案の内容は【現在の提案】に書かれているものがすべてである。そこに無い科目を提案済みであるかのように書かない。
2. 講義の内容・評価方法・教科書などシラバスの事項は、ツールが返した内容だけを根拠にする。ツールを使わずに答えない。
3. シラバスの語をそのまま使う。より具体的な語や製品名への言い換えをしない(例:「文書作成ソフト」を「Word」と書き換えない)。
4. 科目名・単位数・曜日・時限・学期は【現在の提案】の値をそのまま用いる。自分で計算・推定しない。合計単位数は totalCredits を答え、これが null のときは不明と答える。
5. 卒業要件の充足状況は、【現在の提案】の summary と各科目の reason に書かれている範囲でのみ述べる。不足単位を自分で算出しない。
6. 同じ科目名で複数のクラスが開講されている場合は、どのクラスの情報かを講義コード・担当教員・サブタイトルで明示し、他のクラスにも当てはまるかのように書かない。
7. 提案の変更を求められたときは、変更案を文章で示すにとどめる。時間割を差し替えたかのようには書かず、実際の作り直しは提案の再生成で行うと案内する。
8. 推測を述べる場合は、推測であることを明示する。
9. 情報が無い事項は、無いと答える。
```

提案チャットはシラバスチャット(§7.4)と同じ `chat_agent` を共用し、専用のエージェントは作らない。提案を camelCase の JSON に直して `instructions` に載せることで役割の差をそこで吸収しているためである。

規則4・5が科目名・単位数・曜日・時限・学期、合計単位数(`totalCredits`)、卒業要件の充足状況(`summary`・各科目の `reason`)を【現在の提案】の値に固定しているのは、提案チャット固有の危うさが「提案そのものを言い直すうちに中身が変わる」ことにあるためである。これらは提案に書いてあり、モデルが数え直す必要はない。

規則7は、対話の中で時間割を差し替えたかのように書かせないためのものである。作り直しは提案の再生成(§7.2)で行う。規則6はシラバスチャットの規則6(§7.4.1)と同じ文言であり、同じ誤りに同じ規則を当てる。

回答内容は LLM 依存で非決定的なため、単体テストで確かめるのは規則がプロンプトに載りモデルに渡ることまでとし、規則の効果は実機スモークで確認する。提案チャット専用のスモークスクリプトは未整備であり、§13 に挙げる。

#### 7.4.1 システムプロンプト

backend は毎リクエスト、次のプロンプトを `instructions` としてエージェントに渡す(実体は `app/api/chat_syllabus.py` の `_SYLLABUS_PROMPT`)。§7.5 も同じ本文を先頭に置き、その後ろに対象講義の詳細を連結する。

```
あなたは龍谷大学の履修登録を支援するAIアシスタントです。
学生のシラバスに関する質問に日本語で答えてください。
必要に応じてツールを使ってシラバス情報を検索・参照してください。

回答は次の規則に従ってください。
1. ツールが返した内容だけを根拠にする。シラバスに書かれていない事項を補わない。
2. シラバスの語をそのまま使う。より具体的な語や製品名への言い換えをしない(例:「文書作成ソフト」を「Word」、「ネットワークストレージ」を「クラウド」と書き換えない)。
3. シラバスにない形容や評価を付け加えない(例:「実践的な」)。
4. 週数・回数・期間などの数値は、シラバスに書かれている場合だけ示す。自分で計算・推定しない。
5. 必修・選択必修・推奨といった履修要件の判断はしない。シラバス検索ツールはこれを判断できる情報を返さないため、履修要項で確認するよう案内する。
6. 同じ科目名で複数のクラスが開講されている場合は、どのクラスの情報かを講義コード・担当教員・サブタイトルで明示し、他のクラスにも当てはまるかのように書かない。
7. 推測を述べる場合は、推測であることを明示する。
8. シラバスに情報が無い事項は、無いと答える。
```

規則2〜4が個別の言い換えを名指ししているのは、2026-09-04 の実機検証で**捏造が装飾部分に集中して現れた**ためである。科目名・単位・担当教員・各回の内容といった骨格は原典どおりで、誤りは「文書作成ソフト」→「Word」、「ネットワークストレージ」→「クラウド」のような一般語の具体化、原典にない概念(プライバシー保護)の追加、`course_plan` の回数からの開講週数の推定、原典にない形容(「実践的な」)の付加として出た。「シラバスにない事を書くな」という一般規則だけではこれらは抑止されない。LLM の側にはいずれも言い換え・要約の範囲内に見えるためである。したがって観測された誤りの型を具体例つきで挙げる。

規則5は、必修・選択必修の判定に使える情報をシラバス検索ツールが返さないことによる。課程の紐付け(`programs`)は返るが、これは「どの課程の科目か」を示すのみである。**必修・選択必修の別は api-clean から取得できない**(§1.1.1)。科目区分を持つ `syllabus_attribute` が空であり、`note`(例: `Y1000 ◎`)の意味も未解明であるためである(§13)。判定の根拠が無い以上、履修要項側で確認させる。**科目区分がツールから取れるようになった時点で、この規則は見直す。**

規則6はプロンプト単独では働かない。同名科目が何クラス開講されているかを LLM が知る手段が無く(`search_syllabi` は api-clean のレスポンスをそのまま返す)、規則は「知っていれば書け」としか作用しないためである。**クラス数をツールの返却値に含める**(§13)。

回答内容は LLM 依存で非決定的なため、単体テストで確かめるのは規則がプロンプトに載り両ルートでモデルに渡ることまでとし、捏造が実際に消えたかは実機スモーク(`backend/scripts/smoke_chat_syllabus.py`)で確認する。

## 8. 画面構成とルーティング

| パス | 画面 | 主な機能 |
|---|---|---|
| / | 成績表の取り込み | PDF取り込みと取り扱いの確認ダイアログ(要件§5.6)、取り込み内容の確認、解析失敗時の手入力フォールバック、デモモードの読み込み(§11) |
| /import | (旧ルート) | `/` へ転送するだけ。古いリンクから来た人を取り込み画面へ送る |
| /proposal | 履修提案 | 希望条件の入力と提案の開始・再提案(§8.3)、時間割表示、提案チャット(要件§4.3、§4.4) |
| /syllabus | 独自シラバス一覧 | 検索、タグ表示(状態 / 区分 / 履修区分の3軸。要件§4.5) |
| /syllabus/[code] | 講義詳細 | シラバス情報、講義単位チャット(要件§4.6) |
| /mydata | マイデータ | 取り込んだプロファイルの確認・編集・破棄(要件§4.1、§4.8) |
| /privacy | プライバシーポリシー | データの流れの図解、要件§5の規定説明 |

**取り込み完了画面の行き先は履修提案だけではない。** シラバス検索への入口も同じ画面に置く(PC は `履修提案を見る` の下に、モバイルは「次のステップ」の3枚目に)。取り込んだプロファイルは**検索結果のタグ付けに効く**(§6.1.3)ため、取り込み直後は「自分にとっての必修・選択・修得済み」が付いたシラバス検索が使えるようになっている。そこへ辿り着く手段が履修提案経由しか無いと、要件§4.5 の主機能への導線が実質1本になる。

**PC とモバイルで同じ URL に同じ役割の画面を置く。** 見た目(レイアウト)だけを画面幅で切り替え、どの URL がどの画面かは端末に依らない(各 `page.tsx` が PC 用とモバイル用の組み立てを並べて置き、CSS で出し分ける)。v0.9.62 までのモバイルは `/` が時間割、`/import` が取り込み、`/proposal` がページ内に対話欄を持つ別物の提案画面であり、**同じリンクが端末によって別の画面を開いていた**(PC の `/` は取り込み、`/proposal` は時間割)。PC のルートに寄せ、モバイルも `/` を取り込み(手順は画面の中の3段で分ける)、`/proposal` を時間割とした。`/import` は転送だけを残す。ナビ(PC のヘッダー・モバイルのボトムドック)も同じ3つ・同じ行き先 — 時間割(`/proposal`)・シラバス(`/syllabus`)・マイデータ(`/mydata`)— を持ち、取り込み(`/`)ではどちらもナビを出さない。

`/mydata` は当初の設計には無く、実装で追加した。取り込んだプロファイルの確認・編集・破棄を、取り込みの手順とは別に後から開けるようにするためである。

**シラバス全体への質問に専用のルートは設けない。** 同じ口(`POST /api/chat/syllabus`。§7.4)は `/syllabus` から叩ける — PC は検索結果の右に AIパネルがあり、モバイルは画面下部のボトムドックの Ask Bar から AI シートが開く。**両者は同じ会話を読み書きする**(§4.1.5)。かつては講義を特定しない質問の入口として `/chat` を別ルートに置いていたが、**ルート表に載っていながらどの画面からもリンクされておらず、URL を直接開く以外に到達できなかった。** 要件§4.6 の「シラバス全体に対する質問」は検索画面の面で満たすため、重複するこのルートは削除した。

### 8.1 講義詳細（`/syllabus/[code]`）の情報設計

**開講の表示は `term_schedule_raw` を整形して使い、1か所にだけ出す。** api-clean の `day_of_week` / `period` は1コマ分しか持たないため、`２Ｑ　火４・火５` のような複数コマ科目では2コマ目が落ち、集中講義(2026年度で 263 件)では両方が null になる。生値には開講期とコマがそのまま入っているので、**全角の数字を半角に寄せ、`月３` を `月3限` に直して出す**(`lib/schedule.ts`)。`３Ｑ　金２、４Ｑ　金２` のように期が分かれる科目は行を分ける。開講期はこの1か所にだけ置き、見出しのバッジには出さない。**生値を持たない一覧**(`/syllabus`)は api-clean 0.3.0 の `slots`(§6.2)から `金4・5限` の形で出す(`formatSlots()`)。

**戻り先は開いた元に合わせる。** シラバス一覧から開いたときは「シラバス一覧に戻る」(絞り込みは `back` で復元。§8)、履修提案の時間割から開いたときは「時間割に戻る」(`from=proposal`。§8.3.4)。**「時間割に追加」はこの科目を時間割に直接登録する**(§8.3.6)。すでに入っている科目(同じシラバスコード)では「時間割に入っています」と「外す」に替え、時間割の「別の科目に変更する」から来たときは「(元の科目)をこの科目に変更」に替える。

**基本情報にはラベルを付ける。** 開講・担当教員・単位・配当年次・場所・対象学部(課程)をラベルと値の組で並べる。アイコンと値だけを横に並べると、`オンライン` がキャンパスなのか授業形態なのか、`2年次～4年次` が何の年次なのかが読み取れない。

**api-clean が返しているものを捨てない。** 書誌(`textbooks`)は自由記述とは別に構造化されて返っており(2026年度でテキスト 607 件・参考文献 1,206 件)、書名・著者・出版社・価格まで出す。

**書影は ISBN から openBD に引き、引けたものだけ出す(§6.4)。** 書名の文字列だけが縦に並ぶ一覧では、指定された本が手元のどれなのかを本の見た目で照合できない。**ただし書影が付くのは一部の本だけ**(openBD の書影は版元ドットコム登録分に限られる)なので、**引けなかった本の枠は書影と同じ大きさの背表紙アイコンのままにする。** 書影の有無で行の高さが変わると、1科目に何冊も並ぶ書誌が階段状になる。

**書名を押すと、その本の内容紹介・目次・ページ数と、版元ドットコムの書誌ページへのリンクが開く(§6.4)。** 書名・著者・出版社だけでは、その本が何を扱っていて講義にどう関わるのかが分からない。**押して開けるのは openBD が書誌を返した本だけ**にする — 引けなかった本は押しても出せるものが無く、押せるように見えるほうが誤りである(タグを「判定できないものには出さない」(§8.2)のと同じ扱い)。**開閉は `<details>` で組み、この木をクライアントコンポーネントにしない。** 開閉のためだけに講義詳細へクライアント JS を足す必要はなく、`<details>` はキーボード操作と支援技術への対応を素で持つ。**逆に、紹介文も目次も無い本でもパネルは開く** — 版元ドットコムへのリンクはどの本にも出せるので、そこから先を辿れる。

**備考(`note`)は履修登録の注記であり、扱いを3つに分ける。** 2026年度は1,512件すべてに値が入っており、中身は (1) 登録方法 — `【抽選登録科目】`(392件)・`【オープン登録科目】`(221件)、(2) ラベル付きの注記 — `【対象】T:情報メディア学科、Y:知能情報メディア課程` の形、(3) 履修要項の記号 — `Y4000` と `◎`(840件)のような科目区分コードと必修記号、に分かれる。**抽選かオープンかは履修できるかどうかそのものなので、これだけを見出しのタグとして出す。** (2)はラベルと値に分け、(3)は原文のまま並べる。**(3)を言葉に開いて書き換えない。** 記号の対応は履修要項側の定義であり、シラバスの値だけからは確定できない(§13)。

**同じことを2か所に書かない。** 備考の `【対象】` は 238 件あるが、うち 102 件は基本情報の対象課程と同じ内容であり、落としてよい。残す条件は、対象課程に無い課程を挙げているか(api-clean の課程マッピングが欠けている場合がある)、`留学生` のように課程では表せない条件を書いている場合に限る。**残すときも名前は組み立て直さず、名前空間を示す `Y:` だけを外す。** `T:` で始まる節は旧学科(理工学部)向けの表記であり、本システムの利用者である先端理工学部の学生には当たらないため落とす(`lib/courseTarget.ts`)。

**自由記述の改行は、折り返しのぶんだけ畳んでから出す。** api-clean の `summary`(授業概要)などは元の教務システムの固定幅のまま返っており、`…情報科学の基礎となる離散数` / `学の考え方を学ぶ。` のように**語の途中で改行が入っている**。講義詳細は本文を画面幅に合わせて流すため、この改行をそのまま出すと本文と無関係な位置で行が切れる。一方で、段落や箇条書きの区切りとして書き手が入れた改行は残さなければならず、**両者は本文からは見分けられない**。そこで**折り返しの証拠がある改行だけを畳む**(`lib/syllabusText.ts` の `unwrapWrappedLines()`。描画は `RichText`)。畳む条件は3つで、(1) その行が最長行と同じ桁数まで埋まっている(幅が尽きた以外に切れる理由がない)、(2) その行が句点で終わっていない、(3) 次の行が箇条書き・番号で始まっていない、である。**(2) を条件に入れるのは、文末の改行が書き手のものである可能性を捨てないため**であり、畳まずに残るのは文と文のあいだの改行だけで読めなくはならない。逆にここで畳むと、書き手が分けた文を1つにつないでしまう。**最長行が40桁に満たない本文には手を触れない** — 固定幅の折り返しではなく、短く書き分けた本文とみなす。つなぎ目は詰めるが、英字どうしは単語が溶けるため空白を挟む(URL の途中は詰める)。

**左は読み物、右は参照物に分ける。** 授業概要・到達目標・授業方法・授業外学習・授業計画を左に、成績評価・受講に際しての注意・備考・テキスト・参考文献を右に、この順で置く。**書誌は縦に長くなるので右の最後に置く。****縦に積むと本文がいたずらに長くなる**ためで、書誌は1科目で最大16件あり、これを本文側に入れると講義詳細の高さが5割増しになる。

**講義単位チャットの質問サジェストは、その科目のシラバスに対応する記述があるものだけを出す。** 講義単位チャットは対象講義のシラバスをそのまま渡し、「ツールが返した内容だけを根拠にする」「情報が無い事項は無いと答える」という規則で答えさせる(§7.4.1)。**対応する項目が無い質問は必ず「書かれていません」で終わる**ため、固定の文言を置かず、その科目が持つフィールド(`grading` / `textbooks` / `outside_study` / `goals` / `course_plan` / `methods` / `advice`)から組み立てる(`lib/courseQuestions.ts`)。例えば「課題の分量はどのくらい?」はシラバスに対応する項目が無く、多くの科目で空振りする。履修要件(必修 / 選択必修)の判断は §7.4.1 の規則5 で禁じているため入れない。

#### 8.2 タグ

**タグは一覧と詳細の両方に出す。** 突合は `lib/useTagMap.ts` に1つだけ置き、一覧(PC・モバイル)と詳細で同じ結果になるようにする。**`useTagMap()` は `Map` ではなくタグを決める関数を返す。** タグは履修要項との突合と履修可否の判定(§6.1.3)の2段でできており、関数として渡すことで呼び出し側が2段目を掛け忘れられないようにする。**履修できないクラスにはタグを出さない**ため、タグが付かない科目は「その学生には関係がないか、判定できなかったもの」である。

**タグは3つの軸に分ける。** 卒業要件の枠は **(区分 × 履修区分)** で決まっており(`basic.required` = 専門基礎科目 × 必修、`applied.elective` = 専門応用科目 × 選択、…。§5.1.5)、1つの軸に潰すとその対応が消える。学生が「この科目がどの枠を埋めるのか」を読み取れるようにするため、履修要項の構造をそのまま出す。要件§4.3.2 の「単位数の最適化」を学生が自分で判断する材料でもある。

| 軸 | 値 |
|---|---|
| 状態 | `修得済み` |
| 区分 | `教養教育` / `専門基礎` / `専門応用` / `専門関連` |
| 履修区分 | `必修` / `選択必修` / `選択` / `随意` |

出し方は次のとおり(`lib/syllabusUI.ts` の `resolveTags()`)。並びは **状態 → 区分 → 履修区分** に固定する。「もう取ったか」→「どの枠か」→「取る必要があるか」の順で、学生が途中で判断を打ち切れる。

| 状況 | 出すタグ |
|---|---|
| 履修不可(§6.1.3) | なし |
| 履修可 × 修得済み | `修得済み` + 区分 |
| 履修可 × 未修得 × 自課程の設置科目 | 区分 + 履修区分 |
| 履修可 × 未修得 × 他課程の設置科目 | `専門関連` のみ |
| 履修要項に無い | なし |

**履修区分を出さない場合が2つある。** (1) **修得済みのとき。** 履修区分は「これから履修する必要があるか」を示す情報であり、単位を修得した科目では意味を持たない。バッジも2つに収まる。(2) **他課程の設置科目(`own` が false)のとき。** その `type` は導出元の課程にとっての区分であって、閲覧している学生にとっての区分ではない(§6.1)。その学生にとっての区分は**専門関連科目**であり、`related` → `free.faculty` の要件枠に計上される(§4.4.3)。

**`選択必修` と `随意` を欠かしてはならない。** 従来は `選択必修` を `選択` に丸め、`随意` はタグなしにしていた。`選択必修` は2024・2025年度入学コホートで 142 科目あり(専門基礎24・専門応用52・教養66)、`随意` は 20 科目ある。**知能情報メディア課程の専攻科目には `選択必修` が1件も無い**ため第1フェーズでは露見しなかったが、他課程(数理・情報科学課程の専門応用13科目、電子情報通信課程の専門基礎9・専門応用13科目など)へ広げると必ず問題になる。`随意` は**卒業要件単位数に算入されず**(`graduation.excluded_types`)履修提案の候補からも外れる科目であり、他と区別が付かないのは危ない。

**色は履修区分にだけ使う。** 区分は「どの卒業要件枠に属するか」を示す分類であって緊急度の軸ではなく、色を割ると履修区分と競合してどちらを先に読むべきか分からなくなる。区分は4値とも共通の落ち着いた配色にし、色の差は必修 / 選択必修 / 選択 / 随意 にだけ与える(`随意` は卒業要件に算入されないため彩度を落とす)。**バッジの実装は `app/syllabus/_components/CourseTags.tsx` に1つだけ置く**(一覧 PC・一覧モバイル・詳細の3か所に配色表が写されており、値を増やすたびに3か所を直す必要があった)。

**ページ送りは結果の上にも置く。** 下端にしか無いと、次のページへ移るたびに一覧の末尾まで運ばせることになる。

**タグが付く条件は、絞り込みを試す前に見えるところへ出す。** タグは学生プロファイルとの突合で決まる(§6.1)ため、**プロファイルが無いあいだはチップも区分のセレクトも、押せるのに必ず0件になる**(`matchesFilter()` は `tags.requirement === activeTag` を見る)。しかも出る文言は「絞り込みに該当する科目がありません」で、本当の理由が画面のどこにも無かった。**チップの直下に、取り込みへのリンクを兼ねた案内を1本置く**(`SyllabusProfileNotice.tsx`。PC・モバイルで共用する)。絞り込みパネルの「区分」にも同じ条件で短い注記を添える — セレクトはパネルを開かないと見えない(モバイル)・スクロールの先にある(PC)ため、バーを見ていない学生もそこで気づける。

**プロファイルがあるときは出さない。** 「取り込むと絞れます」は取り込んだ後には誤りである。以前は PC の左サイドバーに 11px のグレーで常時1行あるだけ(モバイルには無し)で、取り込み済みかどうかの手がかりにもなっていなかった。

**両端のページへの飛び先は対称に出す。** ページ番号は現在地の前後にしか並ばないため、端のページは自力では反対の端へ辿り着けない。末尾への飛び先だけを足していた頃は、1ページ目からは「1 2 3 4 5 … 41」で最後まで飛べる一方、41ページ目は「37 38 39 40 41」となり**1ページ目へ戻る手段が「前へ」を40回だけ**だった。先頭と末尾は同じ規則で足す(`SyllabusPagination.tsx`)。**番号が隣り合うときは「…」を挟まない** — 飛ばしたページがあるように見えるため。

**検索の対象は先端理工学部に固定し、課程で絞れるようにする。** 本サービスの対象は先端理工学部の学生であり(要件§2.1。第1フェーズは知能情報メディア課程、第3フェーズでも同学部の他課程まで)、**他学部の科目は履修要項を持たないためタグ付け(§6.1)の対象外になり、履修の判断にも使えない**。したがって学部は選ばせず `先端理工学部` を常に送る(2026年度は 1,512 件中 1,219 件)。代わりに **課程(`program`)で絞れるようにする**。候補は `/masters` の `course_program`(先端理工学部の7課程)である。

**課程で絞ると、課程の対応が付いていない科目は外れる。** api-clean の `program` は `syllabus_course_program` の結合で効くため、全学向けの教養教育科目(2026年度で 288 件)のように課程が結び付いていない科目は結果に出ない。絞り込みの UI にその旨を添える。

**`/syllabus` の絞り込みは URL のクエリに持ち、`/syllabus/[code]` へは `back` に畳んで渡す。** 検索語・学部・課程・キャンパス・開講期・曜日・時限・対象年次・ページ送りはサーバ側描画の入力(`searchParams`)であり、詳細画面へ移れば当然失われる。そのため検索結果カードのリンクに現在のクエリを `back` として持たせ、「シラバス一覧に戻る」でそれを開き直す(`lib/syllabusQuery.ts`)。`router.back()` は詳細 URL を直接開かれたときに戻り先が無いため採らない。**時間割・マイデータなど別の画面を経由したときも検索条件を保つ。** この経路では `back` を運べないため、一覧を開いているあいだクエリ(`LIST_QUERY_KEYS` で濾したもの)を `useSyllabusUIStore` の `listQuery` に書き写し(`app/syllabus/_components/SyllabusQueryMemory.tsx`)、PC ヘッダーとモバイルのタブバーの「シラバス」をそこへ向ける(`listHref(listQuery)`)。写しの正本はあくまで URL であり、ストアは戻り先を覚えるだけである。他のクライアント状態と同じくメモリにだけ持ち、再読み込みとリセット(全消去)で消える。一方、**タグの絞り込み(履修区分・状態のチップと区分のセレクト)はクライアント状態(`lib/syllabusUI.ts`)に置き**、PC・モバイルとも画面遷移をまたいで保つ。これらは履修要項と学生プロファイルの突合から決まる値であって api-clean に投げる検索条件ではないため、サーバ側描画の入力にはならない(URL に持たせても意味を持たない)。**チップは履修区分と状態の5値+「すべて」に使い、区分はセレクトに出す。** 7値を1行のチップに並べると収まらないため、軸で分ける。選択肢の一覧は `lib/syllabusUI.ts` の `TAG_CHIPS` / `CATEGORY_CHOICES` に1つだけ置き、PC の `SyllabusTopBar` / `SyllabusFilters` とモバイルの `MobileSyllabusPage` が共用する。**曜日と時限はセレクトを対で置く**(`day` / `period`)。時限の選択肢は時間割表と同じ 1〜5 で、`lib/syllabusUI.ts` の `periodChoices()` が返す(api-clean は 1〜7 を受けるが、時間割に置けるのはこの5コマである。URL に範囲外の値が付いていたときだけそれを足す — 選択肢に無い値では選択が空に見え、効いている絞り込みを外せなくなる)。**時限のセレクトが無いあいだ、時間割の空きコマの「この時間に入る科目を探す」で渡した `period` は画面のどこにも出ていなかった** — 検索条件としては効いているのに、学生には絞り込まれている理由も、時限を選び直す手段も外す手段も無く、そこからシラバスを検索し直せなかった。**対象年次(`grade`)もセレクトで選べる**。選択肢は api-clean の値域と同じ 1〜4(`lib/syllabusUI.ts` の `GRADE_CHOICES`)で、`grade_min <= grade <= grade_max` の科目、つまりその年次で履修できる科目に絞る(§6.2)。**`period` / `grade` は api-clean の値域(1〜7 / 1〜4)に入る整数のときだけ検索条件にする**(`app/syllabus/page.tsx`)。値域外や数値でない値を渡すと api-clean が 422 を返して一覧が表示されなくなるため、URL に付いていても使わない。**絞り込みを変えたら `offset` を消す**(`lib/useFilterControls.ts`)。絞り込みはクライアント状態、`offset` は URL にあるため、消さないと前の絞り込みでのページ位置が残る(「修得済みの2ページ目」から「選択必修」に切り替えると、38件しかないのに31件目から表示されていた)。

**絞り込み・ページの切り出し・件数はクライアントに置き、PC とモバイルで同じものを使う**(`lib/useTaggedResults.ts`)。絞り込みはプロファイルとの突合で決まり、その結果をサーバへ送れない(§6.1.3)ため、サーバ側描画では表示する行を決められない。**担当教員名も同じ理由でブラウザから引く** — どの行が表示されるかを知っているのはブラウザだけである(§6.2)。教員名は補助情報なので、揃う前でもカードは描く。**ただし教員名の行は取得前から同じ高さで置いておき、届いたら中身だけ入れる**(PC の `CourseCard`・モバイルの一覧とも)。届いた時点で行を足すとカードが一斉に伸び、一覧が押し戻される(モバイルでは一番下まで送った画面が上へ戻された)。

ヘッダーに常にリセットボタン(要件§4.8)を設置する。PC のヘッダーには、リセットの左に取得済み・今期登録・卒業残りの単位数を出す(v0.9.57。§8.3.5)。どの画面からも見え、取り込み前(ナビを出さないあいだ)は出さない。

### 8.3 履修提案（`/proposal`）の開始と再提案

**提案は学生の指示で始める。画面に到達しただけで `POST /api/proposal` を撃たない。** 提案は1回に1分強(以前の形式では4〜5分)かかり(§7.2)、その1本は §6.1 の `preferences`(希望条件)を含めて投げるものである。到達と同時に撃つと、**学生が希望条件を書く前に「特になし」の提案が1本焼かれ、§7.2.1 の規則7・8(希望条件を尊重する / reason にどの希望に合うかを書く)が働く余地が無い。** 要件§4.3.2 の「対話を通じて学生の興味・関心をヒアリングし、提案に反映する」と要件§4.3.3 の「どの粒度で提案するかは、対話の中で学生の要望を汲み取って決める」は、いずれも提案の前に学生の言葉を受け取ることを前提としている。

**開始を学生の操作にすると、混雑で拒否されたときの復帰も学生の手に戻る。** 生成は同一トークンで1本しか通らず、進行中の後続は `503 busy` で即座に拒否される(§3.4.3、§6.3 の状態コード表、§13)。到達と同時に撃つ形では、拒否されたときに画面が死んだままになる。開始が明示の操作であれば、もう一度押すだけでよい。

#### 8.3.1 希望条件は AI履修アシスタントで受ける

**希望条件のための入力欄を別に設けず、提案チャットのパネルを提案前から使えるようにする。** この画面には既に自由記述の入力欄があり(PC は右の AIパネル、モバイルはボトムドックの Ask Bar から開く AI シート)、提案が出るまで使えない状態で置かれている。同じ画面に「提案を始めるための入力欄」と「提案について質問する入力欄」を並べると、**学生はどちらに書けばよいかを画面から判断できない。** 要件§4.3.2・§4.3.3 が求めるのは対話であり、入力欄は1つでよい。

**1つの入力欄が、提案の有無によって2つの口に向かう。**

| 送信時の状態 | 宛先 | 送るもの |
|---|---|---|
| 提案を持っていない(`status` が `idle` / `error`) | `POST /api/proposal`(§7.2) | 本文をそのまま `preferences` とする |
| 提案を持っている(`status` が `done`) | `POST /api/chat/proposal`(§7.3) | 従来どおり、提案と対話履歴を添える |

**分岐の条件を「何通目か」ではなく「提案を持っているか」に置く。** `POST /api/chat/proposal` は `proposal` を必須とし、無ければ 422 を返す(§6.1)。提案が無い状態で提案チャットは成立しないため、分岐の根拠は提案の有無そのものである。再提案(§8.3.3)で提案を捨てたあとも、次の1通は再び `/api/proposal` へ向かう。`status` が `loading` のあいだは送信させない — 生成中であり、どちらの口も次の入力を受けられない。

**モバイルの AI シートもこの入力欄である。** 時間割の画面でボトムドックの Ask Bar から開くシートは、PC の右の AIパネルと同じ会話(§5.2.2 の `proposalMessages`)を読み書きし、同じ分岐で `/api/proposal` と `/api/chat/proposal` に向かう(`lib/useProposalConversation.ts` の `useProposalAssistant()`)。v0.9.62 までは画面下部のシートを別の系統(`assistantMessages`)として提案の開始に使わず、時間割とは別の画面に対話欄を置いていたため、PC とモバイルで提案の始め方が違っていた。**提案を持っていないあいだは、Ask Bar を押すとハーフシートを飛ばして全画面のシートで開く**(ui-design_phone.pen AI_STEP0)。ハーフシートのサジェストは提案についての質問であり、提案前に送ると希望条件として提案が1本焼かれてしまう。科目・コマを選んだ状態で書いた質問は、何についての質問かを添えて送る。

**希望条件を書かずに始められる。** `preferences` は任意であり、未指定なら【希望条件】節が「特になし」になる(§6.1)。入力欄は空文字を送れないため、**案内メッセージに「希望条件なしで提案する」導線を添える。** 卒業要件だけで組んでほしい学生に、書く必要のない文章を書かせない。

#### 8.3.2 提案前の画面

- **AIパネル(モバイルは全画面の AI シート)** — 1通目に、何を書けばよいか(例:「午前中の科目を多めにしたい」「必修だけ知りたい」)と、書かずに始められることを示す案内を出す。**この案内は対話履歴(§5.2.2 の `proposalMessages`)に置く。** 提案後に出す `summary` と同じ系統の assistant メッセージであり、別扱いにする理由が無い
- **時間割表・単位数** — まだ提案が無いことを示す。生成が始まったら、`snapshot`(§6.1.1)が届くたびに逐次描く(従来どおり)
- **提案する学期** — 卒業要件の帯の右端(PC。§8.3.5)・単位バーの直下(モバイル)に、対象学期(§5.2.1)を**表示だけする**(`TargetTermLabel`)。**提案するのは取り込んだ成績表の次の学期であり、選択欄は置かない**(以前は推定の前後1学期から選び直せたが、成績表から一意に決まるため外した)。どの学期の提案かが分かるよう、見える場所には必ず出す。手入力・デモ(成績表なし)では今日の日付で決め、「今日の日付から決めています」と添える。以前ここに出していた「ブラウザの今日の日付から作った学期」は、提案の対象と無関係だったので置き換えた
- **提案を作れないとき** — (課程コード, 入学年度) を解決できない、学年が取れていない場合は、入力欄を不活性にし、理由と `/mydata` への導線を出す。**このとき提案チャットも使えない**(提案が無いため。§8.3.1 の表)。`POST /api/proposal` は履修要項を引けなければ 404 を返す(§6.1)ので投げても結論は同じだが、**往復を待たせてから同じ結論に達するより、投げる前に画面で示すほうがよい**

#### 8.3.3 再提案

**提案が出たあとも、条件を変えて提案し直せる。** 要件§4.4 の「提案内容の一部を変更したい場合の相談」は提案チャット(§7.3)が受けるが、**チャットは提案そのものを差し替えない** — `/api/chat/proposal` が返すのは本文であり、時間割は最初の1本のままである。希望条件を言い忘れた場合(「午前だけにしたい」等)、チャットだけでは時間割を立て直せない。

再提案は `status` を `idle` に戻すことで行い、その時点で次の3つを行う。

1. **提案を捨てる**(`courses` / `totalCredits` / `message`)。`snapshot` は組み立て途中の部分的な提案であり(§6.1.1)、前の提案を残したまま重ねると、時間割の各コマが前後の提案の混成になって読めない。**失敗したときは前の提案も戻らないが、条件を送り直せば済む**ため、混成を許すより捨てる
2. **提案チャットの履歴を切り、対話履歴へ退避する。** `/api/chat/proposal` は「学生プロファイル・生成済みの提案・対話全体」を1本の `messages` で受ける(§6.1)。前の提案についての問答を残したまま新しい提案を渡すと、**モデルは既に存在しない提案を根拠に答える**
3. **直前に送った希望条件を新しい案内に示す。** 2で前の会話を退避するため、学生が何を書いたかは画面から消える。差分だけ書き足せるよう、送った条件そのものは残して見せる(§5.2.3 の `preferences` はこのために持つ)

**提案の生成中に別の会話へ切り替えたときは、生成を中止して提案を捨てる(`status` を `idle` に戻す)。** 「最近のチャット」は生成中も開けるため、過去の会話を選ぶと生成中の要求は中止される。このとき `loading` のまま残すと、生成中の印が消えず入力欄も開始の導線も戻らない — 実装の初版はこの状態に陥り、リロードするまで提案画面が使えなくなっていた。中止した生成の吹き出しは「提案の作成を中断しました。」として退避する(§4.1.4)

#### 8.3.4 時間割表

**提案の科目はすべて画面に出す。** 表に出ていない科目があると、表の科目の単位の和が単位数の「今期登録」(`totalCredits`。PC はヘッダー、モバイルは単位バー)と合わず、学生は何を登録すればよいか読めない。v0.9.53 までの PC の時間割表は1マスに1科目しか持てず、表に置けない科目の置き場も無かったため、2026-09-23 の実機の提案(11科目・23単位)で2科目・3単位が画面から消えていた。

- **1マスに複数の科目を並べる。** クォーターの違う科目(3Q と 4Q)は同じコマに入り得る(重複ではない。§5.3)。1マス1科目では後から来た科目で上書きされ、「生理生態学」(3Q 月1)が「高分子化学Ⅱ」(4Q 月1)に消された。複数入ったマスは科目ごとに区分の色の枠を縦に積む(`lib/timetable.ts` の `coursesToSlotTable()`。PC は `TimetablePanel.tsx`、モバイルは `app/_components/TimetableGrid.tsx`)
- **クォーターの科目には印を付ける。** 「3Q」「4Q」の印が無いと、4Q だけの科目が後期いっぱいの科目と同じ見た目になる。学期いっぱい(前期・後期・通年、または 1Q・2Q / 3Q・4Q の両方)を占める科目には付けない
- **複数コマの科目は全部のマスに置く**(「金4・金5」。§5.3 の `slots`)
- **曜日・時限の無い科目は表の下の「曜日・時限未定」に並べる。** 集中講義や、開講のコマが未定の科目(「知能情報メディアセミナー」など)である。表に置けないからといって捨てない

- **科目を押すとその場のメニュー(`app/_components/CourseMenu.tsx`。モバイルと同じもの)を開き、そこから講義詳細(`/syllabus/[code]`、§8.1)を開く**(ほかの項目は §8.3.6)。シラバス検索から開くのと同じ画面である。マス・複数入ったマスの科目ごとの枠・「曜日・時限未定」の欄の科目が対象で、シラバスコードの無い科目には「シラバスを開く」を出さない。**メニューの「AIに相談する」でその科目を右の AI パネルの参照中の文脈にする**(選択中の科目は枠で示す) — パネルのヘッダーの下に「〇〇 を参照中」を出し(×で「表示中の時間割」に戻す)、送る質問にその科目を添え、その科目について聞けること(モバイルのハーフシートのサジェストと同じ `timetableSuggestions()`)を定型の質問として並べる。選択はモバイルと同じ `useAiStore` の `selection` に置く。**空きコマを押すとその場のメニュー(`SlotPopover`。モバイルの長押しと同じもの)を出し**、「この時間に入る科目を探す」でそのコマで絞ったシラバス一覧を、「AIに相談する」でそのコマを参照中の文脈にする。v0.9.63 までの PC は科目を押すとすぐ講義詳細へ移り、科目やコマを指して AI に聞く手段が無かった。**同じタブのクライアント遷移で開く** — 学生プロファイル・提案・対話はブラウザのメモリにしか無い(§9)ため、別タブで開くと取り込み前の状態になる。リンクには `from=proposal` を付け、詳細画面の戻り先を「時間割に戻る」(`/proposal`)にする(`lib/syllabusQuery.ts` の `proposalDetailHref()` / `backLink()`)。戻っても提案と対話はそのまま残る。生成中に開いた場合も生成は止めない

**モバイルも同じ `coursesToSlotTable()` を描く**(1マスに複数の科目・クォーターの印・「曜日・時限未定」の欄)。v0.9.62 までのモバイルは `coursesToTimetable()` の1マス1科目で、3Q と 4Q の科目の一方が消え、曜日・時限の無い科目が出なかった。**モバイルの科目は、押すとまず選択になる** — Ask Bar の文脈がその科目に絞られる(ui-design_phone.pen AI_STEP2)。同時に PC と同じその場のメニューを開き、講義詳細(リンクは PC と同じ `proposalDetailHref()`)・変更・外す・AIに相談する を選ばせる(v0.9.63 までは「選択中の科目をもう一度押すと講義詳細を開く」だった)。空きコマの長押しはその場のメニュー(AI_STEP3)で、軽く押すと選択を外す。

#### 8.3.5 卒業要件枠の内訳

**ヘッダーカードの直下の帯に、卒業要件枠ごとの充足状況を1行で出す**(PC。常に出す。モバイルは下記)。足りない枠ごとに、修得済みの単位(紺)と、今期の時間割を修得したときに埋まる単位(赤)をバーに積み、「修得済み+今期 / 必要」の単位数を添える(`app/proposal/_components/RequirementsPanel.tsx`)。不足の単位数(「あと○単位」)は行を割かずツールチップに出す。枠の名前は公式の区分名(§5.1.2)で、受け皿を持たない `required: 0` の枠は出さない。

- **充足した枠は1つのまとめに畳み、足りない枠だけを並べる。** v0.9.56 は全枠を4列の格子に並べ、単位バーと合わせて帯が2〜3段になって時間割が低くなった。学生が見るべきは足りない枠である。まとめには「取得済み」と枠の名前を出す。**充足かどうかは修得済みの単位だけで決める**(今期の時間割を足した見込みで決めると、時間割の生成中に枠がまとめとバーを行き来してバーの本数が増減し、今期で埋まるだけの枠まで「取得済み」に入る)。今期で埋まる枠はバーのまま残し、赤で満たして示す
- **足りない枠は折り返さず、入りきらない分は横にスクロールさせる。** 枠は 140px の固定幅で並べる(枠が少なくてもバーを引き伸ばさない。入りきらない枠名は省略し、ツールチップで全体を出す)。実データ(3回生・知能情報メディア課程)では足りない枠が10あり、1行に詰めると枠名が「専…」まで切れた。折り返すと帯がまた高くなる。スクロールバーは出さず、続きのある側の端をぼかして矢印ボタン(押すと1画面ぶん送る)を置く
- **凡例(修得済み・今期で埋まる分)は行を割かず、「取得済み」のまとめの ⓘ に畳む**(乗せる・フォーカスで開く)。数値の「+4」がバーの赤と同じ色なので、開かなくても読める。計算し直しているあいだは帯を薄くし、ⓘ の中に「計算し直しています」と出す
- **帯の右端に提案する学期を表示する**(§8.3.2)。取得済み・今期登録・卒業残りの単位数はヘッダーに移した(§8)

- **数字は `POST /api/requirements` の判定であり、画面で足し算しない**(§4.4.5)。同じ枠の科目を不足より多く取った分は下流の枠(オールフリーゾーンなど)に回るので、科目の区分から手元で数えると枠が食い違う
- **2回引いて差を取る**(`lib/requirements.ts` の `useRequirements()`)。1回目はプロファイルのまま(修得済み)、2回目は今期の時間割を修得したとみなして足したもの(見込み)。今期の時間割は、提案の科目と、登録済みで成績が未確定の科目(`registered`。§5.2.1)である。修得したとみなす科目は対象学期(§5.2.1)の年度・学期で送る
- **今期の時間割に追従する。** 見込みは提案の store の `courses` から作るので、提案の生成中は snapshot が届くたびに、提案が差し替われば(再提案。§8.3.3)そのたびに計算し直す。snapshot は短い間隔で何度も届くため、落ち着いてから(300ms)引き、古い要求は取り消す。計算し直しているあいだは修得済みだけを出し、帯を薄くして示す。提案を捨てれば見込みは消える
- **提案チャット(§7.3)は時間割を差し替えない**(§8.3.3)ため、会話で科目を足す依頼をしても数字は変わらない。時間割を変える経路を足すときは、store の `courses` を書き換えれば、ここは変えずに追従する
- **単位数の「卒業残り」も同じ判定を使う**(§4.4.5)。ヘッダーと帯が同じ値を見るよう、集計と判定の呼び出しは `lib/creditSummary.tsx` の `CreditSummaryProvider` に1つだけ置く(ルートのレイアウト。各所で `useRequirements()` を呼ぶと `POST /api/requirements` が呼んだ数だけ飛ぶ)。見込みの計算が追いついたあと(`updating` でない)に、今期の時間割を修得したあとの残りを出す
- **モバイルは単位バー・提案する学期の下に同じ判定を2段で出す**(`RequirementsPanel.tsx` の `MobileRequirementsStrip`。ui-design_phone.pen RequirementsStrip)。上に充足した枠のまとめ(「取得済み：」と枠の名前)、下に足りない枠のカード(140px 固定幅・横スクロール)を並べる。指で送れるので矢印ボタンは置かない。単位バーの数字も `useCreditSummary()` から採り、PC のヘッダーと同じ値を出す

#### 8.3.6 学生による時間割の編集

**時間割は学生が自分で直せる。** AI の提案を待たずに組む・提案の一部だけを差し替える・要らない科目を外す、のいずれも AI との対話を経ずにできる。編集は提案の store(`lib/proposal.ts`)の `courses` を書き換えるだけで、今期登録単位・卒業要件の見込み(§8.3.5)はそれに追従する。

| 操作 | 入口 | store |
|---|---|---|
| 登録 | 講義詳細の「時間割に追加」。空きコマのメニュー(PC は押す、モバイルは長押し)の「この時間に入る科目を探す」からそのコマで絞ったシラバス一覧を開ける(`slotSearchHref()`) | `addCourse()` |
| 外す | 時間割の科目のメニューの「時間割から外す」(もう一度押して確定)、または講義詳細の「外す」 | `removeCourse()` |
| 変更 | 時間割の科目のメニューの「別の科目に変更する」→ そのコマで絞ったシラバス一覧 → 講義詳細の「(元の科目)をこの科目に変更」 | `startReplace()` → `replaceCourse()` |

- **登録した時間割は提案と同じ扱いにする。** 提案前(`idle`)や失敗後(`error`)に登録すると `done` になり、提案チャットの宛先(§8.3.1)もその時間割についての質問になる。学生が登録した科目の `reason` は「学生が自分で時間割に登録した科目」で、提案チャットにもそのまま渡る。`totalCredits` は編集のたびに科目の単位から数え直す
- **生成中は編集させない。** 届く snapshot に上書きされて編集が消えるためである(メニューを開かせず、「時間割に追加」も押させない)
- **AI の提案と違い単位数上限などの検査を通らないため、入れる前に手元で確かめる。** 開講学期が時間割の学期(`useTargetTerm()`)と合わないとき、同じ曜日・時限・クォーターに別の科目があるとき(`lib/timetable.ts` の `termFits()` / `findConflicts()`)は、それでも入れるかを聞く。3Q と 4Q のように期間の分かれた同じコマは重なりとしない
- **変更の途中はシラバスの画面に帯(`components/ReplaceBanner.tsx`)を出し続ける。** 何を入れ替えようとしているかを見失わないためである。時間割へ戻ると入れ替えは終わる(選ばずに戻った場合も)
- 科目の同一性はシラバスコード、無ければ科目名(`courseKey()`。時間割表の `entryKey()` と同じ規則)
