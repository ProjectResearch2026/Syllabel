#### 4.1.2 状態管理

- Zustand store 6本: 学生プロファイル(`lib/student.ts`)、対話履歴(`lib/chat.ts`)、「最近のチャット」に退避した過去の会話(`lib/chatHistory.ts`)、時間割・条件・レポートの状態(`lib/proposal.ts`。スキーマは §5.2.3)、検索画面の絞り込み状態(`lib/syllabusUI.ts`。§8.2.2)、AI シートの表示状態(`lib/ai.ts`。§4.1.5)。時間割の状態(§6.1.1)・検索画面の絞り込み・AI シートの状態はいずれも画面をまたいで共有されるため store に置く
- すべて **永続化機能を意図的にオフ** にする(要件§5.2)。`persist` ミドルウェアを使わないことで担保し、ページリロード・タブクローズで完全消失する
- リセット機能(要件§4.8)は store を初期状態に戻すだけで実現する。学生プロファイル(`clearProfile()`)・対話履歴(`lib/chat.ts` の `clearAll()`)・「最近のチャット」(`lib/chatHistory.ts` の `clearAll()`)・時間割(`lib/proposal.ts` の `clear()`)・検索画面の絞り込み(`lib/syllabusUI.ts` の `reset()`)の5つを消す。AI シートの表示状態は学生データを持たないので残す。消したあとトップ(取り込み画面)へ戻す**遷移は `next/navigation` の `router` で行う** — `window.location` による素の遷移には `basePath`(§3.5.2)が付かず、アプリのトップではなく配信サーバのルートへ飛ぶ。リセットはヘッダー・PC のマイデータ・モバイルの設定の3か所にあり、いずれも同じ形にする
- サーバから取得するデータ(シラバス検索結果、履修要項データ等)は各画面の `fetch` で取る。キャッシュライブラリは導入していない(§2)

#### 4.1.3 PDF解析(クライアント側)

- `pdfjs-dist` でテキストレイヤーを抽出
- **pdfjs-dist は legacy ビルド(`pdfjs-dist/legacy/build/pdf.mjs` と同ビルドの worker)を使い、テキストは `page.streamTextContent()` を `getReader()` で読む(`getTextContent()` は使わない)。** 学生の端末のブラウザは最新とは限らない。pdf.js 6 の通常ビルドの worker は `Map.prototype.getOrInsertComputed` を前提にしており、これを持たないブラウザでは PDF の構造を読めない。legacy ビルドはこれを core-js で補う。一方 `getTextContent()` は legacy ビルドでも ReadableStream の非同期反復(`for await`)で読むため、これを持たない Safari(iPhone を含む)では動かない。どちらも成績表の中身とは無関係に、取り込みの最初で失敗する
- 龍谷大学成績表レイアウト前提のルールベースパーサーを実装
- 評価記号(`T`/`N`/`G`/`D`/`J`/`M`)と数値スコアを認識し、合否を判定(要件§4.2)
- **評価(点数・評価記号)はパーサーの中だけで使う。** 使い道は合否の判定と、再履修した科目の修得学期の判定(評価と同じ値のセルの学期)の2つで、取り込んだプロファイル(`Course`)には持たせない(§5.2.1)
- 履修グリッドの `***`(登録科目)/ `*`(継続履修中)は**登録済み・成績未確定**(`registered`)として取り込む。成績のセルより後の学期にある印だけを採る(§5.2.1)
- 成績表の作成日(右上の月日+ヘッダの年度)と「在籍年数 / 休学年数 / 在学年数」を読む。作成日は次に登録する学期(成績表の次の学期)を決めるのに使う。在籍年数は読むが学期の決定には使わない(§5.2.1)
- **基本情報欄は見出し「入学日」からの相対位置で読む。** 帳票は作成年度によって全体が縦にずれるが、見出しから値までの距離は一定である
- 学籍番号は意図的に抽出しない(要件§4.2)
- 解析失敗時は「読み取れませんでした」と伝え、もう一度選ぶか、デモの学生で試すよう案内する。**手入力のフォームは置かない**(要件§4.1)

#### 4.1.4 ストリーミング表示

- backend からの SSE を `fetch` + `ReadableStream` で受信
- 受信した chunk を逐次 React state に反映、画面に追記表示
- **本文が1文字も届いていないあいだ、吹き出しを空のままにしない。** 何も届いていないあいだは生成中であることを示す指標(3点のアニメーションと短い文言)を出し、思考・ツールの進み具合が届けばそれを出し(§8.3.7、`components/ai/AgentTrace.tsx`)、本文が届いた時点で本文に差し替える。会話はツール呼び出しを挟んでモデル呼び出しが2回以上になり、思考を有効にしている(§6.3.1)ため1回に100秒を超えることがある。そのあいだ吹き出しが無地のままだと、**待っているのか壊れているのかを学生が判断できない**
- **指標は `components/ai/ThinkingIndicator.tsx` に1つだけ置く。** 会話を描く面ごとに写さない(§4.1.5 の `MarkdownText` と同じ扱い)
- **文言は呼び出し側が渡す。** 時間割の画面は送った直後に「読んでいます…」、「希望条件なしで提案する」の組み立てを待つあいだは「時間割を組んでいます…」とする(§8.3.7)。シラバスチャットは既定の文言(「考えています…」)のままとする
- **点は動きを読めない環境では伝わらないため、文言を必ず添える。** 点そのものは `aria-hidden` とし、読み上げは文言に任せる
- **生成が終わっても本文が空のまま、という吹き出しも残さない。** 起きるのは2通りで、(1) 生成・受信の途中で会話を切り替えて退避した場合(退避は `streaming` を下ろして保存するため、戻すと指標も本文も無い吹き出しになる)と、(2) 本文も `error` も来ずに `done` だけが届いた場合である。前者は退避の時点で「応答の途中で会話を切り替えました。」などの中断の旨に置き換え、後者は「応答を受け取れませんでした。」とする

#### 4.1.5 AI回答のMarkdown表示

- AI の回答は **Markdown として描く**(`components/ai/MarkdownText.tsx`)。モデルは太字・箇条書き・表を混ぜて返すため、素のテキストとして描くと `**必修**` の `**` や `|---|---|` の罫線がそのまま学生に見える。科目の比較や条件の列挙では表と箇条書きのほうが読みやすく、モデル側で禁じるのではなくフロントで描く
- 使うのは `react-markdown` と remark プラグイン2つ。`remark-gfm` が表・取り消し線・チェックリストを、`remark-breaks` が**段落内の単独改行**を担う。Markdown の既定では単独改行が消えるが、日本語の回答は1文ずつ改行して返ってくることが多く、消すと読みにくい
- **生の HTML は描かない。** `rehype-raw` を入れなければ `react-markdown` はタグを文字として出す。モデルの出力を DOM に流す口を開けないため、入れない
- 描くのは **AI側の吹き出しだけ**。学生が入力した文は Markdown として解釈せず、そのまま文字として出す
- 表は**吹き出しの中で横スクロールさせる**。吹き出しの幅は会話の欄に対する割合(AI 側 90%・学生側 75%)で決め、表のために広げない。PC のパネル(344px)では設計(`ui-ux/ui-design_*.pen`)の 280px・230px とほぼ同じになり、モバイルのシートでは画面の幅に合わせて広がる
- **会話の吹き出しは `components/ai/ChatMessageList.tsx` の1か所で描く。** PC の AIパネル(`components/pc/AiChatPanel.tsx`。時間割・シラバス一覧・講義詳細の3画面が共用)とモバイルの AI シート(`components/ai/MobileAiAssistant.tsx`)が同じものを使い、ヘッダー・定型の質問・入力欄も `components/ai/ChatParts.tsx` を共有する。会話を描く面ごとに吹き出しを作らない
- **末尾の AI の吹き出しの右に、再生成のボタン(回る矢印。Claude のチャットと同じ)を置く**(`ChatMessageList.tsx`)。押すと直前の学生の発話を、その手前までの会話に送り直して答えを作り直す(`AiConversation.regenerate`、`lib/chat.ts` の `regenerateFrom()`)。作り直す前の答え(失敗の文言を含む)は次のリクエストの履歴に載せない。応答に失敗したときに、同じ質問を書き直さずに送り直すための口である。学生の発話への答えでない吹き出し(案内・「希望条件なしで提案する」の説明)と受信中には出さない。**時間割か条件を変えた答えにも出さない**(答えの途中で `build` / `step` / `timetable` / `conditions` のどれかが届いたら、吹き出しの `changedTimetable` を立てる。途中で失敗した答えも含む)。作り直しても時間割は変わった後のままで、同じ発話(「水環境科学を外して」など)に正しく答えられないため。作り直す前の時間割に戻してから送り直せば答えられるが、手で直した時間割の扱いなど処理が込み入るので、今は置かない
- **受信中は入力欄の送信ボタンを停止ボタン(四角。Claude のチャットと同じ)に替える**(`ChatParts.tsx` の `ChatInputBar`、`AiConversation.stop`)。押すと受信を中断する(時間割の会話では「希望条件なしで提案する」の組み立ても止まる)。届いていた本文と思考の行はそのまま残し、本文の後ろに「応答を止めました」と添える(本文が1文字も届いていなければ本文をその文言にする。`lib/chat.ts` の `stoppedPatch()`)。止めた答えは応答に失敗した答えと同じく再生成でき、時間割か条件を変えた答えは再生成しない。会話の切り替え(新規・最近のチャット)による中断とは分けて扱い、そちらには添えない
- **入力欄は書いた行に合わせて高さが伸び、上限(PC 8行・モバイル 5行)を超えたら欄の中でスクロールする**(`ChatParts.tsx` の `ChatInputBar`)。1行の入力欄だった頃は、長く書くと先頭が欄の外に流れて読み返せず、改行もできなかった。**PC は Enter で送り、Shift+Enter で改行する**(Claude のチャットと同じ。操作の案内は出さない)。**タッチの端末(`pointer: coarse`)は Enter で改行し、送るのは送信ボタンだけにする** — ソフトキーボードには Shift が無く、Enter で送ると改行する手段が無くなる。変換の確定に押した Enter では送らない(Safari は確定の keydown で `isComposing` が false になるため、`keyCode` 229 でも見分ける)。学生の吹き出しは改行をそのまま出し、長い URL などの切れ目の無い文字列も吹き出しの中で折り返す
- **モバイルの AI シートは、上部(グラバーとヘッダー)を押したまま上下に引っ張って高さを変えられる**(`components/ai/MobileAiAssistant.tsx`)。引っ張っているあいだはシートの高さが指に付いてきて、**離した高さで止まる**(ハーフと全画面の2段に限らない)。止めた高さは `lib/ai.ts` の `height` に覚え、閉じて開き直しても全画面から戻ってもその高さで開く(ページを読み直すと既定に戻る)。画面の上端近くまで引き上げて離せば全画面、下端近くまで下げて離せば閉じる。入力欄と会話が入らないほど低くは止めない。ヘッダーのボタンの上から引っ張って離しても、そのボタンを押したことにはしない。グラバーだけを掴めた頃は掴める所が細く、引っ張ってもシートが動かなかったため、調節できることに気づけなかった
- **会話の中身(送信・ストリーミング・履歴)も PC とモバイルで共有する。** 画面ごとの会話を `AiConversation`(`lib/ai.ts`)の形で作り — 時間割は `useProposalAssistant()`(`lib/useProposalConversation.ts`)、シラバス一覧は `lib/useSyllabusConversation.ts`、講義詳細は `lib/useCourseConversation.ts` — PC のパネルとモバイルのシートの双方に渡す。両者は同じ画面に同時に mount される(表示は CSS で切り替わる)ため、送信中かどうかは各自の state ではなく吹き出しの `streaming` から導き、**どちらから送っても両方が同じ状態を映す**

#### 4.2.2 役割

- フロントからのリクエストを受け、履修要項データと要件充足判定から学生の文脈を作る(§7.2.1)
- **時間割の組み立てはモデルを呼ばずに backend が行う**(§7.2)。会話は PydanticAI で定義したエージェントに委ね、エージェントは vllm を OpenAI 互換クライアント経由で呼び、組み立て・シラバスの検索を tool calling で呼ぶ(§7.3、§7.4)
- 応答は SSE でフロントへストリーミング

#### 4.2.3 学生データの取り扱い

- backend は学生プロファイル(学年・課程・既修得科目)をリクエスト本文で受け取り、推論用プロンプトの組み立てに使うが、**永続化しない**
- リクエスト処理完了後にメモリから破棄される
- backend 自身のログにも記録しない(要件§5.5)
- **ただし、組み立てたプロンプトと応答は経路上のトークンゲートウェイに100日間記録される**(§3.4.3、§9.1)。受け取った学生プロファイルのうちプロンプトへ載せるものは最小限とする(§7.3.1、§7.4.1。修得済み科目の一覧は載せない)
- **api-clean へは学生プロファイルを渡さない。** 送るのは科目の検索条件(科目名・開講年度・シラバスコード等)に限られる(§6.2)

#### 4.2.4 配置と実行基盤

- **公開 VM 上で rootless Podman のコンテナとして動かす**(§3.1、§3.2.1)。`backend/Dockerfile` をそのままビルドする
- **`USER` による非 root 化を行わない。** 公開 VM のホームの default ACL とコンテナの uid マッピングが噛み合わず、非 root ユーザではイメージ内の実行ファイルを読めずに起動に失敗する(理由は §3.2.1)
- **イメージは公開 VM 上で x86_64 としてビルドする。** DGX Spark 上で arm64 として作ったイメージは流用できない(§3.2)
- **上流2つはいずれもホストを跨ぎ、いずれもトークンゲートウェイを経由する。** vllm は §3.4.3・§6.3、api-clean は §3.4.4 による。**base_url とトークンを環境変数で与える形が2組になるだけで、扱いは同じ**である(`backend/app/settings.py`)。コード側は接続先の所在を知らない

### 4.3 vllm(LLM 推論サーバ)

vLLM を Docker で DGX Spark 上に起動し、OpenAI 互換 API(`/v1/chat/completions`)を公開する。構成は `docker-compose.yml` の `vllm` サービスが正本である。

**イメージとモデル**

- **イメージはタグを固定する**(`vllm/vllm-openai:v0.27.1`)。`latest` は pull のたびに実体が黙って変わり、起動オプションの互換性や性能の見積もりと対応しなくなる
- **モデルは事前に取得し、読み取り専用で bind mount する。** `hf download Qwen/Qwen3.8-27B-FP8 --revision <commit SHA> --local-dir ...` でリビジョンを固定して `/srv/qwen3.8/models/Qwen3.8-27B-FP8` に置き、`/models:ro` として渡す(`--model /models`)。起動のたびに HF から取得しないことで再現性を保つ。現在のリビジョンは `017b9c7af6b5689d5dd426a76e0bc077eb5ca20a`
- **旧モデル(Qwen3.6-27B-FP8)は消さずに残す。** bind mount 元とモデル名を戻すだけで切り戻せる
- Qwen3.8-27B-FP8 は Qwen3.6-27B-FP8 と `config.json` が同一(`transformers_version` を除く)で、違いは重みだけである。起動オプションはモデルの差し替えで変えない

**起動オプション**

| オプション | 値 | 理由 |
|---|---|---|
| `--model` | `/models` | 上記のローカルパス。**将来の vLLM で削除される予定**であり、位置引数への移行を §13 に置く |
| `--served-model-name` | `qwen3.8-27b-fp8` | backend の `OpenAIChatModel` に渡すモデル名(§6.3)と一致させる。**モデル名は backend・トークンゲートウェイ・vllm の3箇所で一致していなければならず、差し替えるときは3つを揃える**(§3.4.3.1) |
| `--language-model-only` | — | モデルはビジョンエンコーダ付きだが本サービスはテキストだけを扱う。ビジョンを無効にしてメモリを KV cache に回す |
| `--reasoning-parser` | `qwen3` | 思考モデルのため必須。無いと思考トークンが本文に混ざり、PydanticAI のツール呼び出しの解釈が壊れる。**思考を出させるかどうかはサーバ側で固定せず**、リクエストごとに `chat_template_kwargs.enable_thinking` で決める(§6.3.1) |
| `--enable-auto-tool-choice` / `--tool-call-parser` | `qwen3_coder` | 公式モデルカードの指定。`hermes` はこのモデルの出力書式と合わず、ツール呼び出しがエラーにならずに**黙って無視される**。`qwen3_xml` への変更は、ツール呼び出しが `tool_calls` として返ることを確かめてから判断する(§13) |
| `--max-model-len` | `131072` | 既定の 262,144 ではメモリが足りない。公式は思考能力の維持のため 128K 以上を推奨する |
| `--gpu-memory-utilization` | `0.4` | 121GiB のユニファイドメモリを本プロジェクト外の推論サーバと分け合う(§3.2.3)。この値で KV cache は約68,000トークン(`--max-model-len` に対して同時実行約2倍)を見込む |
| tensor parallel | 使わない(1) | DGX Spark は単GPUである |

- **DeepGemm の自動無効化を上書きしない。** Blackwell(GB10)では vLLM が精度劣化を理由に DeepGemm を無効にして CUTLASS へ退避する(起動ログに `Auto-disabled DeepGemm ...` が出る)。`VLLM_USE_DEEP_GEMM` で戻さない
- **`--language-model-only` が効いていることは起動ログで確かめる**(`... running in text-only mode.`)

**運用上の注意**

- **初回起動は6〜7分かかる**(重みのロード、`torch.compile`、ウォームアップ、CUDA graph のキャプチャ)。`docker-compose.yml` の healthcheck の `start_period: 900s` はこれを見込んだ値である。2回目以降は `/root/.cache/vllm/torch_compile_cache` が効いて短くなる
- **`vllm` の CLI は GPU が見えないと、引数を解釈する前に `RuntimeError: Failed to infer device type` で落ちる**(`--help` も出ない)。`docker run` でオプションを確かめるときは `--gpus all` を付ける。全オプションは `--help=all`、個別のフラグは `--help=<フラグ名>` で引く
- **ホストの loopback にだけバインドする。** backend は別ホスト(公開 VM)にあり、教員側のトークンゲートウェイ経由で、発行されたトークンを用いて到達する(§3.4.3、§6.3)。frontend からは直接呼ばない

### 4.4 履修要項データ層

#### 4.4.1 データの方針

- **対象は先端理工学部6課程 × 2023・2024・2025・2026年度入学の4コホートとする。** 2026年度時点の1〜4年次にあたる。2024年度入学以降は履修要項サイト、2023年度入学は冊子の PDF(サイトに2023年度版が無いため)を出典とする。専門関連科目(他課程が開講する専攻科目)の判定に他課程の `courses` が要る(下記)ため、全課程を揃えて扱う(要件§2.1)
- 学修プログラムは構造が複雑なため現時点では扱わない。扱いを確定した上でスキーマ・データに追加する
- 他学部に対象を広げる際は、対象範囲のファイルを追加する

**出典は入学年度ごとに別ページに分かれており、教養教育科目は2025年度入学分から学部ページの外にある。** 対応は次のとおり(2024年度入学以降は `https://rishu.ryukoku.ac.jp` 配下)。

| 入学年度 | 専攻科目 | 教養教育科目 |
|---|---|---|
| 2023 | 冊子 PDF `https://cweb.ryukoku.ac.jp/~kyoga/rishu/pdf/01/2023/Y2023youkou20230324_<課程>.pdf` と冊子配付後の変更点(`.../pdf/02/2024/Y2023henko20250306.pdf`) | 冊子 PDF `.../pdf/01/2023/Y2023youkou20230324_3Elect.pdf` |
| 2024 | `/curriculum/2024/faculty-rikou/s05` | `/curriculum/2024/faculty-rikou/s04` 【3】(学部ページ内) |
| 2025 | `/curriculum/2025/faculty-rikou/s04` | `/organization/no5`(教育課程＜共通＞。先端理工学部【〜2025年度入学】) |
| 2026 | `/curriculum/faculty-rikou/s04`(年度を含まない URL が最新年度) | `/organization/no3`(同上。先端理工学部【2026年度入学〜】・農学部) |

**入学年度で決まって変わらないデータと、開講年度ごとに変わるデータを分離する。** 履修要項(卒業要件・科目区分・設置科目)は、ある年度の入学生に対して入学時点で決まり、その学生が卒業するまで変わらない。したがって一度確定したら以後編集しない。一方シラバスコードは開講年度ごとに発行される値であり、毎年更新が要る。両者を同一ファイルに置くと、開講年度が進むたびに過去の入学年度のファイルまで書き換えることになり、確定済みの卒業要件を壊しかねない。したがって**履修要項ファイル(`curricula/`)にはシラバスコードを持たせず、開講年度ファイル(`offerings/`)に分離する**(§4.4.2)。両者は**科目名**で結合する。

**教養教育科目は課程間では共通だが、入学年度で版が分かれる。** 履修要項の「教養教育科目の教育目的及び履修方法」は学部単位で規定されており、6課程で内容が一致する。したがって課程ファイル6本に同一内容(約150科目)を複製することはせず、入学年度ディレクトリごとに教養教育科目ファイル(`00-liberal-arts.yaml`)を1本置く。教養教育科目の**卒業要件枠(`liberal.*` スロット)も課程ではなく学部で決まる**ため、設置科目一覧と併せてこのファイルが唯一の定義元となる(§5.1.3)。課程ファイルは `liberal.*` スロットを持たない。課程固有の例外(2024・2025年度入学版の「生活の中の化学」は応用化学課程では履修不可)も、出典が教養教育科目側の設置科目表の備考欄であるため、課程ファイルではなくこのファイルに `not_available_to_programs` として持たせる。

**ただし入学年度をまたいだ共通化はしない。** 2026年度入学生から教養教育カリキュラムが全面改訂されており(改訂内容は§5.1.3)、単一の共通ファイルでは表現できない。2023・2024・2025年度入学は内容が一致する(設置科目一覧を科目名レベルで突合し、差分が表ヘッダと備考の文言のみであることを確認済み)が、この場合も**共通ファイルへの参照ではなく、同一内容のファイルを両方のディレクトリに置く**。参照方式では入学年度をまたぐパス参照と版の適用範囲判定が必要になり、「このコホートはどの版を見るか」の分岐がロード処理と検証の双方に入り込む。複製であれば `admission-<年度>/` 1ディレクトリがそのコホートの完結した定義になり、マージがディレクトリ内で閉じる。複製であることは `duplicate_of` で宣言し、修正するときは複製元・複製先の双方に同じ変更を入れる(§5.1.3、§4.4.4)。

**専門関連科目は YAML に書かず、同一入学年度の他課程ファイルから導出する。** 専門関連科目とは所属課程以外の課程が主体となって開講する専攻科目であり、その実体は他課程ファイルの `courses` そのものである。各課程ファイルに列挙すると同じ科目を課程数ぶん複製することになるため、`category: "専門関連科目"` を持つレコードは書かず、ロード時に「同一入学年度の他課程ファイルに載る専攻科目」として解決する(§4.4.3)。ただし学修プログラム科目は対象外(前述)であり、この導出にも含まれない。

**履修要項の版表記(【20XX年度以降入学生】)を、ファイルの同一性の根拠にしてはならない。** 各課程の見出しにはこの表記があるが、更新の基準が一貫していない。2024年度版と2025年度版を突合した結果は次のとおりで、版表記が据え置きでも設置科目一覧は変わっている。

| 課程 | 2024年度版 | 2025年度版 | 2024→2025 の実際の変更 |
|---|---|---|---|
| 01 数理・情報科学 | 【2020年度以降】 | 【2020年度以降】 | 設置科目 +5 のみ(下記の全課程共通分) |
| 02 知能情報メディア | 【2020年度以降】 | 【2025年度以降】 | +5 に加え、「ネットワーク構成論」が2年次配当→3年次配当、「コラボレーション演習」廃止。規定本文は変更なし |
| 03 電子情報通信 | 【2023年度以降】 | 【2023年度以降】 | 設置科目 +5 のみ |
| 04 機械工学・ロボティクス | 【2020年度以降】 | 【2025年度以降】 | +5 に加え、Ⅰ/Ⅱに分割されていた科目の統合を含む大規模再編。規定本文は変更なし |
| 05 応用化学 | 【2020年度以降】 | 【2025年度以降】 | +5 に加え、先修制の変更(「特別研究」の履修要件に指定7科目の単位修得が追加) |
| 06 環境生態工学→環境科学 | 表記なし | 表記なし | 課程名の改称と設置科目 +5 |

全課程共通の +5 は、2025年度入学から新設された「キャリア実習・実習指導」「先端理工キャリア実習Ⅰ・Ⅱ」「先端理工インターンシップⅠ・Ⅱ」である。2026年度入学ではさらに「協定型インターンシップ」「理工インターンシップ(学外実習)Ⅰ・Ⅱ」「クラウドコンピューティング演習」が全課程から削除されている。すなわち**専攻科目は6課程 × 4入学年度の24ファイルすべてが別内容**であり、複製になるのは教養教育科目ファイル(2023・2025年度入学が2024年度入学の複製)だけである。

- 入学年度をディレクトリ、課程をファイルとする。入学年度が第一階層になることで、新しい入学年度を追加するときに既存ディレクトリへ手を入れずに済む
- **ファイル名は `<課程コード2桁>-<課程名のローマ字表記>.yaml`。**
  - **課程コード**は大学が公表している番号で、科目ナンバリングの第2要素(`Y-01-MMA-1-01-P` の `01`)およびシラバスコード先頭4桁(`Y001` の `001`)と一致する。課程が改称されても変わらない(環境生態工学課程 → 環境科学課程の改称後も `Y006` のまま)ため、これを一次識別子とする
  - **ローマ字表記は課程名を省略せずすべて音写する。** 語の区切りはハイフン。末尾の「課程」と中黒(・)は書かない。語を省略すると省略の基準が定まらず、課程名からファイル名を導出できなくなる。省略しない規則にすることで一意に定まる
  - 対応表: 01 数理・情報科学 `suri-joho-kagaku` / 02 知能情報メディア `chinou-joho-media` / 03 電子情報通信 `denshi-joho-tsushin` / 04 機械工学・ロボティクス `kikai-kogaku-robotics` / 05 応用化学 `oyo-kagaku` / 06 環境生態工学 `kankyo-seitai-kogaku`(2023・2024年度入学。2025年度以降の入学年度は環境科学 `kankyo-kagaku`)
- 課程名は改称され得る。ファイル名のローマ字部分は**その入学年度時点の名称**に固定し、以後変更しない。改称の追跡は課程コードと `program.name_aliases` が担う
- **教養教育科目ファイルは各入学年度ディレクトリに `00-liberal-arts.yaml` として置く。** 課程ファイルからのパス参照は持たず、**同一ディレクトリにあることをもって対応づける**(§4.4.3)。`00` は課程コードとして使われていない値であり、一覧したとき課程ファイルより先に並ぶ
- **内容が他コホートと同一のファイルは、参照ではなく複製を置き、`duplicate_of` に複製元のパスを書く**(§5.1.3)
- `offerings/<開講年度>/` は `curricula/` と**同じ相対パス構造**(`admission-<入学年度>/<同名ファイル>`)を持たせる。入学年度が違っても同じ開講年度コードを指すことは正常であり、重複を排除しない

#### 4.4.3 ロード方式

- backend 起動時に `curricula/**/*.yaml` と `offerings/<運用対象年度>/**/*.yaml` を読み込み、Pydantic スキーマ(§5.1)で型付けしてメモリ上に保持する
- 課程ファイルは以下の順にマージし、課程ごとに1つの完全なオブジェクトを組み立てる。**参照はすべて同一の `admission-<年度>/` ディレクトリ内で閉じ、他の入学年度のファイルを読まない**:
  1. 同一ディレクトリの `00-liberal-arts.yaml` の `requirement_slots` / `credit_caps` / `courses` / `prerequisites` を取り込む(教養教育科目の要件枠と設置科目はこのファイルが唯一の定義元。§4.4.1)。このとき `not_available_to_programs` に当該課程の `program.code` を含む科目は取り込まない(§5.1.5)。`prerequisites` は課程ファイルと教養教育科目ファイルの双方が同じ形で持つ先修制の規定であり(§5.1.5)、いずれも規則レイヤとして履修提案の先修条件の判定(§7.2.1 手順4b)に用いるため、課程ファイル由来のものと合わせて1つのリストに保持する。要件充足判定(§4.4.5)は先修制を見ない(卒業要件の単位数だけを数える)
  2. 同一ディレクトリの他課程ファイルの `courses` を `category: "専門関連科目"` として取り込む(§4.4.1)。取り込んだ科目は `related` / `free.faculty` スロットの判定にのみ用い、当該課程の設置科目としては扱わない
     - **当該課程の `courses[].title` と同名の科目は導出しない。** §4.4.1 の「所属課程以外の課程が主体となって開講する専攻科目」という定義上、当該課程が開講している科目は専門関連科目ではない。除外しないと課程あたり17〜22科目が二重に載り、うち1〜2件は同名で単位数が食い違う(2024年度入学コホートでは、課程01の「セミナーⅠ」が自課程の4単位と課程06由来の2単位の2件になる)
     - **他課程どうしで同名の科目は全レコードを保持し、出典の課程コードで区別する。** 属性が食い違う場合にマージ時点で単位数を決め打ちする根拠がないため(課程01の「特別研究」は他5課程から導出され、応用化学課程のみ10単位・他は6単位)。どの出典を採るかの判断は充足判定(§4.4.5)の側に委ねる。この重複が後述の `courses[].title` 重複検査の対象外である理由でもある
- 起動時にスキーマバリデーションを実行し、不正があれば起動失敗(データの誤りを早期に検出)。型検査に加えて以下の整合性を検証する:
  - `type` が {必修, 選択必修, 選択, 随意} のいずれかであること。`category` / `subcategory` が §5.1.5 の列挙値のいずれかであること
  - `term` と `quarters` の整合(§5.1.5)。`quarters` は任意であり、教養教育科目は `前期` / `後期` でも持たない(クォーター制の対象外。§5.1.3)。持つ場合のみ `前期` ⇔ `{1Q, 2Q}` / `後期` ⇔ `{3Q, 4Q}` を検査し、`通年` / `サ集` は持たないことを検査する
  - `constraints[].slot` および `constraints[].track_group` の参照先が存在すること(前者は `requirement_slots`、後者は `courses[].track_groups`)
  - `by_semester` の各要素が `max_credits_per_semester` と `max_credits_per_year` のどちらか一方のみを持つこと
  - 課程ファイル・教養教育科目ファイルの `admission_year` が、そのファイルが置かれているディレクトリ名の年度と一致すること
  - 各 `admission-<年度>/` ディレクトリに `00-liberal-arts.yaml` がちょうど1つ存在すること
- 次の5件は**マージ後**のオブジェクトに対して検証する。教養教育科目ファイル単体では `liberal.elective` の `overflow_to` 先である `free.all` が解決できず、スロット単位の検算も成立しないため、ファイル単体では検査しない:
  - `requirement_slots[].key` が一意であること
  - `requirement_slots[].credits` の合計が `graduation.total_credits` に一致すること
  - `overflow_to` の参照先が `requirement_slots` に存在し、循環していないこと
  - `courses[].title` に重複がないこと。この検査の対象は当該課程の設置科目(教養教育科目ファイル由来の教養教育科目 + 課程ファイルの専攻科目)であり、上記2.で導出した専門関連科目は含めない(他課程に同名科目が存在し得るため)
  - `prerequisites` に書いた科目名(`title`、`all_of` / `any_of`、`min_credits[].from`、`one_of` の中のもの)が、同じ `admission-<年度>/` の履修要項ファイルのいずれかの `courses[].title` に存在すること(§5.1.5)。先修制の判定は科目名で修得科目と突き合わせるため、科目名の誤りは黙って「未修得」になる。比較は突合と同じ規則(NFKC 正規化と空白除去)で行う。当該課程が履修できない教養教育科目(`not_available_to_programs`)の先修制も1つのリストに取り込まれるため、上記1.で除外する前の科目名と照らす。正規化の規則は `app/curricula/titles.py`(科目名の突合規則を1か所に置くモジュール)にあり、要件充足判定(§4.4.5)とこの検査が共用する
- **`offerings` の `unresolved` が非空でも起動は継続し、警告ログを出す。** 当該科目はシラバスコード未解決として扱い、コードを要する処理(検索画面のタグ付け §6.1、開講情報の取得 §7.2)の対象外とする。`offerings` は api-clean のシラバスと突き合わせて作る値であり、上流の科目名変更ひとつで稼働中のサービスが起動不能になる事態は避ける
- 任意フィールドは null / 省略を許容する。Pydantic では `Optional` として定義する
- 個々のリクエストでは、該当課程・該当入学年度のオブジェクトのみを参照する
- **クライアントへ返すのは科目レイヤに限り、規則レイヤは返さない。** 保持したオブジェクトは用途の異なる次の2層からなる:
  - **科目レイヤ** — `courses` の科目属性(`title` / `category` / `subcategory` / `type` / `credits` / `grade` / `term` / `quarters`)と、`offerings` の `resolved` が与えるシラバスコード。検索画面のタグ付け(§6.1)はこの層だけで完結する(コードから科目を引き、`type` と既修得科目を突き合わせるだけで、履修要項の規則の解釈を伴わない)ため、`GET /api/curricula`(§6.1)でクライアントへ返す
  - **規則レイヤ** — `requirement_slots`(`accepts` / `overflow_to`)・`credit_caps`・`tracks[].constraints`・`prerequisites`・`grade_up_requirements`・`registration_limits`。卒業要件の充足判定に用いる規則であり、クライアントへは返さない(§4.4.5)
  - **この分割の基準はデータ量ではない。** 科目レイヤはタグ付けの都合上マージ後の全課程分(数百科目)を返す必要があり、量としては規則レイヤより大きい。学生データを含まない `GET` であるため ETag / Cache-Control が有効に働き、量は問題にならない。規則レイヤを返さないのは、返せば同じ判定規則の実装がクライアントと backend の2箇所に分かれるためである(§4.4.5)

#### 4.4.4 更新運用

- **`curricula/` は確定後は編集しない。** 誤記の修正を除いて手を入れない。履修要項が改訂された場合は既存ファイルを書き換えず、新しい `admission-<年度>/` を追加する
- **`duplicate_of` を持つファイルを修正するときは、複製元・複製先の双方に同じ変更を入れる。** 複製をやめて内容を分岐させる場合は `duplicate_of` を外す
- **`offerings/` は毎年度シラバス公開後に新しいディレクトリを追加する。** backend が参照するのは運用対象年度の1ディレクトリのみだが、過去年度分は削除せず残す(名寄せ結果の変遷を追跡し、シラバスコードの年度不変性を検証するため。§5.1.4)

#### 4.4.5 要件充足判定の所在

**卒業要件の充足判定(要件枠ごとの修得済み単位と不足単位の算出)は backend で行い、クライアントでは行わない。** 判定は `requirement_slots[].accepts` による科目の割り当て、`overflow_to` のカスケード3系統、`credit_caps` の算入上限と溢れ先、`tracks[].constraints` のコース別下限、マージで導出した専門関連科目の限定的な扱い(§4.4.3)を伴う。これらをクライアントにも実装すると、§5.1.5 の規約の解釈が TypeScript と Python の2箇所に分かれ、履修要項の改訂時に片方だけが更新されても検出できない。加えて時間割の組み立て(§7.2)は同じ判定で不足を埋め、アシスタントのプロンプトにも判定結果を与える必要があり(要件§4.3 の単位数の最適化)、backend 側の実装はいずれにせよ避けられない。判定を1箇所に置く理由はこの二重実装の回避であって、データをクライアントへ渡さないことではない(§4.4.3)。

- 判定は `app/curricula/requirements.py` に**純関数**として置く。入力はマージ済みの Curriculum と既修得科目リスト、出力は要件枠ごとの充足状況とし、HTTP に依存させない
- frontend へは `POST /api/requirements`(§6.1)で提供する。既修得科目を本文に含むため `GET` ではなく `POST` とし(成績情報を URL やアクセスログに残さないため)、他のチャット系と同様に永続化もログ記録もしない(§4.2.3)
- 時間割の組み立て・アシスタント・シラバスチャット(§7.2〜§7.4)では、この関数を **HTTP を経由せず直接呼ぶ**
- **検索画面のタグ(§8.2.1)は規則レイヤを必要としない単純な突合であり、クライアント側で行う**(既修得科目をサーバへ送らずに済む)
- **卒業残り単位は `POST /api/requirements` の `remainingCredits` を使う**(今期の時間割を修得したとみなした判定の値。§8.3.5)。単純な引き算(`graduation.total_credits` − 合格科目の単位合計)は、算入上限や随意科目で数えられない単位があると残りを少なく見せるためである。判定が引けないあいだだけ、その引き算で代わりに出す(`lib/creditSummary.tsx`。`total_credits` は `GET /api/curricula` が返す。§6.1)
