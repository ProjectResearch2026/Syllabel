#### 4.1.2 状態管理

- Zustand store 4本: 学生プロファイル(`lib/student.ts`)、対話履歴(`lib/chat.ts`)、履修提案の受信状態(`lib/proposal.ts`。スキーマは §5.2.3)、検索画面の絞り込み状態(`lib/syllabusUI.ts`)。後の2本は当初想定していなかったもので、提案の SSE 受信状態(§6.1.1)と検索画面の絞り込みがいずれも画面をまたいで共有されるため store に置いた
- すべて **永続化機能を意図的にオフ** にする(要件§5.2)。`persist` ミドルウェアを使わないことで担保し、ページリロード・タブクローズで完全消失する
- リセット機能(要件§4.8)は `clearProfile()` と対話履歴の `clearAll()` を呼ぶだけで実現。消したあとトップ(取り込み画面)へ戻す**遷移は `next/navigation` の `router` で行う** — `window.location` による素の遷移には `basePath`(§3.5.2)が付かず、アプリのトップではなく配信サーバのルートへ飛ぶ。リセットはヘッダー・PC のマイデータ・モバイルの設定の3か所にあり、いずれも同じ形にする
- サーバから取得するデータ(シラバス検索結果、履修要項データ等)は各画面の `fetch` で取る。キャッシュライブラリは導入していない(§2)

#### 4.1.3 PDF解析(クライアント側)

- `pdfjs-dist` でテキストレイヤーを抽出
- 龍谷大学成績表レイアウト前提のルールベースパーサーを実装
- 評価記号(`T`/`N`/`G`/`D`/`J`/`M`)と数値スコアを認識し、合否を判定(要件§4.2)
- 履修グリッドの `***`(登録科目)/ `*`(継続履修中)は**登録済み・成績未確定**(`registered`)として取り込む。成績のセルより後の学期にある印だけを採る(§5.2.1)
- 成績表の作成日(右上の月日+ヘッダの年度)と「在籍年数 / 休学年数 / 在学年数」を読む。次に登録する学期の推定に使う(§5.2.1)
- **基本情報欄は見出し「入学日」からの相対位置で読む。** 帳票は作成年度によって全体が縦にずれる(値の行が 2026年9月作成は y=701、2024・2025年9月作成は y=719)。見出しから値までは3枚とも +30 で一定だった
- 学籍番号は意図的に抽出しない(要件§4.2)
- 解析失敗時は「読み取れませんでした、手入力に切り替えてください」とフォールバック

#### 4.1.4 ストリーミング表示

- backend からの SSE を `fetch` + `ReadableStream` で受信
- 受信した chunk を逐次 React state に反映、画面に追記表示
- **本文が1文字も届いていないあいだ、吹き出しを空のままにしない。** 生成中であることを示す指標(3点のアニメーションと短い文言)を出し、本文が届いた時点で本文に差し替える。履修提案は最初の1文字まで4〜5分かかり得る(§7.2)し、チャット系も思考を有効にしている(§6.3.1)ため1回に100秒を超えることがある。そのあいだ吹き出しが無地のままだと、**待っているのか壊れているのかを学生が判断できない**
- **指標は `components/ai/ThinkingIndicator.tsx` に1つだけ置く。** 会話を描く面ごとに写さない(§4.1.5 の `MarkdownText` と同じ扱い)
- **文言は呼び出し側が渡す。** 待ち時間の長さが画面で違うためで、**履修提案の生成だけは所要時間を添える**(「提案を作っています。4〜5分ほどかかります」)。チャット系は分の単位ではないため既定の文言(「考えています…」)のままとする。提案の生成中かどうかは §5.2.3 の `status` が `loading` かで決まる
- **点は動きを読めない環境では伝わらないため、文言を必ず添える。** 点そのものは `aria-hidden` とし、読み上げは文言に任せる
- **生成が終わっても本文が空のまま、という吹き出しも残さない。** 起きるのは2通りで、(1) 生成・受信の途中で会話を切り替えて退避した場合(退避は `streaming` を下ろして保存するため、戻すと指標も本文も無い吹き出しになる)と、(2) 本文も `error` も来ずに `done` だけが届いた場合である。前者は退避の時点で「提案の作成を中断しました。」などの中断の旨に置き換え、後者は「応答を受け取れませんでした。」とする

#### 4.1.5 AI回答のMarkdown表示

- AI の回答は **Markdown として描く**(`components/ai/MarkdownText.tsx`)。モデルは太字・箇条書き・表を混ぜて返すため、素のテキストとして描くと `**必修**` の `**` や `|---|---|` の罫線がそのまま学生に見える。科目の比較や条件の列挙では表と箇条書きのほうが読みやすく、モデル側で禁じるのではなくフロントで描く
- 使うのは `react-markdown` と remark プラグイン2つ。`remark-gfm` が表・取り消し線・チェックリストを、`remark-breaks` が**段落内の単独改行**を担う。Markdown の既定では単独改行が消えるが、日本語の回答は1文ずつ改行して返ってくることが多く、消すと読みにくい
- **生の HTML は描かない。** `rehype-raw` を入れなければ `react-markdown` はタグを文字として出す。モデルの出力を DOM に流す口を開けないため、入れない
- 描くのは **AI側の吹き出しだけ**。学生が入力した文は Markdown として解釈せず、そのまま文字として出す
- 表は**吹き出しの中で横スクロールさせる**。吹き出しの幅(280〜290px。`ui-ux/ui-design_*.pen`)は設計どおりに保ち、表のために広げない
- 会話を描く3か所(モバイルのシート `AiMessageArea`、PC のパネル `AiChatPanel`、モバイルの履修提案チャット `MobileProposalPage`)で**同じ描き方**を共有する。字の大きさ・行間・色だけを吹き出しごとに外から与える

#### 4.2.2 役割

- フロントからのリクエストを受け、必要に応じて履修要項データを参照し、PydanticAI で定義したエージェントに処理を委ねる
- エージェントは vllm を OpenAI 互換クライアント経由で呼び、必要に応じて api-clean を tool calling で叩く
- 応答は SSE でフロントへストリーミング

#### 4.2.3 学生データの取り扱い

- backend は学生プロファイル(学年・課程・既修得科目)をリクエスト本文で受け取り、推論用プロンプトの組み立てに使うが、**永続化しない**
- リクエスト処理完了後にメモリから破棄される
- backend 自身のログにも記録しない(要件§5.5)
- **ただし、組み立てたプロンプトと応答は経路上のトークンゲートウェイに100日間記録される**(§3.4.3、§9.1)。受け取った学生プロファイルのうちプロンプトへ載せるものは最小限とする(§7.2.1)
- **api-clean へは学生プロファイルを渡さない。** 送るのは科目の検索条件(科目名・開講年度・シラバスコード等)に限られる(§6.2)

#### 4.2.4 配置と実行基盤

- **公開 VM 上で rootless Podman のコンテナとして動かす**(§3.1、§3.2.1)。`backend/Dockerfile` をそのままビルドする
- **`USER` による非 root 化を行わない。** 公開 VM のホームの default ACL とコンテナの uid マッピングが噛み合わず、非 root ユーザではイメージ内の実行ファイルを読めずに起動に失敗する(理由は §3.2.1)
- **イメージは公開 VM 上で x86_64 としてビルドする。** DGX Spark 上で arm64 として作ったイメージは流用できない(§3.2)
- **上流2つはいずれもホストを跨ぎ、いずれもトークンゲートウェイを経由する。** vllm は §3.4.3・§6.3、api-clean は §3.4.4 による。**base_url とトークンを環境変数で与える形が2組になるだけで、扱いは同じ**である(`backend/app/settings.py`)。コード側は接続先の所在を知らない

### 4.3 vllm(LLM 推論サーバ)

- vLLM を Docker(**`vllm/vllm-openai:v0.27.1`**)で起動する。**タグを固定する** — 従来の `latest` は次の pull で実体が黙って変わり、本書に記した実測値と対応しなくなる。既存の qwen-ocr も `v0.24.0` でピン留めされており(§3.2.3)、運用を揃える。移行前の実体は vLLM 0.20.0 / transformers 5.6.2 であった(2026-09-19 実測)
- **下記の起動オプションが v0.27.1 でそのまま通ることは検証済みである**(2026-09-19)。存在しないモデルパスを与えて `vllm serve` を起動し、`unrecognized arguments` も `invalid choice` も出ずにモデルの解決段階まで到達することを確認した。`--language-model-only` は残っており、`--reasoning-parser qwen3` と `--tool-call-parser qwen3_coder` は値ごと受理される
- **`vllm` の CLI は GPU が見えないと、引数を解釈する前に `RuntimeError: Failed to infer device type` で落ちる。** `VllmConfig` の既定値の計算がデバイス判定に依存するためで、`--help` すら印字されない。**この挙動は 0.20.0 も v0.27.1 も同じ**であり、`docker run` でオプションを確認するときは `--gpus all` を付ける。compose 経由の起動では `deploy.resources.reservations.devices` が GPU を渡すため問題にならない
- **`vllm serve --help` の出力形式は 0.20.0 から変わっている。** v0.27.1 は設定セクションの一覧のみを出し、全オプションは `--help=all`、個別のフラグは `--help=<フラグ名>` で引く
- **Qwen3.8-27B-FP8 と Qwen3.6-27B-FP8 の差は重みだけである。** 両者の `config.json` は `transformers_version`(`4.57.1` → `5.8.0.dev0`)の1行を除いて完全に一致する(2026-09-19 差分確認)。64層(`linear_attention` 48 + `full_attention` 16)・`max_position_embeddings` 262144・ビジョンエンコーダ付き・FP8(e4m3、`weight_block_size` [128,128])の量子化設定まで同一であり、**モデルの側から起動オプションを変える理由は無い**。新しい `transformers_version` で書かれた config は移行前の 0.20.0(transformers 5.6.2)でも読めており(`AutoConfig.from_pretrained` で確認、同日)、**モデル側のバージョン要求のためにイメージを上げる必要は無かった**。上げるのはタグ固定と将来の可搬性のためである
- `--model /models`(暫定モデル Qwen3.8-27B-FP8 を事前DLしたローカルパスを指す。リポジトリ名は起動時に使わない)。FP8 量子化済みで、**重みのロードは実測 27.64 GiB**(2026-09-19 起動ログ)。3.6 とほぼ同じであり、GPU の取り分は据え置いた(§3.2.3)
- **`--model` は将来の vLLM で削除される。** v0.27.1 は起動時に「モデルは位置引数か設定ファイルで渡すべきで、`--model` は将来の版で削除される」と警告する。**いまは動くが、次にイメージを上げたときに壊れうる**ため、位置引数への移行を §13 に置く
- このモデルは**ビジョンエンコーダ付き(画像/動画対応)**だが、本プロジェクトはテキスト用途のため **`--language-model-only`** を付け、ビジョンを無効化してメモリを KV cache に回す。効いていることは起動ログの `All limits of multimodal modalities supported by the model are set to 0, running in text-only mode.` で確認する
- **Blackwell(GB10)では vLLM が DeepGemm を自動で無効化し、CUTLASS へ退避する。** 起動ログに `Auto-disabled DeepGemm for model_type=qwen3_5_text on Blackwell. DeepGemm E8M0 scale format causes accuracy degradation for this architecture.` が出る。**精度に関わる退避を vLLM 側が行っている**ので、`VLLM_USE_DEEP_GEMM` を触って上書きしない
- **`--reasoning-parser qwen3`** を指定(思考(reasoning)モデルのため必須。無いと思考トークンが本文に混ざり、PydanticAI の構造化出力が壊れる)
- 思考を**出させるかどうかはサーバ側では固定しない**。上記のパーサは思考と本文を分離するためのものであり、思考の有無はリクエストごとに `chat_template_kwargs.enable_thinking` で決める。履修提案は思考を切り、チャット系は既定のまま有効とする(理由と実機計測は §6.3.1)
- tool calling は **`--enable-auto-tool-choice` + `--tool-call-parser qwen3_coder`** で対応(公式モデルカード指定。`hermes` ではこのモデルの出力書式と合わず、ツール呼び出しがエラーにならず**サイレントに無視される**。`--tool-call-parser` 自体がないと vLLM は起動時にエラーで停止する)。**より頑健とされる `qwen3_xml` への変更は、実機でツール呼び出しが `tool_calls` として返ることを確認したうえで判断する**(§13)
- **`--served-model-name qwen3.8-27b-fp8`** を指定し、§6.3 の `OpenAIChatModel('qwen3.8-27b-fp8', ...)` と一致させる(不一致だと 404)。**モデル名は backend・トークンゲートウェイ・vllm の3箇所で一致していなければならず、差し替えるときは3つを揃えて動かす**(§3.4.3.1)
- `--max-model-len 131072`(既定 262,144 はメモリ過大。公式は思考能力維持のため最低 128K の確保を推奨。OOM 時はさらに削減)
- DGX Spark は**単GPU**のため tensor parallel は使わない(=1)。`--gpu-memory-utilization` は同一GPUを共有する他ワークロードがある前提で 121GiB のユニファイドメモリに収めるため **0.4** とする。**3.6 での実測(2026-09-19)は本コンテナ 47,645 MiB、KV cache 16.77 GiB = 68,208 tokens(`--max-model-len 131072` に対し同時実行 2.05x)**であり、重みがほぼ同じ 3.8 でも同水準を見込む(§3.2.3)
- モデルは**事前に取得**して `/srv/qwen3.8/models/Qwen3.8-27B-FP8` に置き、`-v .../Qwen3.8-27B-FP8:/models:ro` で**読み取り専用 bind mount** する(`--model /models`)。取得は `hf download Qwen/Qwen3.8-27B-FP8 --revision <commit SHA> --local-dir ...` で**リビジョンを固定**する(移行時に用いた SHA は `017b9c7af6b5689d5dd426a76e0bc077eb5ca20a`)。`--model` がローカルパスを指すため起動時に HF から重みを取得せず、再現性を確保する(コンテナ起動時に都度DLしない。なお現状 `HF_HUB_OFFLINE` 等の環境変数までは設定していない)
- **旧モデルは消さずに残す。** `/srv` に十分な空きがあり(2026-09-19 時点で 2.8 TB)、`/srv/qwen3.6/models/Qwen3.6-27B-FP8` を残しておけば bind mount 元とモデル ID を戻すだけで切り戻せる
- OpenAI 互換 API を `/v1/chat/completions` で公開
- **初回起動は約6分半かかる**(2026-09-19 実測。重みのロード 203 秒 + `torch.compile` 71.5 秒 + ウォームアップ 36.5 秒 + CUDA graph キャプチャ)。`docker-compose.yml` の `start_period: 900s` はこれを見込んだ値である。2回目以降は `/root/.cache/vllm/torch_compile_cache` が効くため短くなる
- **DGX Spark 上でホストの loopback にのみバインドする。** backend は別ホスト(公開 VM)にあり、教員側のトークンゲートウェイ経由で到達する(§3.4.3、§6.3)。frontend からは直接呼ばない。**この経路は発行されたトークンを用いて利用する**(§3.4.3)

### 4.4 履修要項データ層

#### 4.4.1 データ生成方針

- 龍谷大学公式サイトから閲覧できる履修要項を、**手動で YAML 形式に転記**する
- 出典ページの設置科目一覧・卒業要件表は画像形式で提供されるが、これらも転記対象とする(単位数・配当年次・開講クォーター・科目区分・区分別要件単位数)。画像にのみ掲載される科目(キャリア実習系・職業指導など)も記載する
- **対象は先端理工学部6課程 × 2024・2025・2026年度入学の3コホートとする。** 2026年度時点で1〜3年次にあたる。4年次(2023年度以前の入学生)を対象外とするのは、履修要項サイトで参照できるのが2024・2025・2026年度入学生版の3種のみであるため。2024・2025年度入学分は6課程と教養教育科目を作成済みで、2026年度入学分は転記中である(2026-09-09 時点)。第1フェーズで利用するのは知能情報メディア課程分のみで、他課程分は第2フェーズ以降に向けた先行整備という位置づけ
- 学修プログラムは構造が複雑なため現時点では転記しない。第2フェーズで扱いを確定した上でスキーマ・データに追加する
- 転記担当者がドラフトを作成 → Pull Request → アドバイザー教員のレビュー・承認(要件§8末尾)
- 第2フェーズ以降で他学年・他学部に対象を広げる際は、同じ手順で対象範囲のファイルを追加する

**出典は入学年度ごとに別ページに分かれており、教養教育科目は2025年度入学分から学部ページの外にある。** 転記時は次の対応表に従う(いずれも `https://rishu.ryukoku.ac.jp` 配下)。

| 入学年度 | 専攻科目 | 教養教育科目 |
|---|---|---|
| 2024 | `/curriculum/2024/faculty-rikou/s05` | `/curriculum/2024/faculty-rikou/s04` 【3】(学部ページ内) |
| 2025 | `/curriculum/2025/faculty-rikou/s04` | `/organization/no5`(教育課程＜共通＞。先端理工学部【〜2025年度入学】) |
| 2026 | `/curriculum/faculty-rikou/s04`(年度を含まない URL が最新年度) | `/organization/no3`(同上。先端理工学部【2026年度入学〜】・農学部) |

**入学年度で決まって変わらないデータと、開講年度ごとに変わるデータを分離する。** 履修要項(卒業要件・科目区分・設置科目)は、ある年度の入学生に対して入学時点で決まり、その学生が卒業するまで変わらない。したがって一度確定したら以後編集しない。一方シラバスコードは開講年度ごとに発行される値であり、毎年更新が要る。両者を同一ファイルに置くと、開講年度が進むたびに過去の入学年度のファイルまで書き換えることになり、確定済みの卒業要件を壊しかねない。したがって**履修要項ファイル(`curricula/`)にはシラバスコードを持たせず、開講年度ファイル(`offerings/`)に分離する**(§4.4.2)。両者は**科目名**で結合する。

**教養教育科目は課程間では共通だが、入学年度で版が分かれる。** 履修要項の「教養教育科目の教育目的及び履修方法」は学部単位で規定されており、6課程で内容が一致する。したがって課程ファイル6本に同一内容(約150科目)を複製することはせず、入学年度ディレクトリごとに教養教育科目ファイル(`00-liberal-arts.yaml`)を1本置く。教養教育科目の**卒業要件枠(`liberal.*` スロット)も課程ではなく学部で決まる**ため、設置科目一覧と併せてこのファイルが唯一の定義元となる(§5.1.3)。課程ファイルは `liberal.*` スロットを持たない。課程固有の例外(2024・2025年度入学版の「生活の中の化学」は応用化学課程では履修不可)も、出典が教養教育科目側の設置科目表の備考欄であるため、課程ファイルではなくこのファイルに `not_available_to_programs` として持たせる。

**ただし入学年度をまたいだ共通化はしない。** 2026年度入学生から教養教育カリキュラムが全面改訂されており(改訂内容は§5.1.3)、単一の共通ファイルでは表現できない。2024年度入学と2025年度入学は内容が一致する(設置科目一覧を科目名レベルで突合し、差分が表ヘッダと備考の文言のみであることを確認済み)が、この場合も**共通ファイルへの参照ではなく、同一内容のファイルを両方のディレクトリに置く**。参照方式では入学年度をまたぐパス参照と版の適用範囲判定が必要になり、「このコホートはどの版を見るか」の分岐がロード処理と検証の双方に入り込む。複製であれば `admission-<年度>/` 1ディレクトリがそのコホートの完結した定義になり、マージがディレクトリ内で閉じる。複製が黙って食い違う事故は `duplicate_of` の宣言と CI のハッシュ一致検査で防ぐ(§5.1.3、§12.2)。

**専門関連科目は転記せず、同一入学年度の他課程ファイルから導出する。** 専門関連科目とは所属課程以外の課程が主体となって開講する専攻科目であり、その実体は他課程ファイルの `courses` そのものである。各課程ファイルに列挙すると同じ科目を課程数ぶん複製することになるため、`category: "専門関連科目"` を持つレコードは転記せず、ロード時に「同一入学年度の他課程ファイルに載る専攻科目」として解決する(§4.4.3)。ただし学修プログラム科目は転記対象外(前述)であり、この導出にも含まれない。

**履修要項の版表記(【20XX年度以降入学生】)を、ファイルの同一性の根拠にしてはならない。** 各課程の見出しにはこの表記があるが、更新の基準が一貫していない。2024年度版と2025年度版を突合した結果は次のとおりで、版表記が据え置きでも設置科目一覧は変わっている。

| 課程 | 2024年度版 | 2025年度版 | 2024→2025 の実際の変更 |
|---|---|---|---|
| 01 数理・情報科学 | 【2020年度以降】 | 【2020年度以降】 | 設置科目 +5 のみ(下記の全課程共通分) |
| 02 知能情報メディア | 【2020年度以降】 | 【2025年度以降】 | +5 に加え、「ネットワーク構成論」が2年次配当→3年次配当、「コラボレーション演習」廃止。規定本文は変更なし |
| 03 電子情報通信 | 【2023年度以降】 | 【2023年度以降】 | 設置科目 +5 のみ |
| 04 機械工学・ロボティクス | 【2020年度以降】 | 【2025年度以降】 | +5 に加え、Ⅰ/Ⅱに分割されていた科目の統合を含む大規模再編。規定本文は変更なし |
| 05 応用化学 | 【2020年度以降】 | 【2025年度以降】 | +5 に加え、先修制の変更(「特別研究」の履修要件に指定7科目の単位修得が追加) |
| 06 環境生態工学→環境科学 | 表記なし | 表記なし | 課程名の改称と設置科目 +5 |

全課程共通の +5 は、2025年度入学から新設された「キャリア実習・実習指導」「先端理工キャリア実習Ⅰ・Ⅱ」「先端理工インターンシップⅠ・Ⅱ」である。2026年度入学ではさらに「協定型インターンシップ」「理工インターンシップ(学外実習)Ⅰ・Ⅱ」「クラウドコンピューティング演習」が全課程から削除されている。すなわち**専攻科目は6課程 × 3入学年度の18ファイルすべてが別内容**であり、複製になるのは教養教育科目ファイルの1組(2024年度入学と2025年度入学)だけである。

#### 4.4.2 ファイル配置と命名

```
curricula/
  admission-2024/
    00-liberal-arts.yaml              # 教養教育科目(〜2025年度入学版)
    01-suri-joho-kagaku.yaml          # 数理・情報科学課程
    02-chinou-joho-media.yaml         # 知能情報メディア課程
    03-denshi-joho-tsushin.yaml       # 電子情報通信課程
    04-kikai-kogaku-robotics.yaml     # 機械工学・ロボティクス課程
    05-oyo-kagaku.yaml                # 応用化学課程
    06-kankyo-seitai-kogaku.yaml      # 環境生態工学課程
  admission-2025/
    00-liberal-arts.yaml              # admission-2024/ と同一内容(duplicate_of を付す)
    01-suri-joho-kagaku.yaml          # 01〜05 はファイル名のみ admission-2024/ と共通。内容は別
    ...
    06-kankyo-kagaku.yaml             # 2025年度に環境科学課程へ改称
  admission-2026/
    00-liberal-arts.yaml              # 教養教育科目(2026年度入学版。別カリキュラム)
    01-suri-joho-kagaku.yaml          # 6課程すべて履修要項が改訂されている
    ...
    06-kankyo-kagaku.yaml
offerings/
  2026/
    admission-2024/
      00-liberal-arts.yaml
      01-suri-joho-kagaku.yaml
    admission-2025/
    admission-2026/
```

- 入学年度をディレクトリ、課程をファイルとする(旧 `<課程略称>_<入学年度>.yaml` から変更)。入学年度が第一階層になることで、新しい入学年度を追加するときに既存ディレクトリへ手を入れずに済む
- **ファイル名は `<課程コード2桁>-<課程名のローマ字表記>.yaml`。**
  - **課程コード**は大学が公表している番号で、科目ナンバリングの第2要素(`Y-01-MMA-1-01-P` の `01`)およびシラバスコード先頭4桁(`Y001` の `001`)と一致する。課程が改称されても変わらない(環境生態工学課程 → 環境科学課程の改称後も `Y006` のまま)ため、これを一次識別子とする
  - **ローマ字表記は課程名を省略せずすべて音写する。** 語の区切りはハイフン。末尾の「課程」と中黒(・)は書かない。旧命名(`chinou_media` は「情報」を、`kankyo_seitai` は「工学」を落としていた)は省略の基準が定まっておらず、課程名からファイル名を導出できなかった。省略しない規則にすることで一意に定まる
  - 対応表: 01 数理・情報科学 `suri-joho-kagaku` / 02 知能情報メディア `chinou-joho-media` / 03 電子情報通信 `denshi-joho-tsushin` / 04 機械工学・ロボティクス `kikai-kogaku-robotics` / 05 応用化学 `oyo-kagaku` / 06 環境生態工学 `kankyo-seitai-kogaku`(2025年度以降の入学年度は環境科学 `kankyo-kagaku`)
- 課程名は改称され得る。ファイル名のローマ字部分は**その入学年度時点の名称**に固定し、以後変更しない。改称の追跡は課程コードと `program.name_aliases` が担う
- **教養教育科目ファイルは各入学年度ディレクトリに `00-liberal-arts.yaml` として置く。** 課程ファイルからのパス参照は持たず、**同一ディレクトリにあることをもって対応づける**(§4.4.3)。`00` は課程コードとして使われていない値であり、一覧したとき課程ファイルより先に並ぶ
- **内容が他コホートと同一のファイルは、参照ではなく複製を置き、`duplicate_of` に複製元のパスを書く**(§5.1.3)。同一性の検査対象はこの宣言があるファイルのみとする(§12.2)
- `offerings/<開講年度>/` は `curricula/` と**同じ相対パス構造**(`admission-<入学年度>/<同名ファイル>`)を持たせる。入学年度が違っても同じ開講年度コードを指すことは正常であり、重複を排除しない

#### 4.4.3 ロード方式

- backend 起動時に `curricula/**/*.yaml` と `offerings/<運用対象年度>/**/*.yaml` を読み込み、Pydantic スキーマ(§5.1)で型付けしてメモリ上に保持する
- 課程ファイルは以下の順にマージし、課程ごとに1つの完全なオブジェクトを組み立てる。**参照はすべて同一の `admission-<年度>/` ディレクトリ内で閉じ、他の入学年度のファイルを読まない**:
  1. 同一ディレクトリの `00-liberal-arts.yaml` の `requirement_slots` / `credit_caps` / `courses` / `prerequisites` を取り込む(教養教育科目の要件枠と設置科目はこのファイルが唯一の定義元。§4.4.1)。このとき `not_available_to_programs` に当該課程の `program.code` を含む科目は取り込まない(§5.1.5)。`prerequisites` は課程ファイルと教養教育科目ファイルの双方が同じ形で持つ先修制の規定であり(§5.1.5)、いずれも規則レイヤとして履修提案の先修条件の判定(§7.2.1 手順4b)に用いるため、課程ファイル由来のものと合わせて1つのリストに保持する。要件充足判定(§4.4.5)は先修制を見ない(卒業要件の単位数だけを数える)
  2. 同一ディレクトリの他課程ファイルの `courses` を `category: "専門関連科目"` として取り込む(§4.4.1)。取り込んだ科目は `related` / `free.faculty` スロットの判定にのみ用い、当該課程の設置科目としては扱わない
     - **当該課程の `courses[].title` と同名の科目は導出しない。** §4.4.1 の「所属課程以外の課程が主体となって開講する専攻科目」という定義上、当該課程が開講している科目は専門関連科目ではない。除外しないと課程あたり17〜22科目が二重に載り、うち1〜2件は同名で単位数が食い違う(2024年度入学コホートでは、課程01の「セミナーⅠ」が自課程の4単位と課程06由来の2単位の2件になる)
     - **他課程どうしで同名の科目は全レコードを保持し、出典の課程コードで区別する。** 属性が食い違う場合にマージ時点で単位数を決め打ちする根拠がないため(課程01の「特別研究」は他5課程から導出され、応用化学課程のみ10単位・他は6単位)。どの出典を採るかの判断は充足判定(§4.4.5)の側に委ねる。この重複が後述の `courses[].title` 重複検査の対象外である理由でもある
- 起動時にスキーマバリデーションを実行し、不正があれば起動失敗(転記ミスを早期に検出)。型検査に加えて以下の整合性を検証する:
  - `type` が {必修, 選択必修, 選択, 随意} のいずれかであること。`category` / `subcategory` が §5.1.5 の列挙値のいずれかであること
  - `term` と `quarters` の整合(§5.1.5)。`quarters` は任意であり、教養教育科目は `前期` / `後期` でも持たない(クォーター制の対象外。§5.1.3)。持つ場合のみ `前期` ⇔ `{1Q, 2Q}` / `後期` ⇔ `{3Q, 4Q}` を検査し、`通年` / `サ集` は持たないことを検査する
  - `kikan: true` の科目が `type: "選択必修"` であること(§5.1.5)
  - `constraints[].slot` および `constraints[].track_group` の参照先が存在すること(前者は `requirement_slots`、後者は `courses[].track_groups`)
  - `by_semester` の各要素が `max_credits_per_semester` と `max_credits_per_year` のどちらか一方のみを持つこと
  - 課程ファイル・教養教育科目ファイルの `admission_year` が、そのファイルが置かれているディレクトリ名の年度と一致すること
  - 各 `admission-<年度>/` ディレクトリに `00-liberal-arts.yaml` がちょうど1つ存在すること
- 次の5件は**マージ後**のオブジェクトに対して検証する。教養教育科目ファイル単体では `liberal.elective` の `overflow_to` 先である `free.all` が解決できず、スロット単位の検算も成立しないため、ファイル単体では検査しない:
  - `requirement_slots[].key` が一意であること
  - `requirement_slots[].credits` の合計が `graduation.total_credits` に一致すること
  - `overflow_to` の参照先が `requirement_slots` に存在し、循環していないこと
  - `courses[].title` に重複がないこと。この検査の対象は当該課程の設置科目(教養教育科目ファイル由来の教養教育科目 + 課程ファイルの専攻科目)であり、上記2.で導出した専門関連科目は含めない(他課程に同名科目が存在し得るため)
  - `prerequisites` に書いた科目名(`title`、`all_of` / `any_of`、`min_credits[].from`、`one_of` の中のもの)が、同じ `admission-<年度>/` の履修要項ファイルのいずれかの `courses[].title` に存在すること(§5.1.5)。先修制の判定は科目名で修得科目と突き合わせるため、転記ミスは黙って「未修得」になる。比較は突合と同じ規則(NFKC 正規化と空白除去)で行う。当該課程が履修できない教養教育科目(`not_available_to_programs`)の先修制も1つのリストに取り込まれるため、上記1.で除外する前の科目名と照らす。正規化の規則は `app/curricula/titles.py`(科目名の突合規則を1か所に置くモジュール)にあり、要件充足判定(§4.4.5)とこの検査が共用する
- **`offerings` の `unresolved` が非空でも起動は継続し、警告ログを出す。** 当該科目はシラバスコード未解決として扱い、コードを要する処理(検索画面のタグ付け §6.1、開講情報の取得 §7.2)の対象外とする。`offerings` は api-clean から機械生成する値であり、上流の科目名変更ひとつで稼働中のサービスが起動不能になる事態は避ける。不整合の検出は PR 時の CI(§12.2)で行い、そこでマージをブロックする
- 任意フィールドは null / 省略を許容する。Pydantic では `Optional` として定義する
- 個々のリクエストでは、該当課程・該当入学年度のオブジェクトのみを参照する
- **クライアントへ返すのは科目レイヤに限り、規則レイヤは返さない。** 保持したオブジェクトは用途の異なる次の2層からなる:
  - **科目レイヤ** — `courses` の科目属性(`title` / `category` / `subcategory` / `type` / `credits` / `grade` / `term` / `quarters` / `kikan`)と、`offerings` の `resolved` が与えるシラバスコード。検索画面のタグ付け(§6.1)はこの層だけで完結する(コードから科目を引き、`type` と既修得科目を突き合わせるだけで、履修要項の規則の解釈を伴わない)ため、`GET /api/curricula`(§6.1)でクライアントへ返す
  - **規則レイヤ** — `requirement_slots`(`accepts` / `overflow_to`)・`credit_caps`・`tracks[].constraints`・`prerequisites`・`grade_up_requirements`・`registration_limits`。卒業要件の充足判定に用いる規則であり、クライアントへは返さない(§4.4.5)
  - **この分割の基準はデータ量ではない。** 科目レイヤはタグ付けの都合上マージ後の全課程分を返す必要があり(2024年度入学コホートで650科目、JSON 約109KB / gzip 約6KB)、量としては規則レイヤより大きい。学生データを含まない `GET` であるため ETag / Cache-Control が有効に働き、量は問題にならない。規則レイヤを返さないのは、返せば同じ判定規則の実装がクライアントと backend の2箇所に分かれるためである(§4.4.5)

#### 4.4.4 更新運用

- **`curricula/` 配下の追加・変更は Pull Request 経由でアドバイザー教員のレビュー・承認を必須とする。** GitHub の CODEOWNERS で `curricula/` の承認者をアドバイザー教員に限定することを想定
- **`offerings/` はレビュー対象外とする。** 履修要項の転記物ではなく、api-clean から機械的に生成した名寄せ結果であるため。正しさは CI の api-clean 照合(§12.2)で担保する
- **`curricula/` は確定後は編集しない。** 誤記の修正を除いて手を入れない。履修要項が改訂された場合は既存ファイルを書き換えず、新しい `admission-<年度>/` を追加する
- **`duplicate_of` を持つファイルを修正するときは、複製元・複製先の双方に同じ変更を入れる。** 片方にしか入らなかった場合は CI のハッシュ一致検査(§12.2)で失敗する。複製をやめて内容を分岐させる場合は `duplicate_of` を外す
- **`offerings/` は毎年度シラバス公開後に新しいディレクトリを追加する。** backend が参照するのは運用対象年度の1ディレクトリのみだが、過去年度分は削除せず残す(名寄せ結果の変遷を追跡し、シラバスコードの年度不変性を検証するため。§5.1.4)

#### 4.4.5 要件充足判定の所在

**卒業要件の充足判定(要件枠ごとの修得済み単位と不足単位の算出)は backend で行い、クライアントでは行わない。** 判定は `requirement_slots[].accepts` による科目の割り当て、`overflow_to` のカスケード3系統、`credit_caps` の算入上限と溢れ先、`tracks[].constraints` のコース別下限、マージで導出した専門関連科目の限定的な扱い(§4.4.3)を伴う。これらをクライアントにも実装すると、§5.1.5 の規約の解釈が TypeScript と Python の2箇所に分かれ、履修要項の改訂時に片方だけが更新されても検出できない。加えて履修提案(§7.2)では同じ判定結果をプロンプトへ与える必要があり(要件§4.3 の単位数の最適化)、backend 側の実装はいずれにせよ避けられない。判定を1箇所に置く理由はこの二重実装の回避であって、データをクライアントへ渡さないことではない(§4.4.3)。

- 判定は `app/curricula/requirements.py` に**純関数**として置く。入力はマージ済みの Curriculum と既修得科目リスト、出力は要件枠ごとの充足状況とし、HTTP に依存させない
- frontend へは `POST /api/requirements`(§6.1)で提供する。既修得科目を本文に含むため `GET` ではなく `POST` とし(成績情報を URL やアクセスログに残さないため)、他のチャット系と同様に永続化もログ記録もしない(§4.2.3)
- 履修提案(§7.2)では、この関数を **HTTP を経由せず直接呼ぶ**
- 次の2つは規則レイヤを必要としない単純な突合であり、**クライアント側で行う**(既修得科目をサーバへ送らずに済む)
  - 検索画面のタグ表示「必修 / 選択 / 既修得済み」(§6.1、§8)
  - 卒業残り単位の表示(`graduation.total_credits` − 合格科目の単位合計)。`total_credits` は `GET /api/curricula` のレスポンスに含める(§6.1)
