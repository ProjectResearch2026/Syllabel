## 3. デプロイ構成

> 本書はリポジトリとともに公開する。学内の構成は、本サービスの配置と動作を理解するのに要る範囲に限って書く。ホスト名・アドレス・ポート・アカウント、ホストの内部構成、教員側が管理する中継・入口・トークンゲートウェイの設定は記載せず、運用メモに置く。未確定の事項は §13 に送る。

### 3.1 配置先

本サービスは学内の2台のホストに分けて置く。

| ホスト | 実体 | 稼働させるもの |
|---|---|---|
| **公開 VM** | アドバイザー教員研究室のサーバ上の仮想マシン(x86_64) | 本プロジェクトの gateway(Caddy)、frontend、**backend** |
| **DGX Spark** | 学内の GPU サーバ(arm64) | **vllm、api-clean、postgres-clean** |

このほか、教員側が運用する次の2つを経由する。いずれも本プロジェクトの管理外である。

| 要素 | 役割 |
|---|---|
| 公開入口 | 学外からの HTTPS を受けて TLS を終端し、公開 VM の gateway へ渡す。他のサービスと共用する |
| トークンゲートウェイ | 発行されたトークンを検証し、DGX Spark 上の vllm(★1)と api-clean(★2)へ中継する(§3.4.3、§3.4.4) |

**公開 VM に置くのは、本プロジェクトが新規開発した要素(gateway / frontend / backend)に限る。** シラバスバックエンドは DGX Spark 上のスタックを使う。配置の根拠は §3.4.2(backend)と §3.4.4(シラバスデータ層)による。

**本プロジェクトが DGX Spark にホスト外向けの口を設けることはない。** vllm・api-clean・postgres-clean はいずれもホストの loopback で待ち受け、backend からはトークンゲートウェイ経由でのみ到達する(§3.4.3、§3.4.4)。

**2台とも所有者はアドバイザー教員であり、開発チームは貸与を受けて運用している。** ホスト外へ口を開ける変更(中継の設置、ポートの開放、ファイアウォール)は、権限の有無にかかわらず所有者の判断による(§3.5.3)。公開 VM では root 権限を持たず、OS レベルの操作は依頼による。

学生データを処理する一連の機能は、ブラウザ・公開 VM・DGX Spark で完結する(要件§3.1)。公開 VM とブラウザが学生プロファイルを扱い、DGX Spark は LLM 推論とシラバス参照を担う。**api-clean へ学生プロファイルを渡すことはない**(送るのは科目の検索条件のみ。§6.2)。いずれのホストも学内にあり、成績データが学外へ出ることはない。

### 3.2 コンテナ構成

**2台でコンテナ基盤とアーキテクチャが異なる。** 同一のイメージを両方で使い回すことはできない。

| | 公開 VM | DGX Spark |
|---|---|---|
| 基盤 | **rootless Podman**(docker は無い) | Docker |
| アーキテクチャ | x86_64 | **arm64** |
| 定義 | **Quadlet**(systemd ユーザユニットとして動かす。§3.3) | `docker-compose.yml`(vllm)と、シラバスバックエンドのリポジトリの compose |
| 待受 | rootless のため **1024 未満のポートを待ち受けられない** | すべて loopback(§3.4) |

frontend(`frontend/Containerfile`)と backend(`backend/Dockerfile`)のイメージは**公開 VM 上で x86_64 としてビルドする**。DGX Spark 上で arm64 としてビルドしたイメージは公開 VM では使えない。

シラバスバックエンド(api-clean / postgres-clean)は **DGX Spark 上のスタックを使い、本プロジェクトは移設しない**(§1.1.1、§3.4.4)。公開 VM 側に要るのは、api-clean へトークンゲートウェイ経由で到達するための base_url とトークンだけである(§6.2)。

#### 3.2.1 公開 VM

rootless Podman で3つのコンテナを、Podman ネットワーク `syllabel` 上で名前解決させて動かす。定義は **Quadlet** で、ネットワークと3つのコンテナから systemd ユーザユニットが生成される(§3.3)。**ユニットファイルは本リポジトリの管理外である**(運用メモ)。

**名前はサービス名 `Syllabel` で揃える。** ネットワークは `syllabel`、コンテナとユニットは `syllabel-{backend,frontend,gateway}`、イメージは `localhost/syllabel-{backend,frontend}:latest` とする。**コンテナ名はネットワーク内の名前解決の宛先そのもの**であり、gateway の `BACKEND_ADDR`、frontend の `BACKEND_ORIGIN`、`lib/api_base.ts` の既定値(§6.1)がこの名前を指す。名前を変えるときは、ユニットファイルと環境ファイルを揃えて書き換える。

| コンテナ | イメージ | 役割 |
|---|---|---|
| gateway | `caddy:alpine` | 振り分け。`/syllabel/api/*` を backend、`/syllabel`・`/syllabel/*` を frontend へ。公開 VM で外から受けるのはこのコンテナだけである |
| frontend | 自ビルド(`frontend/Containerfile`) | Next.js standalone(`PORT=3000`、`NODE_ENV=production`) |
| backend | 自ビルド(`backend/Dockerfile`) | FastAPI + PydanticAI。トークンゲートウェイ経由で vllm(§6.3)と api-clean(§3.4.4)を呼ぶ |

**イメージは `USER` による非 root 化を行わない。** 公開 VM のホームの ACL とコンテナの uid の対応の都合で、コンテナ内の非 root ユーザはイメージ内の実行ファイルを読めずに起動に失敗する(`frontend/Containerfile` に同じ理由の記載がある)。rootless Podman ではコンテナ内の root もホスト上の非特権 uid に対応するため、ホストの root 権限には繋がらない。

`curricula/` と `offerings/` は backend コンテナへ読み取り専用でマウントする。**公開 VM 上にリポジトリの clone が要る。**

gateway の振り分けは次のとおりである(Caddyfile は公開 VM 上に置く)。

```caddyfile
:8080 {
      # /syllabel/api/* → バックエンド(/syllabel だけ剥がす)
      handle /syllabel/api/* {
              uri strip_prefix /syllabel
              reverse_proxy {$BACKEND_ADDR}
      }

      # Next.js は basePath 使用時に末尾スラッシュ無しを正規とするため、
      # /syllabel と /syllabel/* の両方をフロントへ渡す
      @app path /syllabel /syllabel/*
      handle @app {
              reverse_proxy syllabel-frontend:3000
      }

      handle {
              respond "not found" 404
      }
}
```

稼働中の設定には、公開入口が渡すパスを `/syllabel` に戻す受けが加わる(§3.5.1。運用メモ)。`BACKEND_ADDR` は環境ファイルで与え、同一 Podman ネットワーク上の `syllabel-backend:8000` を指す。この振り分けが §3.5.2 の URL 構造を決めている。

**Quadlet 管理下のコンテナは、`podman run` で作り直しても定義から作り直される。** 環境変数を変えるときは環境ファイルを直して `systemctl --user restart` を行う。

**SSE のために読み取りタイムアウトを明示する。** Caddy の `reverse_proxy` は既定でレスポンスをバッファリングしないため逐次配信自体は通るが、チャット系は1回のモデル呼び出しに100秒超かかることがあるため、既定のタイムアウトに委ねない(§13)。

**frontend コンテナには backend の宛先を `BACKEND_ORIGIN` で渡す。** サーバ側描画から backend を引く経路(§6.1)が宛先を解決できるようにするためである。渡さない場合は本番既定の `http://syllabel-backend:8000` にフォールバックする。

**backend コンテナには、トークンゲートウェイへの接続情報を渡す**(§6.3)。接続情報は **vllm 向けと api-clean 向けの2組**(base_url とトークン)である(§3.4.4、§6.2)。トークンは環境ファイル(パーミッション 600)に置き、イメージには焼き込まない。ゲートウェイへの名前解決など公開 VM 固有の設定は運用メモに置く。

#### 3.2.2 DGX Spark

リポジトリ直下の `docker-compose.yml` が **vllm を定義する**。**backend はここでは定義しない**(公開 VM 側に置くため。§3.2.1)。シラバスバックエンドは当該リポジトリの compose で DGX Spark 上に稼働する。

**compose のプロジェクト名はサービス名 `syllabel` に固定する**(`docker-compose.yml` の `name:`)。省略時はクローン先のディレクトリ名がプロジェクト名になり、クローンし直すだけで別プロジェクトとして扱われてしまう。

**コンテナはすべてホストの loopback で待ち受ける。** シラバスバックエンド側が定めた条件でもあり、本プロジェクトの都合で外さない。トークンゲートウェイからは教員側が設けた中継を通じて届く(§3.4.1)。

vllm のイメージ・モデル・起動オプションは §4.3 に置く。**`--served-model-name` を変えると、呼び出し側のモデル ID も揃えて変える必要がある**(§3.4.3.1、§6.3)。

#### 3.2.3 GPU の共有状況

DGX Spark の GPU(統合メモリ 121 GiB)は、本プロジェクト外の推論サーバと分け合っている。**`--gpu-memory-utilization 0.4` はこの同居を前提とした値であり、本プロジェクトの都合だけで上げない。** 本プロジェクトの vllm の内訳は、重み約28 GiB・CUDA graph 約1.4 GiB・KV cache 約15.5 GiB で、`--max-model-len 131072` に対して**同時実行は約1.9倍**である。

vLLM v0.21.0 以降は CUDA graph の使用量を見込んでから KV cache を割り当てるため、0.4 の実効値は 0.3884 相当になり、起動ログは 0.4116 への引き上げを助言する。上げるかどうかは同時実行の要件(§10.2)と GPU を分け合う相手との兼ね合いで決める(§13)。

**KV cache のトークン数は vLLM の版によって数え方が違う。** 版をまたいで比べるときは、トークン数ではなく同時実行の倍率で比べる。

### 3.3 起動順序

0. (初回のみ) vllm 用モデルを事前に取得する(§4.3)
1. (DGX Spark)シラバスバックエンドを起動する(当該リポジトリの手順による)
2. (DGX Spark)`docker compose up -d vllm`
3. (公開 VM)backend と frontend のイメージを x86_64 でビルドする(§3.2)
4. (公開 VM)Quadlet のユニットが `default.target` から起動する。個別に操作する場合は `systemctl --user start syllabel-{backend,frontend,gateway}.service`

backend は起動時に履修要項 YAML をロードする。api-clean へ到達できなくても backend 自体は上がるが、シラバス参照を伴う機能が失敗する(§3.4.4)。**vllm は公開 VM 側の起動順序に関与しない**(backend は起動時に vllm へ接続しない)。ただし vllm が停止していると、提案・チャットは `502 upstream_unavailable` で失敗する(§6.3)。

**frontend と backend は揃えて入れ替える。** 両者の間には API の契約があり(§6.1)、片方だけ新しくすると、呼ぶ口が無い・形が違うといった食い違いが起きる。デプロイは両方を建て直してから両方を再起動する。

```bash
podman build -t localhost/syllabel-backend:latest ./backend
podman build -t localhost/syllabel-frontend:latest ./frontend
systemctl --user restart syllabel-backend.service syllabel-frontend.service
```

**API を足した側だけを先に入れるのは安全側である**(使われない口が増えるだけ)。逆順(呼ぶ側を先)は落ちる。判断に迷うときは backend を先に入れる。

**公開 VM のコンテナは Quadlet で systemd ユーザユニットとして動かし、lingering を有効にする。** rootless Podman のコンテナは lingering が無いとログアウトで落ちるため、常時稼働(§3.5.3)の前提となる。自動起動は各ユニットの `[Install] WantedBy=default.target` が担うので、**生成されたユニットに `systemctl --user enable` は行わない**(生成ユニットは enable の対象外であり、実行すると失敗する)。

### 3.4 待受

**公開 VM で外から受けるのは gateway だけである。** frontend(3000)と backend(8000)はホストに公開せず、gateway から Podman ネットワーク経由(例 `http://syllabel-backend:8000`)で参照する。

**DGX Spark 上のコンテナはすべて loopback で待ち受け、本プロジェクトは新たな待受を設けない。** ホスト外から届く経路は、教員側が運用する中継とトークンゲートウェイに限られる(§3.4.1、§3.4.3、§3.4.4)。postgres-clean には本プロジェクトから触れない。

#### 3.4.1 教員側の中継

DGX Spark の loopback で待ち受ける vllm と api-clean へは、教員側が設けた中継を通じてトークンゲートウェイが届く。**中継は本プロジェクトが管理しない**ため、設定の変更・停止は教員側の判断による。設定は運用メモに置く。

**backend は中継を直接使わず、必ずトークンゲートウェイを経由する。** 中継はトークンゲートウェイのために設けられたものであり、本プロジェクトが直接利用する前提のものではない。

#### 3.4.2 backend を公開 VM に置く理由

`/api/timetable/*` と `/api/chat/*` は backend が担うため、**gateway から backend へ到達できなければサービスは成立しない。** 時間割の組み立て(§7.2)・履修要項のマージ(§4.4.3)・要件充足判定(§4.4.5)・アシスタントのプロンプトの組み立て(§7.3.1)はいずれも backend 側にあり、クライアントからは行えない。

backend を DGX Spark に置くと、この必須の経路がホストを跨ぐ。DGX Spark 上のコンテナは loopback で待ち受けるため(§3.4)、gateway から届かせるには**ホスト外向けの口を新たに設けるか、公開 VM 側からトンネルを張る**ことになる。前者は学生プロファイルを受ける口を DGX Spark の外へ開けることになり、後者はサービスの根幹の経路がトンネルの生存に依存する(切れれば提案もチャットも全面停止する)。

**backend を公開 VM に置けば、gateway → backend が同一ホスト内に収まり、この判断自体が不要になる。** ローカル LLM へはトークンゲートウェイを経由するため(§3.4.3)、**backend がどちらのホストにあっても LLM への経路は変わらない**。

公開 VM に置くことで、**学生プロファイルを扱う処理(gateway・backend)とブラウザ内処理が、公開 VM とブラウザに収まる**。要件§3.1 の「学内で完結させる」は、公開 VM と DGX Spark の2台で担保する(§3.1)。

#### 3.4.3 vllm への到達経路(トークンゲートウェイ)

**backend は教員側のトークンゲートウェイ経由で vllm を呼ぶ**(★1)。HTTPS で、発行されたトークンを `Authorization: Bearer` で送る。API の詳細は §6.3。

この経路の性質を次のとおり前提とする。

| 事項 | 性質 |
|---|---|
| **ストリーミング** | 中継を越えて逐次到達する(バッファリングされない)。思考は本文とは別のフィールドで流れる(§6.3.1) |
| **リクエスト単位の推論設定** | `chat_template_kwargs` がそのまま透過する(§6.3.1) |
| **同時実行** | **同一トークンで生成が進行中の場合、後続は `503 busy` で即座に拒否される**(待たされない)。同時に成立するのは1トークンあたり1リクエストである。**制約はトークン単位である** |
| **モデル名の指定** | 接続先ごとに1つのモデル名が固定されており、**本文の `model` がそれと違えば `400 model_mismatch` で弾かれる**(期待値が応答に入る)。PydanticAI は常に `model` を送る(§6.3) |
| **宛先とモデルの分離** | ゲートウェイの宛先は**モデル名を含まない**。したがって **vllm のモデルを差し替えてもトークンの再発行は不要**である(§3.4.3.1) |
| **トークンの有効期間** | 有効期限がある。期限切れ・失効は `401` となり全機能が停止する(§6.3、§13) |

**制約が3つ、設計に影響する。**

1. **同時実行数がトークン数で決まる。** 時間割のアシスタントは1回の応答に1分前後かかる(§7.3)ため、1トークンのままでは、その間の他の利用者がすべて `503` になる。トークンを複数発行すれば同時に成立する数は増えるが、発行数は教員側の流量制御に関わるため、**本数を含めて所有者の判断による**(§13)
2. **利用ログが100日間保存される。** プロンプトと応答が記録されるため、プロンプトに載せる学生データを要件§5.5 の範囲に限る(要件§5.5、§9、§7.3.1)。**★2(api-clean)もトークンを発行して使うため、同じく100日間記録される。** 流れるのは科目の検索条件と結果で、学生プロファイルは含まない(§6.2、§9.1)
3. **モデル名を3箇所で一致させる必要がある。** 下記 §3.4.3.1 による

##### 3.4.3.1 モデル名の一致

**backend・ゲートウェイ・vllm の3箇所が同じモデル名を持っていなければ、経路は通らない。** モデルを差し替えるときは3つを揃えて動かす。

| 箇所 | 設定 | 不一致のときの症状 |
|---|---|---|
| backend | `LLM_MODEL_ID`(環境変数。§6.3) | — |
| トークンゲートウェイ | 接続先ごとに固定されたモデル名 | **`400 model_mismatch`**(期待値が応答に入る) |
| vllm | `--served-model-name`(§4.3) | **`404`** |

症状で切り分けられる。`400` ならゲートウェイまでは届いており backend 側の設定ずれ、`404` ならゲートウェイは通って vllm 側とずれている。**トークンはモデル名に紐づかない**ため、この作業で再発行は要らない。

#### 3.4.4 シラバスデータ層の配置と api-clean への到達経路

**api-clean・postgres-clean は DGX Spark に置き、公開 VM の backend からはトークンゲートウェイ経由で到達する**(★2)。★1(vllm)と同じ機構であり、backend から見れば base_url とトークンを環境変数で与えて HTTP で叩く同じ形になる。

##### DGX Spark に置く理由

1. **役割の分離。** DGX Spark は「計算サーバ(vllm)＋ DB サーバ(シラバス)」とし、本プロジェクト固有の処理は公開 VM に集約する
2. **公開 VM の資源が足りない。** 公開 VM はメモリが小さく、postgres-clean と api-clean を常駐させると、`next build` のたびに他のコンテナを止めることになる(§13)
3. **シラバスバックエンドは他の担当が運用する資産である。** DGX Spark 上のスタックをそのまま使えば、再構築・データ投入・移設の合意がいずれも不要になる(§1.1.1、§3.5.3)

##### トークンゲートウェイに載せる理由

api-clean は無認証であり、本サービスが使わない口(任意の SELECT を実行できる `POST /sql`)も持つ。**トークンゲートウェイに載せれば、トークンによる認証が前段に入り、かつゲートが通すパスを本サービスが使う3つに限れる。** DGX Spark に本プロジェクト固有のものを置かずに済む点でも ★1 と揃う。

| パス | 認証 | 用途 |
|---|---|---|
| `GET /syllabi` | 要 | 検索(§6.2) |
| `GET /syllabi/{code}` | 要 | 詳細(§6.2) |
| `GET /masters` | 要 | 値マスタ(§6.2) |
| `GET /healthz` | 不要 | 死活監視 |
| **上記以外(`POST /sql` を含む)** | — | **拒否** |

##### 障害時の挙動

**api-clean へ到達できないと、シラバス参照を伴う機能がすべて失敗する。** 影響範囲は次のとおりで、いずれも学生には一時的な不調として提示する。

| 機能 | 影響 |
|---|---|
| シラバス検索・詳細(§6.1 の `/api/syllabi`) | 失敗する |
| チャットの tool calling(§6.2) | ツール呼び出しが失敗し、モデルが根拠を得られない |
| 時間割の組み立て(§7.2) | **候補がゼロになる。** 開講曜日・時限を突合できない科目は候補から外す規定(§7.2.1 手順4)のため、api-clean が全滅すると組み立てが成立しない(開講クラスを持っている30分のあいだ(§7.2.1)は組める) |

**切断中に時間割を「候補なし」として返すと、学生には正常な応答と区別がつかない。** 到達不能を検知して明示的に失敗させる(§13)。

**シラバスバックエンドのデータ再投入中も同じ症状になる。** 再投入は api-clean と postgres-clean を作り直すため、**事前の周知を要する**(§3.5.3)。

##### 経路の性質

| 事項 | 内容 |
|---|---|
| トークン | ★1 とは**別に発行する** |
| **同時実行の制限** | **★2 には掛からない。** ゲートウェイの排他は生成系のパスに限られ、参照系は対象外である。★1 の生成と ★2 の参照は競合しない |
| 利用ログ | ★2 も100日間記録される(トークンを発行して使うため)。流れるのは検索条件と結果で、学生プロファイルは含まない(§9.1) |
| レイテンシ | 開講年度ぶんの開講クラスの取得(§7.2.1、千件規模)がホストを跨ぐ。backend は結果を30分持つ。持っていないときの1回目が `http_timeout`(既定 30 秒)で足りるかを実測する(§13) |

### 3.5 アクセス制御

#### 3.5.1 公開経路

**frontend は学外から HTTPS で到達できる。** 公開 URL は §3.5.2 のとおり `/syllabel` 配下のサブパスである。

```
学生ブラウザ ──HTTPS──> 公開入口(教員側。TLS 終端)
                          ↓
               公開 VM の gateway(Caddy)
                          ├──── frontend :3000
                          └──── backend :8000       同一 VM 内(§3.4.2)
                                     │
                                     └──HTTPS──> トークンゲートウェイ(教員側) ─┬─> DGX Spark の vllm      ★1
                                                                                └─> DGX Spark の api-clean ★2
```

**★1・★2 はいずれも backend からトークンゲートウェイへ向かう通信であり、学生のブラウザは使わない。** ブラウザが触れるのは `/syllabel` 配下だけである(§3.5.2)。

TLS 終端と証明書の管理は公開入口が担う。公開 VM の gateway はその後段にあり、HTTP で受ける。公開入口は他のサービスと共用で所有者が管理するため、入口側の設定(パスの書き換えなど)はこちらから変えない。入口が書き換えて渡すパスは公開 VM の gateway が `/syllabel` に戻して受ける(§3.2.1)。ブラウザから見える URL は一貫して `/syllabel` である。

**死活確認には `/syllabel/api/healthz` を用いる。** gateway が `/syllabel` を剥がすため、backend には `/api/healthz` として届く。backend はルート直下の `/healthz` も持つが、`/syllabel/*` は frontend へ振り分けられるため、**公開経路からは到達しない**。

#### 3.5.2 URL 構造

公開 URL は **`/syllabel` 配下のサブパス配信**とする。frontend は `next.config.ts` の `basePath: "/syllabel"` でビルドされており、gateway の振り分けもこれに合わせている(§3.2.1)。パスの名はサービス名 `Syllabel` から採る。

| 公開パス | 転送先 | 備考 |
|---|---|---|
| `/syllabel`、`/syllabel/*` | frontend | Next.js が `basePath` で受ける |
| `/syllabel/api/*` | backend | gateway が `/syllabel` を剥がし、backend には `/api/*` として届く |
| 上記以外 | 404 | gateway が返す |

**内部 API の公開パスは `/syllabel/api/*` であり、`/api/*` ではない。** Next.js の `basePath` はページとアセットの生成先を変えるだけで、アプリケーションコードが呼ぶ `fetch()` のパスには前置されない。したがって **frontend は自身の呼び出し先に `/syllabel` を明示的に含める必要がある**(§6.1)。

`/` をルート配信へ寄せる案は採らない。公開入口は他のサービスと共用されており、ルートを本プロジェクトが占有できないためである。

#### 3.5.3 権限と責任分界

| 範囲 | 権限 | 変更方法 |
|---|---|---|
| 公開入口(TLS・振り分け)と、公開 VM を載せるホスト | 教員側 | 依頼 |
| 公開 VM のユーザ権限内(Podman コンテナ、Caddyfile、イメージ) | 開発チーム | 直接 |
| 公開 VM の root 権限(OS 更新、1024 未満のポート、ファイアウォール) | **無し** | 依頼 |
| DGX Spark のコンテナと compose | 開発チーム | 直接。ただし **vllm を止めるとトークンゲートウェイ経由の呼び出しが `502 upstream_unavailable` になる**(§6.3) |
| DGX Spark のホスト外への口(中継の設置、ポートの開放、ファイアウォール) | 所有者(アドバイザー教員) | 依頼。**本構成では新たな口を設けない**(§3.4.2、§3.4.4) |
| トークンゲートウェイ(トークンの発行数、利用ログ、中継先) | アドバイザー教員 | 依頼。**発行本数は流量制御に関わるため判断を仰ぐ**(§3.4.3) |
| シラバスバックエンド(api-clean / postgres-clean)のコードとデータ | シラバスバックエンド担当([ProjectResearch2026/syllabus_backend](https://github.com/ProjectResearch2026/syllabus_backend)) | **本リポジトリでは改修しない**(§1.1.1)。必要な改修は当該リポジトリへ起票する。データの再投入は事前に周知する |

- **学生がサービスを利用するのに SSH は不要**(学生はブラウザから HTTPS でアクセスするのみ)
- リクエスト/レスポンスのボディはログに記録しない(要件§5.5。詳細は§9)
- 龍谷祭期間を含む常時稼働が前提となるため、公開 VM のコンテナは systemd ユーザユニット化と lingering の有効化を要する(§3.3)

#### 3.5.4 公開に向けて必要なもの

公開ホスト名・TLS 証明書・公開入口から公開 VM の gateway への振り分け、および学外公開に要る学内の手続きは、教員側が整える(状況は運用メモ)。

本プロジェクトの側で公開までに整えるものは次のとおりである。

1. gateway 経由での SSE 中継の確認(§13 の読み取りタイムアウトと併せて)
2. **★1 の同時実行の扱いの決定**(§3.4.3)— トークンの発行本数

学生データの処理を学外へ出さないこと(要件§3.1)は、アクセス経路を学外に公開することとは別概念であり、引き続き担保する(処理はブラウザ・公開 VM・DGX Spark で完結し、いずれも学内にあり、学外クラウドへ送信しない)。
