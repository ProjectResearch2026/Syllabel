## 3. デプロイ構成

> 本節は 2026-09-09 時点の実機構成を記す。ホスト名・IP アドレス・アカウント名などの環境固有の値は、本書が公開される可能性を考慮して記載しない。実値は運用メモを参照する。未確定の事項は §13 に送る。

### 3.1 配置先

配置は2ホストに分かれ、GW 側はさらにホストとゲスト VM の2層になる。

| 層 | 実体 | 管理 | 稼働させるもの |
|---|---|---|---|
| **GW ホスト** | アドバイザー教員研究室の Web サーバ(x86_64 デスクトップ機、学内アドレスと FQDN を保持) | **教員側** | libvirt(KVM)と Incus。公開入口の Caddy(TLS 終端)を Incus コンテナで、本プロジェクトの公開 VM を含む複数の VM を libvirt で動かす |
| **公開 VM** | GW ホスト上の libvirt ゲスト(Ubuntu 24.04 LTS / x86_64、libvirt NAT 配下の私設アドレス) | **開発チーム(root 権限なし)** | 本プロジェクトの gateway(Caddy)と frontend |
| **DGX Spark** | 学内。**DGX OS 7.5.0**(Ubuntu 24.04 LTS ベース、カーネル `6.17.0-1021-nvidia`、**arm64**、GB10) | 開発チーム(sudo あり) | backend、vllm、api-clean、postgres-clean |

**開発チームが構成を変更できるのは、公開 VM のユーザ権限内と DGX Spark の2つに限られる。** GW ホスト側(公開アドレスでの受け、DNAT、TLS 終端、公開入口の Incus コンテナ、libvirt、ファイアウォール)は教員側の管理下にあり、開発チームは sudo を持たない。公開 VM で与えられている sudo も教員側が用意した特定スクリプト1本の実行に限られ、**一般の root 権限は無い**。したがって、公開経路そのものに関わる設定変更と、VM の OS レベルの操作は**依頼**によって行う。


GW ホストには本プロジェクト以外の VM(トークンゲートウェイ用途と見られるもの、および別用途のもの)と Incus コンテナが同居する。本プロジェクトが占有するのは公開 VM 1台である。

学生データを処理する一連の機能は、ブラウザと DGX Spark 上で完結する(要件§3.1)。公開 VM は画面の配信と通信の中継のみを担い、成績データの処理・永続保存・記録を行わない。

### 3.2 コンテナ構成

**2ホストでコンテナ基盤とアーキテクチャが異なる。** 同一のイメージを両ホストで使い回すことはできない。

| | 公開 VM | DGX Spark |
|---|---|---|
| 基盤 | **rootless Podman**(docker 未導入) | **Docker 29.x** |
| アーキテクチャ | x86_64 | **arm64(aarch64)** |
| 定義 | コンテナを個別に起動(compose ファイルなし) | `docker-compose.yml`(backend + vllm)、既存の `docker-compose.clean.yml`(api-clean + postgres-clean) |
| 特権ポート | **1024 未満を待ち受けられない**(rootless のため)。gateway は 8080 を使う | 制約なし(ただし全サービスを loopback バインドとする。§3.4) |

`vllm/vllm-openai` は DGX 側で **arm64 イメージ**として取得される。frontend のイメージ(`frontend/Containerfile`)は公開 VM 上で x86_64 としてビルドする。イメージのアーキテクチャがホストごとに異なるため、一方でビルドしたイメージを他方へ持ち込む運用は取らない。

compose ファイルは DGX 側の `docker-compose.yml` のみが存在する。GW 側はコンテナを個別に起動しており、定義方法は §13 の未確定事項とする。

#### 3.2.1 公開 VM

rootless Podman で2つのコンテナを、Podman ネットワーク上で名前解決させて動かす。

| コンテナ | イメージ | 公開 | 役割 |
|---|---|---|---|
| gateway | `caddy:alpine` | `0.0.0.0:8080` | 振り分け。`/pr-2026/api/*` を backend、`/pr-2026`・`/pr-2026/*` を frontend へ |
| frontend | 自ビルド(`frontend/Containerfile`) | なし(ネットワーク経由でのみ到達) | Next.js standalone(`PORT=3000`、`NODE_ENV=production`) |

稼働中の Caddyfile は VM 上のディレクトリを読み取り専用で bind mount している(パスは運用メモ)。

```caddyfile
:8080 {
      # /pr-2026/api/* → バックエンド(/pr-2026 だけ剥がす)
      handle /pr-2026/api/* {
              uri strip_prefix /pr-2026
              reverse_proxy {$BACKEND_ADDR}
      }

      # Next.js は basePath 使用時に末尾スラッシュ無しを正規とするため、
      # /pr-2026 と /pr-2026/* の両方をフロントへ渡す
      @app path /pr-2026 /pr-2026/*
      handle @app {
              reverse_proxy pr2026-frontend:3000
      }

      handle {
              respond "not found" 404
      }
}
```

`BACKEND_ADDR` は環境ファイルで DGX Spark の `<アドレス>:8000` を与える。この振り分けが §3.5.2 の URL 構造を決めている。

**この Caddyfile には SSE 向けの設定が入っていない。** Caddy の `reverse_proxy` は既定でレスポンスをバッファリングしないため逐次配信自体は通るが、長時間の応答に対する読み取りタイムアウトは明示しておくべきである(チャット系は1回のモデル呼び出しに100秒超かかることがある。§13)。

**frontend コンテナに backend の宛先を渡す環境変数が無い。** 現状のコンテナが持つのは `PORT` / `HOSTNAME` / `NODE_ENV` などの既定値のみであり、サーバ側描画から backend を引く経路(§6.1)は宛先を解決できずに失敗する。実際、稼働中の frontend は `127.0.0.1:8000` への接続拒否をログに出している。frontend 側の修正と併せて解消する(§13)。

#### 3.2.2 DGX Spark

リポジトリ直下の `docker-compose.yml` が backend と vllm を定義する(配置先は運用メモ)。既存のシラバスバックエンド(`docker-compose.clean.yml`)には一切手を加えない。

ネットワークは以下で成立する。

- **app-net** — backend ↔ vllm。`docker-compose.yml` が自動作成
- **syllabus-clean-net**(既存) — backend が api-clean を呼ぶための共有ネットワーク。`external: true` で参照

backend のみ両方に参加し、橋渡しを担う。**backend → vllm と backend → api-clean はいずれも DGX Spark 内のコンテナネットワークで閉じており、ホストをまたがない。** ホストをまたぐ通信は gateway → backend の1本だけである。

vllm の起動オプションは以下とする。

```yaml
    command:
      - --model
      - /models                       # 事前DLしたローカルパス。起動時に HF からは取得しない
      - --served-model-name           # §6.3 の OpenAIChatModel(model=...) と一致させ 404 を防ぐ
      - qwen3.6-27b-fp8
      - --language-model-only         # テキスト専用。ビジョンを省きメモリを KV cache に回す
      - --reasoning-parser            # 思考モデルのため必須。無いと思考が本文に漏れ構造化出力が壊れる
      - qwen3
      - --enable-auto-tool-choice
      - --tool-call-parser            # hermes ではなく qwen3_coder(公式指定の出力書式)
      - qwen3_coder
      - --max-model-len               # 既定262144はメモリ過大。最低128K推奨に沿い131072。OOM時さらに削減
      - "131072"
      - --gpu-memory-utilization      # 同一GPUを共有する他ワークロードがある前提。§3.2.3
      - "0.4"
      # 単GPU構成のため tensor-parallel は指定しない(=1)
```

モデルはイメージ内に持たず、ホスト上に**事前DL**したものを読み取り専用で bind mount する。コンテナ起動時に HuggingFace から取得しないため、Docker 名前付きボリュームは使わない。

#### 3.2.3 GPU の共有状況

GB10 の統合メモリ上で **vLLM のエンジンが2基動いている**(2026-09-09 実測)。

| プロセス | 用途 | GPU メモリ |
|---|---|---|
| `VLLM::EngineCore` | 既存の qwen-ocr(本プロジェクト外) | 約 55 GB |
| `VLLM::EngineCore` | 本プロジェクトの vllm | 約 47 GB |

`--gpu-memory-utilization 0.4` はこの同居を前提とした値である。本プロジェクトが取り分を増やすと qwen-ocr 側に影響するため、変更は単独で判断しない。

### 3.3 起動順序

0. (初回のみ) vllm 用モデルを事前DL(§4.3)
1. (DGX Spark)シラバスバックエンド側で `bin/init_clean.sh`(初回のみデータ投入込み)、以降は `docker compose -f docker-compose.clean.yml up -d`
2. (DGX Spark)`docker compose up -d`(backend + vllm。vllm の healthcheck 通過を待って backend が起動する)
3. (公開 VM)frontend と gateway のコンテナを起動する

公開 VM 側は DGX Spark 側の起動完了を待たずに立ち上がるが、backend が未起動の間は API 呼び出しが失敗するため、上記の順序で起動する。

**公開 VM のコンテナは現状ユーザセッションに紐づいて動いている。** rootless Podman のコンテナは、lingering を有効にした systemd ユーザユニットにしないと、ログアウトやホスト再起動で落ちる。常時稼働(§3.5.3)の前提としてユニット化が要る(§13)。

### 3.4 ポート割り当てと待受状況

**GW ホスト**(教員側管理)

| ポート | 状態(2026-09-09) | 備考 |
|---|---|---|
| 22 | 待受あり | 管理用 SSH |
| 80 / 443 | ホスト自身は待ち受けず、**DNAT で公開入口の Incus コンテナへ転送** | 転送された通信はホストへローカル配送されないため `ss` には現れない(§3.5.1) |

**公開 VM**

| サービス | コンテナ内 | ホスト公開 |
|---|---|---|
| gateway(Caddy) | 8080 | `0.0.0.0:8080` |
| frontend | 3000 | 公開しない(Podman ネットワーク経由で gateway から参照) |

**DGX Spark**

| サービス | コンテナ内 | ホスト公開 | ホスト外からの到達 |
|---|---|---|---|
| backend | 8000 | `127.0.0.1:8000` | **不可** |
| vllm | 8000 | `127.0.0.1:8001` | **socat 経由で可**(§3.4.1) |
| api-clean(既存) | 5000 | `127.0.0.1:5050` | 不可 |
| postgres-clean(既存) | 5432 | `127.0.0.1:5433` | 不可 |

**DGX Spark 上の本プロジェクトのコンテナは、すべてホストの loopback にのみバインドしている。** 同一ホスト内のコンテナ間通信はホスト公開ポートではなく Docker network 経由(サービス名:コンテナ内ポート、例 `http://vllm:8000`、`http://api-clean:5000`)で行うため、ホスト公開はデバッグ用の位置づけである。

#### 3.4.1 socat フォワーダ層

DGX Spark には、**loopback にバインドされた vLLM を学内アドレスへ中継する root 所有の socat プロセス**が systemd サービスとして常駐している(2026-09-08 設置。本プロジェクトの管理外)。

| 待受 | 転送先 | 送信元制限 | 用途 |
|---|---|---|---|
| `<学内アドレス>:8001` | `127.0.0.1:8001` | **GW ホストの1アドレスのみ**(socat の `range` オプション) | 本プロジェクトの Qwen3.6 |
| `<学内アドレス>:11437` | `127.0.0.1:11435` | 同上 | 既存の qwen-ocr |
| `0.0.0.0:11436` | `127.0.0.1:11435` | **なし(学内全体)** | 既存の qwen-ocr(本プロジェクト外、2026-04 設置) |

**したがって、コンテナのバインドだけを見て「外部から到達しない」と判断してはならない。** 実態は「コンテナは loopback、その手前で送信元を1アドレスに絞った中継が外向きに開いている」である。この中継は本プロジェクトが管理しないため、設定の変更・停止は教員側の判断による。

公開 VM から DGX Spark の vLLM に到達できるのは、VM の通信が GW ホストのアドレスへ SNAT されるためである(libvirt NAT)。socat の送信元制限は GW ホストのアドレスを許可しており、VM はその背後にいる。

**vLLM 自体に認証は設定されていない。** トークンなしの `/v1/chat/completions` が 200 を返すことを実測で確認した(2026-09-09)。この経路のアクセス制御は socat の送信元制限のみで成立している。

#### 3.4.2 backend への到達経路(未成立)

`POST /api/proposal` と `/api/chat/*` は backend が担うため、**gateway から backend へ到達できなければサービスは成立しない。** LLM 推論もシラバス参照も backend が DGX Spark の内部ネットワークで行うため(§3.2.2)、Qwen の口だけが開いていても代替にはならない。提案プロンプトの組み立て(§7.2.1)・履修要項のマージ(§4.4.3)・要件充足判定(§4.4.5)・構造化出力の検証(§5.3)はいずれも backend 側にあり、クライアントからは行えない。

2026-08 の時点では、DGX Spark の 8000 を学内に開放し、公開 VM の Caddy から `<アドレス>:8000` を叩く構成で疎通していた(§3.2.1 の `BACKEND_ADDR` はその名残である)。**その後、認証なしのポートを学内全体に開放する方針が採られないこととなり、8000 は loopback バインドに戻された。**

現時点で backend への到達経路は無い。**これが唯一の欠落である**ことは実測で確認できている(§3.5.1。学外からの `/pr-2026/api/*` が 404 ではなく 502 を返す)。

§3.4.1 が示すとおり、**送信元を GW ホスト1アドレスに限定した中継**という方式は同じホスト上で既に採用実績があるため、backend にも同じ方式を適用することを想定する。この場合、学内全体への開放は生じない。採否は §13 の未確定事項とする。

### 3.5 アクセス制御

#### 3.5.1 公開経路

**frontend は学外から HTTPS で到達できる**(2026-09-09 に外部から確認)。公開 URL は §3.5.2 のとおり `/pr-2026` 配下のサブパスである(実 URL は運用メモ)。

```
学生ブラウザ ──HTTPS──> GW ホストの公開アドレス :443
                          │ DNAT(ホスト自身は待ち受けない)
                          ↓
               Incus コンテナ(Caddy)          TLS 終端・振り分け
                          ↓
               公開 VM :8080(Caddy)
                          ├──✓── frontend :3000
                          └──✗── DGX backend :8000   到達不可(§3.4.2)
```

TLS 終端と証明書の管理は GW ホスト側の Incus コンテナが担う。公開 VM の gateway はその後段にあり、HTTP で受ける。

**GW ホストの `ss` に 80/443 は現れない。** DNAT された通信は転送されるだけでホストへローカル配送されないためである。同じ理由で、公開 VM から GW ホストの公開アドレスへ向けた通信は DNAT の対象とならず到達しない。**外部からの到達性を公開 VM の内側から検証することはできない。**

**欠けているのは backend への到達経路だけである**(§3.4.2)。学外から `/pr-2026/api/healthz` を叩くと **502** が返る(2026-09-09 実測)。404 ではなく 502 であることは、**公開入口から公開 VM の gateway までの振り分けが `/pr-2026/api/*` について正しく成立しており、失敗しているのが gateway → backend の1ホップだけである**ことを示す。`/pr-2026` 配下の画面は表示されるが、`/pr-2026/api/*` を必要とする機能(履修提案・提案チャット・シラバスチャット・シラバス検索)は動作しない。

#### 3.5.2 URL 構造

公開 URL は **`/pr-2026` 配下のサブパス配信**とする。frontend は `next.config.ts` の `basePath: "/pr-2026"` でビルドされており、gateway の振り分けもこれに合わせている(§3.2.1)。

| 公開パス | 転送先 | 備考 |
|---|---|---|
| `/pr-2026`、`/pr-2026/*` | frontend | Next.js が `basePath` で受ける |
| `/pr-2026/api/*` | backend | gateway が `/pr-2026` を剥がし、backend には `/api/*` として届く |
| 上記以外 | 404 | gateway が返す |

**内部 API の公開パスは `/pr-2026/api/*` であり、`/api/*` ではない。** Next.js の `basePath` はページとアセットの生成先を変えるだけで、アプリケーションコードが呼ぶ `fetch()` のパスには前置されない。したがって **frontend は自身の呼び出し先に `/pr-2026` を明示的に含める必要がある**(§6.1)。

`/` をルート配信へ寄せる案は採らない。GW ホストは他用途と共用されており、ルートを本プロジェクトが占有できないためである。

#### 3.5.3 権限と責任分界

| 範囲 | 権限 | 変更方法 |
|---|---|---|
| GW ホスト(80/443、TLS、VM フォワード、ファイアウォール、Incus / libvirt) | 教員側 | 依頼 |
| 公開 VM のユーザ権限内(Podman コンテナ、Caddyfile、frontend イメージ) | 開発チーム | 直接 |
| 公開 VM の root 権限(OS 更新、1024 未満のポート、ufw) | **無し**(特定スクリプト1本の実行のみ) | 依頼 |
| DGX Spark(コンテナ、compose、socat、ホストのファイアウォール) | 開発チーム(sudo あり) | 直接。ただし公開範囲に関わる変更は方針確認を要する |

- **学生がサービスを利用するのに SSH は不要**(学生はブラウザから HTTPS でアクセスするのみ)。SSH は運用者側の管理経路である
- 公開 VM の外向き通信を本プロジェクトの宛先に限定する方針は、root 権限が無いため VM 内では実施できない。必要であれば GW ホスト側での実施を依頼する
- リクエスト/レスポンスのボディはログに記録しない(要件§5.5。詳細は§9)
- 龍谷祭期間を含む常時稼働が前提となるため、公開 VM のコンテナは systemd ユーザユニット化と lingering の有効化を要する(§3.3)

#### 3.5.4 公開に向けて必要なもの

RINS への申請は**外部公開のためのファイアウォール制限解除申請1件**であり、アドバイザー教員が代行する。申請対象は GW ホストである。

**済んでいること**(2026-09-09 時点)

- 公開ホスト名の DNS 登録と、GW ホスト公開アドレスから公開入口コンテナへの転送
- TLS 証明書の取得と終端
- 公開入口から公開 VM の gateway、frontend までの振り分け
- 学外からの HTTPS 到達(外部から確認済み)

**残っていること**

1. **backend への到達経路の確保**(§3.4.2)— これが無い間、`/pr-2026/api/*` を必要とする機能は動作しない
2. backend 到達後の、gateway 経由での SSE 中継の確認
3. RINS への申請状況の確認(下表。学外から到達できている以上、必要な手当ては済んでいる可能性がある。§13)

**申請の内容**

| 項目 | 内容 |
|---|---|
| 対象ホスト | GW ホスト(アドバイザー教員研究室) |
| 開放ポート | 443/tcp(必須)、80/tcp(証明書の HTTP-01 認証および HTTPS へのリダイレクトに使用。可否は要確認) |
| 利用目的 | 履修登録支援AIチャットボットの公開ゲートウェイ。履修提案ロジックと LLM は DGX Spark 側 |
| 公開範囲 | 学外を含む(在学生が自宅からも利用するため) |
| 実務管理担当 | 運用メモを参照 |

学生データの処理を学外へ出さないこと(要件§3.1)は、アクセス経路を学外に公開することとは別概念であり、引き続き担保する(処理は DGX Spark とブラウザで完結し、学外クラウドへ送信しない)。
