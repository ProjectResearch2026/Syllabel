## 3. デプロイ構成

> 本節は 2026-09-09 時点の実機構成を記す。ホスト名・IP アドレス・アカウント名などの環境固有の値は、本書が公開される可能性を考慮して記載しない。実値は運用メモを参照する。未確定の事項は §13 に送る。

### 3.1 配置先

配置は2ホストに分かれ、GW 側はさらにホストとゲスト VM の2層になる。

| 層 | 実体 | 所有 | 運用権限 | 稼働させるもの |
|---|---|---|---|---|
| **GW ホスト** | アドバイザー教員研究室の Web サーバ(x86_64 デスクトップ機、学内アドレスと FQDN を保持) | アドバイザー教員 | **教員側** | libvirt(KVM)と Incus。公開入口の Caddy(TLS 終端)を Incus コンテナで、本プロジェクトの公開 VM を含む複数の VM を libvirt で動かす |
| **公開 VM** | GW ホスト上の libvirt ゲスト(Ubuntu 24.04 LTS / x86_64、libvirt NAT 配下の私設アドレス) | アドバイザー教員 | **開発チーム(root 権限なし)** | 本プロジェクトの gateway(Caddy)、frontend、**backend**、および api-clean へ向かう **ssh-tunnel** |
| **DGX Spark** | 学内。**DGX OS 7.5.0**(Ubuntu 24.04 LTS ベース、カーネル `6.17.0-1021-nvidia`、**arm64**、GB10) | アドバイザー教員 | 開発チーム(sudo あり) | **vllm、api-clean、postgres-clean** |

**配置は2度動いている。** 当初は backend・api-clean・postgres-clean を DGX Spark 側に置く計画だったが、GW 側から DGX Spark の backend へ到達する経路が確保できず、2026-09-13 に3つとも公開 VM 側へ移した(§3.4.2)。その後、公開 VM の資源が5コンテナの常時稼働に足りないこと、および既存スタックの移設を伴わずに済むことから、2026-09-14 に **api-clean・postgres-clean を DGX Spark へ戻した**(§3.4.4)。backend は公開 VM に留まる。

**公開 VM に置くのは、本プロジェクトが新規開発した要素(gateway / frontend / backend)に限る。** 既存資産であるシラバスバックエンドは DGX Spark 上の既存スタックをそのまま使い、移設しない。

**本プロジェクトが DGX Spark に新たな待受を設けることはない。** vllm・api-clean・postgres-clean はいずれもホストの loopback にバインドし、ホスト外から届く経路は、教員側が運用する既存の中継(★1。§3.4.1)と、公開 VM 側から張る SSH ローカルフォワード(★2。§3.4.4)に限られる。★2 が使うのは DGX Spark の SSH(22)であり、新規の口ではない。

**2ホストとも所有者はアドバイザー教員であり、開発チームは貸与を受けて運用している。** 運用権限を持つことは、構成を単独で決めてよいことを意味しない。とくにホスト外へ口を開ける変更(中継の設置、ポートの開放、ホストのファイアウォール)は、権限の有無にかかわらず所有者の判断による(§3.5.3)。

**開発チームが構成を変更できるのは、公開 VM のユーザ権限内と DGX Spark の2つに限られる。** GW ホスト側(公開アドレスでの受け、DNAT、TLS 終端、公開入口の Incus コンテナ、libvirt、ファイアウォール)は教員側の管理下にあり、開発チームは sudo を持たない。公開 VM で与えられている sudo も教員側が用意した特定スクリプト1本の実行に限られ、**一般の root 権限は無い**。したがって、公開経路そのものに関わる設定変更と、VM の OS レベルの操作は**依頼**によって行う。

GW ホストには本プロジェクト以外の VM(トークンゲートウェイ用途と見られるもの、および別用途のもの)と Incus コンテナが同居する。本プロジェクトが占有するのは公開 VM 1台である。

学生データを処理する一連の機能は、ブラウザ・公開 VM・DGX Spark で完結する(要件§3.1)。公開 VM とブラウザが学生プロファイルを扱い、DGX Spark は LLM 推論とシラバス参照を担う。**DGX Spark 側の api-clean へ学生プロファイルを渡すことはない**(送るのは科目の検索条件のみ。§6.2)。いずれのホストも学内にあり、成績データが学外へ出ることはない。

### 3.2 コンテナ構成

**2ホストでコンテナ基盤とアーキテクチャが異なる。** 同一のイメージを両ホストで使い回すことはできない。

| | 公開 VM | DGX Spark |
|---|---|---|
| 基盤 | **rootless Podman**(docker 未導入) | **Docker 29.x** |
| アーキテクチャ | x86_64 | **arm64(aarch64)** |
| 定義 | コンテナを個別に起動(compose ファイルなし。§13) | `docker-compose.yml`(vllm)と `docker-compose.clean.yml`(既存スタック) |
| 特権ポート | **1024 未満を待ち受けられない**(rootless のため)。gateway は 8080 を使う | 制約なし(ただし全コンテナを loopback バインドとする。§3.4) |

`vllm/vllm-openai` は DGX 側で **arm64 イメージ**として取得される。frontend(`frontend/Containerfile`)と backend(`backend/Dockerfile`)のイメージは**公開 VM 上で x86_64 としてビルドする**。イメージのアーキテクチャがホストごとに異なるため、一方でビルドしたイメージを他方へ持ち込む運用は取らない。**DGX 上で arm64 としてビルドしていた backend イメージは流用できない**(§3.3)。

既存のシラバスバックエンド(api-clean / postgres-clean)は **DGX Spark 上の既存スタックをそのまま使う**。2026-09-13 の決定では公開 VM 側へ移設することとしていたが、移設前に方針を改めたため(§3.4.4)、**移設は実施しない**。当該スタックは既存シラバスバックエンド担当の資産であり、構成を変えないことは合意形成の面でも利点となる。公開 VM 側で必要になるのは、api-clean がホスト側に公開している `127.0.0.1:5050` を SSH の転送先に据えることだけである(§3.4.4)。

#### 3.2.1 公開 VM

rootless Podman で4つのコンテナを、Podman ネットワーク上で名前解決させて動かす。

| コンテナ | イメージ | 公開 | 役割 |
|---|---|---|---|
| gateway | `caddy:alpine` | `0.0.0.0:8080` | 振り分け。`/pr-2026/api/*` を backend、`/pr-2026`・`/pr-2026/*` を frontend へ |
| frontend | 自ビルド(`frontend/Containerfile`) | なし(ネットワーク経由でのみ到達) | Next.js standalone(`PORT=3000`、`NODE_ENV=production`) |
| backend | 自ビルド(`backend/Dockerfile`、x86_64) | なし | FastAPI + PydanticAI。トークンゲートウェイ経由で vllm を呼び(§6.3)、ssh-tunnel 経由で api-clean を引く(§3.4.4) |
| ssh-tunnel | 自ビルド(`deploy/ssh-tunnel/Containerfile`。**未作成**) | なし。**ネットワーク別名 `api-clean`、待受は 5000** | DGX Spark の `127.0.0.1:5050` へ SSH ローカルフォワードを張り、api-clean を Podman ネットワーク上に見せる(§3.4.4) |

**backend コンテナは rootless Podman で動く。** `backend/Dockerfile` は `python:3.12-slim` を基に `pip install .` と `uvicorn --port 8000` を行うだけで、GPU・`ipc: host`・特権のいずれも要さず、待受も 1024 以上である。**`USER` による非 root 化を行っていないことが要件である。** 公開 VM のホームには default ACL(`other::---`)が設定されており、コンテナ内の非 root ユーザはホスト上で別 uid にマップされてファイル所有者から見て「その他」に該当するため、イメージ内の実行ファイルすら読めずに起動に失敗する(`frontend/Containerfile` のコメントに同じ理由の記載がある)。rootless Podman ではコンテナ内 root もホスト上の非特権 uid にマップされるため、ホストの root 権限には繋がらない。

**`docker-compose.yml` の backend 定義はそのままでは使えない。** 公開 VM 側へ移すにあたり、次の3点を落とす必要がある。

| compose 上の定義 | 公開 VM で成り立たない理由 | 対応 |
|---|---|---|
| `depends_on: vllm (service_healthy)` | 公開 VM に vllm が居ない | 削除する。backend は起動時に vllm へ接続しない(§3.3)ため影響しない |
| `networks: syllabus-clean-net`(external) | 公開 VM に当該ネットワークが無い | 削除し、api-clean へは ssh-tunnel 経由で到達する(§3.4.4) |
| `ports: 127.0.0.1:8000:8000` | 公開 VM ではホストに公開しない | 削除する。gateway とは Podman ネットワークで通信する |

`curricula/` と `offerings/` の読み取り専用マウントは rootless Podman でもそのまま通る(Ubuntu は AppArmor のため SELinux ラベル `:z` は不要)。ただし**公開 VM 上にリポジトリの clone が要る**。

稼働中の Caddyfile は VM 上のディレクトリを読み取り専用で bind mount している(パスは運用メモ)。

```caddyfile
:8080 {
      # /pr-2026/api/* → バックエンド(/pr-2026 だけ剥がす)
      handle /pr-2026/api/* {
              uri strip_prefix /pr-2026
              reverse_proxy {$BACKEND_ADDR}
      }

      # Next.js は basePath 使用時に末尾スラッシュ無しを正規とするため、
      # /pr-2026 と /pr-2026/* の両方をフロントへ渡す
      @app path /pr-2026 /pr-2026/*
      handle @app {
              reverse_proxy pr2026-frontend:3000
      }

      handle {
              respond "not found" 404
      }
}
```

`BACKEND_ADDR` は環境ファイルで与える。**配置変更後は同一 Podman ネットワーク上の `pr2026-backend:8000` を指す**(従来は DGX Spark の `<アドレス>:8000` を指しており、到達できずに 502 を返していた)。この振り分けが §3.5.2 の URL 構造を決めている。

**この Caddyfile には SSE 向けの設定が入っていない。** Caddy の `reverse_proxy` は既定でレスポンスをバッファリングしないため逐次配信自体は通るが、長時間の応答に対する読み取りタイムアウトは明示しておくべきである(チャット系は1回のモデル呼び出しに100秒超かかることがある。§13)。

**frontend コンテナに backend の宛先を渡す環境変数が無い。** 現状のコンテナが持つのは `PORT` / `HOSTNAME` / `NODE_ENV` などの既定値のみであり、サーバ側描画から backend を引く経路(§6.1)は宛先を解決できずに失敗する。実際、稼働中の frontend は `127.0.0.1:8000` への接続拒否をログに出している。frontend 側の修正と併せて解消する(§13)。

**backend コンテナには、トークンゲートウェイへの接続情報を渡す**(§6.3)。トークンは環境ファイル(パーミッション 600)に置き `--env-file` で与え、イメージには焼き込まない。あわせて、ゲートウェイの FQDN を公開入口コンテナの私設アドレスへ向けるため `--add-host` を与える(理由は §3.4.3)。**api-clean の宛先(`API_CLEAN_BASE_URL`)は既定値 `http://api-clean:5000` のままでよい**。ssh-tunnel コンテナが同名のネットワーク別名を持つためである(§3.4.4)。

#### 3.2.2 DGX Spark

リポジトリ直下の `docker-compose.yml` が **vllm を定義する**(配置先は運用メモ)。**backend の定義はこのファイルから外し、公開 VM 側へ移す**(未実施)。既存のシラバスバックエンドは `docker-compose.clean.yml` により DGX Spark 上でこれまでどおり稼働させる。

| コンテナ | 定義 | ホスト公開 | 役割 |
|---|---|---|---|
| vllm | `docker-compose.yml` | `127.0.0.1:8001` | LLM 推論。教員側の中継経由でトークンゲートウェイから呼ばれる(★1) |
| api-clean(既存) | `docker-compose.clean.yml` | **`127.0.0.1:5050` → コンテナ 5000** | シラバス情報提供 API。公開 VM から SSH ローカルフォワードで引かれる(★2) |
| postgres-clean(既存) | `docker-compose.clean.yml` | **`127.0.0.1:5433` → コンテナ 5432** | シラバス DB。本プロジェクトは直接触らない |

**ホストをまたぐ通信は backend を起点とする2本である**(★1 = backend → vllm、★2 = backend → api-clean)。★1 は教員側のトークンゲートウェイを経由し(§6.3)、★2 は公開 VM 側から張る SSH ローカルフォワードを通る(§3.4.4)。**どちらも DGX Spark にホスト外向けの待受を新設しない。**

**ホスト側の公開はいずれも loopback に限られる。** これはシラバスバックエンド側が CVE-2026-2005 対応の一環として明示的に定めたものであり(当該リポジトリ `docs/clean_security.md`)、本プロジェクトの都合で外さない。**ホスト側のポートはコンテナ内と番号が異なる**(API は 5050→5000、Postgres は 5433→5432)点に注意する。★2 の転送先は `127.0.0.1:5050` である。

**vllm は本プロジェクト以外からも使われている。** 教員側のトークンゲートウェイが中継する先が、この vllm である(2026-09-13 に `GET /v1/models` の応答で確認。`--served-model-name` で与えた `qwen3.6-27b-fp8`、`--model` のパス `/models`、`--max-model-len 131072` がそのまま返る)。また別リポジトリの開発ログ通知も同じ vllm を利用している。**したがって本プロジェクトが `docker compose down` を行うと、トークンゲートウェイの利用者全員のテキストモデルが停止する。** 停止・再起動は事前の周知を要する(§3.5.3)。

vllm の起動オプションは以下とする。

```yaml
    command:
      - --model
      - /models                       # 事前DLしたローカルパス。起動時に HF からは取得しない
      - --served-model-name           # §6.3 の OpenAIChatModel(model=...) と一致させ 404 を防ぐ
      - qwen3.6-27b-fp8
      - --language-model-only         # テキスト専用。ビジョンを省きメモリを KV cache に回す
      - --reasoning-parser            # 思考モデルのため必須。無いと思考が本文に漏れ構造化出力が壊れる
      - qwen3
      - --enable-auto-tool-choice
      - --tool-call-parser            # hermes ではなく qwen3_coder(公式指定の出力書式)
      - qwen3_coder
      - --max-model-len               # 既定262144はメモリ過大。最低128K推奨に沿い131072。OOM時さらに削減
      - "131072"
      - --gpu-memory-utilization      # 同一GPUを共有する他ワークロードがある前提。§3.2.3
      - "0.4"
      # 単GPU構成のため tensor-parallel は指定しない(=1)
```

モデルはイメージ内に持たず、ホスト上に**事前DL**したものを読み取り専用で bind mount する。コンテナ起動時に HuggingFace から取得しないため、Docker 名前付きボリュームは使わない。

#### 3.2.3 GPU の共有状況

GB10 の統合メモリ上で **vLLM のエンジンが2基動いている**(2026-09-09 実測)。

| プロセス | 用途 | GPU メモリ |
|---|---|---|
| `VLLM::EngineCore` | 既存の qwen-ocr(本プロジェクト外) | 約 55 GB |
| `VLLM::EngineCore` | 本プロジェクトの vllm | 約 47 GB |

`--gpu-memory-utilization 0.4` はこの同居を前提とした値である。本プロジェクトが取り分を増やすと qwen-ocr 側に影響するため、変更は単独で判断しない。

### 3.3 起動順序

0. (初回のみ) vllm 用モデルを事前DL(§4.3)
1. (DGX Spark)`docker compose -f docker-compose.clean.yml up -d` で postgres-clean → api-clean を起動する(既存スタック。初回は `bin/init_clean.sh` でデータ投入込みの構築)
2. (DGX Spark)`docker compose up -d vllm`
3. (公開 VM・初回のみ) backend と frontend のイメージを x86_64 でビルドする。DGX 上の既存イメージは arm64 のため流用できない(§3.2)
4. (公開 VM・初回のみ) ssh-tunnel 用の鍵を生成し、DGX Spark の `authorized_keys` へ登録する(§3.4.4)
5. (公開 VM)ssh-tunnel → backend → frontend → gateway の順に起動する

backend は起動時に履修要項 YAML をロードし、api-clean へ疎通する。**ssh-tunnel を backend より先に起動する**のはこのためである。api-clean へ到達できなくても backend 自体は上がるが、シラバス参照を伴う機能が失敗する(§3.4.4)。**vllm は公開 VM 側の起動順序に関与しない**(トークンゲートウェイ経由で呼ぶため、backend は起動時に vllm へ接続しない)。ただし vllm が停止していると、提案・チャットは `502 upstream_unavailable` で失敗する(§6.3)。

**公開 VM のコンテナは現状ユーザセッションに紐づいて動いている。** rootless Podman のコンテナは、lingering を有効にした systemd ユーザユニットにしないと、ログアウトやホスト再起動で落ちる。常時稼働(§3.5.3)の前提としてユニット化が要る。**ssh-tunnel は断線からの自動復帰を systemd の `Restart=always` に委ねるため、ユニット化が機能要件になる**(§3.4.4、§13)。

### 3.4 ポート割り当てと待受状況

**GW ホスト**(教員側管理)

| ポート | 状態(2026-09-09) | 備考 |
|---|---|---|
| 22 | 待受あり | 管理用 SSH |
| 80 / 443 | ホスト自身は待ち受けず、**DNAT で公開入口の Incus コンテナへ転送** | 転送された通信はホストへローカル配送されないため `ss` には現れない(§3.5.1) |

**公開 VM**

| サービス | コンテナ内 | ホスト公開 |
|---|---|---|
| gateway(Caddy) | 8080 | `0.0.0.0:8080` |
| frontend | 3000 | 公開しない(Podman ネットワーク経由で gateway から参照) |
| backend | 8000 | 公開しない(同上) |
| ssh-tunnel | 5000 | 公開しない(同上。**ネットワーク別名 `api-clean` で backend から参照**) |

**公開 VM でホストに公開するのは gateway の 8080 のみとする。** コンテナ間の通信は Podman ネットワーク経由(サービス名:コンテナ内ポート、例 `http://pr2026-backend:8000`、`http://api-clean:5000`)で行う。**ssh-tunnel の 5000 をホスト側へ公開しない**ことは設計上の要件である。公開すると VM 上の他プロセスから api-clean へ無認証で到達できてしまう(§3.4.4)。

**DGX Spark**

| サービス | コンテナ内 | ホスト公開 | ホスト外からの到達 |
|---|---|---|---|
| vllm | 8000 | `127.0.0.1:8001` | **教員側の中継経由で可**(§3.4.1) |
| api-clean(既存) | 5000 | **`127.0.0.1:5050`** | **SSH ローカルフォワード経由のみ**(§3.4.4) |
| postgres-clean(既存) | 5432 | `127.0.0.1:5433` | 不可(本プロジェクトは参照しない) |

**DGX Spark 上のコンテナはすべて loopback にバインドし、本プロジェクトは新たな待受を設けない。** ホスト外から届く経路は、教員側が設置した中継(§3.4.1)と、公開 VM 側から張る SSH(22 経由。§3.4.4)に限られる。

#### 3.4.1 socat フォワーダ層

DGX Spark には、**loopback にバインドされた vLLM を学内アドレスへ中継する root 所有の socat プロセス**が systemd サービスとして常駐している(2026-09-08 設置。本プロジェクトの管理外)。

| 待受 | 転送先 | 送信元制限 | 用途 |
|---|---|---|---|
| `<学内アドレス>:8001` | `127.0.0.1:8001` | **GW ホストの1アドレスのみ**(socat の `range` オプション) | Qwen3.6。**トークンゲートウェイがこの中継を使って vllm へ届く**(§3.4.3)。本プロジェクトの backend はトークンゲートウェイ越しに間接的にこの経路を通る |
| `<学内アドレス>:11437` | `127.0.0.1:11435` | 同上 | 既存の qwen-ocr |
| `0.0.0.0:11436` | `127.0.0.1:11435` | **なし(学内全体)** | 既存の qwen-ocr(本プロジェクト外、2026-04 設置) |

**したがって、コンテナのバインドだけを見て「外部から到達しない」と判断してはならない。** 実態は「コンテナは loopback、その手前で送信元を1アドレスに絞った中継が外向きに開いている」である。この中継は本プロジェクトが管理しないため、設定の変更・停止は教員側の判断による。

**本プロジェクトはこの層に中継を追加しない。** api-clean を同じ方式で公開する案は §3.4.4 で退けた。

公開 VM から DGX Spark の vLLM に到達できるのは、VM の通信が GW ホストのアドレスへ SNAT されるためである(libvirt NAT)。socat の送信元制限は GW ホストのアドレスを許可しており、VM はその背後にいる。

**vLLM 自体に認証は設定されていない。** `docker-compose.yml` の vllm に `--api-key` を与えておらず、**公開 VM から**トークンなしの `/v1/models` と `/v1/chat/completions` がいずれも 200 を返すことを確認した(2026-09-10 実測)。この経路のアクセス制御は socat の送信元制限のみで成立している。

**送信元制限は同一ホスト上の VM を区別できない。** 公開 VM を含む GW ホスト上の全 VM は libvirt NAT で同一のアドレスへ SNAT されるため、`range` から見て互いに同じ送信元になる。この中継の許可範囲は「GW ホストの背後にいるもの全体」であり、特定の VM に絞ることはできない。

#### 3.4.2 backend の配置(決定・2026-09-13)

`POST /api/proposal` と `/api/chat/*` は backend が担うため、**gateway から backend へ到達できなければサービスは成立しない。**提案プロンプトの組み立て(§7.2.1)・履修要項のマージ(§4.4.3)・要件充足判定(§4.4.5)・構造化出力の検証(§5.3)はいずれも backend 側にあり、クライアントからは行えない。

2026-08 の時点では、DGX Spark の 8000 を学内に開放し、公開 VM の Caddy から `<アドレス>:8000` を叩く構成で疎通していた(§3.2.1 の `BACKEND_ADDR` はその名残である)。**その後、認証なしのポートを学内全体に開放する方針が採られないこととなり、8000 は loopback バインドに戻された。**

その結果、GW 側から backend へ到達する経路が無くなった。**これが唯一の欠落である**ことは実測で確認している(§3.5.1。学外からの `/pr-2026/api/*` が 404 ではなく 502 を返す)。

**検討した案は3つである。**

| 案 | 内容 | 論点 |
|---|---|---|
| 送信元を限定した中継 | §3.4.1 と同じ方式を backend の 8000 に適用する | 同じホスト上で既に採用実績があり、学内全体への開放も生じない。ただし DGX Spark にホスト外向けの待受が1つ増える。§3.4.1 のとおり送信元制限は GW ホスト上の VM を区別できないため、開けた口は**その背後にある全 VM から無認証で到達できる** |
| SSH ローカルフォワード | 公開 VM 側から DGX Spark へ接続し、backend の loopback ポートを公開 VM 側へフォワードする | ホスト外向けの待受を増やさず、認証と暗号化が付く。公開 VM から DGX Spark の SSH に到達できることが前提となる |
| **backend とシラバスデータ層を公開 VM 側へ移す(採用)** | DGX Spark を LLM 推論専用とし、ホストを跨ぐ通信を backend → LLM の1本に変える | gateway → backend がホスト内に収まる。**ホストを跨ぐ口が無くなるわけではなく、宛先が backend → LLM に移る**点に注意する。**要件§3.1 の改訂を伴う**。LLM への接続経路の確保、公開 VM 側の資源、常時稼働の手当て(§3.3)が別途要る |

**2026-09-13、3案目(backend とシラバスデータ層を公開 VM 側へ移す)を採用した。** 決め手は次の2点である。

> **その後の変更(2026-09-14)。** 移設対象のうち **api-clean・postgres-clean は DGX Spark へ戻した**(§3.4.4)。**backend を公開 VM に置くという本節の決定は維持される。** 以下の記述は backend の配置決定の経緯として読むこと。

- 前2案はいずれも DGX Spark 側にホスト外向けの口を増やすか、その可否を所有者に委ねる必要がある(§3.5.3)。3案目は**公開 VM 内だけで完結し、DGX Spark に変更を加えない**
- ローカル LLM へは、教員側が運用するトークンゲートウェイを利用する方針が示されている。**backend がどちらのホストにあっても LLM への経路はこれ1本**であり、backend を DGX Spark に置く利点が失われた

これに伴い次が生じる(**シラバスデータ層に関する項目は §3.4.4 で更新された**)。

- 要件§3.1(学生のデータを処理する一連の機能を学内の**単一**サーバ上で完結させる)を改訂した。処理は公開 VM と DGX Spark の2台に分かれるが、いずれも学内である
- 従来ホストを跨いでいた `/pr-2026/api/*` は公開 VM 内で閉じた。この時点でホストを跨ぐ通信は backend → vllm の1本だけとなったが、**§3.4.4 により backend → api-clean が加わり2本になっている**(§3.2.2)
- §13 の「GW↔DGX 間の HTTPS 再暗号化」は、当該区間が無くなったため項目ごと解消した。ホストを跨ぐ backend → vllm は HTTPS であり(§3.4.3)、backend → api-clean は SSH で暗号化される(§3.4.4)
- 公開 VM のコンテナが2つから5つに増え、資源と常時稼働の手当てが必要になった(§3.3、§13)。**この点が §3.4.4 の再検討を招いた**

#### 3.4.3 vllm への到達経路(トークンゲートウェイ)

**backend は教員側のトークンゲートウェイ経由で vllm を呼ぶ。** 直接 `<学内アドレス>:8001` を叩く経路も公開 VM からは到達可能だが、これは教員側がトークンゲートウェイのために設けた中継であり、本プロジェクトが直接利用する前提のものではない。API の詳細は §6.3。

2026-09-13 に公開 VM から実測して確認した事項を記す。

| 事項 | 実測結果 |
|---|---|
| **公開 URL への直接到達** | **不可。** ゲートウェイの FQDN は公開アドレスへ解決されるが、GW ホストは当該ポートを待ち受けず、外部インタフェース経由の流入のみを転送しているため、VM の内側からは接続が拒否される(§3.5.1) |
| **公開入口コンテナへの直接到達** | **可。** 公開 VM と公開入口コンテナは同一のセグメントにあり、FQDN の名前解決だけを当該コンテナへ向ければ TLS ごと通る(`http 200`)。IP を直接指定すると SNI が送られず TLS が成立しないため、**名前解決を差し替える形をとる**(コンテナには `--add-host` で与える。§3.2.1) |
| **モデル一覧** | `GET /v1/models` が 200。返るモデル ID は本プロジェクトが `--served-model-name` で与えた値と一致する(§3.2.2) |
| **ストリーミング** | 2段のリバースプロキシを越えて逐次到達する(バッファリングされない)。思考は本文とは別のフィールドで流れる(§6.3.1) |
| **リクエスト単位の推論設定** | `chat_template_kwargs.enable_thinking` がそのまま透過する。**履修提案で思考を切る設定(§6.3.1)がこの経路でも有効である** |
| **同時実行** | **同一トークンで生成が進行中の場合、後続は `503 busy` で即座に拒否される**(待たされない)。同時に成立するのは1トークンあたり1リクエストである |

**制約が2つ、設計に影響する。**

1. **同時実行数がトークン数で決まる。** 履修提案は1回あたり4〜5分を要する(§7.2)ため、1トークンのままでは、その間の他の利用者がすべて `503` になる。要件§6・§7(龍谷祭での同時利用)を満たすには、**トークンを複数発行して backend 側で使い分けるか、待ち行列を設けて待ち時間を提示する**必要がある。トークンの発行数は教員側が置いた流量制御に関わるため、**本数を含めて所有者の判断による**(§13)
2. **利用ログが100日間保存される。** プロンプトと応答が記録されるため、プロンプトに載せる学生データを最小化する(要件§5.5、§9、§7.2.1)

公開入口コンテナのアドレスが固定である保証は得られていない。変動した場合 backend の名前解決が失敗するため、§13 の未確定事項とする。

#### 3.4.4 シラバスデータ層の配置と api-clean への到達経路(決定・2026-09-14)

**api-clean・postgres-clean を DGX Spark に置き、公開 VM の backend からは SSH ローカルフォワードで到達する。**

##### 配置を戻す理由

§3.4.2 で公開 VM 側へ移すと決めたが、移設を実施する前に次の2点から見直した。

1. **公開 VM の資源が5コンテナの常時稼働に足りない。** 2026-09-14 時点で 3.8GiB / 2 vCPU、**swap が無く root も無いため swap を足せない**。postgres-clean と api-clean は常時メモリを占有し、`next build` はピークで数GB を使う。移設すると frontend の再ビルドに他コンテナの停止が要る状態が常態化する(§13)
2. **既存スタックを動かしたまま使える。** api-clean / postgres-clean は既存シラバスバックエンド担当の資産であり、DGX Spark 上で現に稼働している。移設は再構築とデータ投入、および担当との合意を伴うが、**据え置けばそのいずれも不要になる**

公開 VM に置くのは本プロジェクトが新規開発した要素に限る、という整理にもなる(§3.1)。

##### 経路の選定

api-clean は DGX Spark の loopback にあり、公開 VM から届く経路が無い。**これは §3.4.2 で backend について生じたのと同じ問題であり、同じ3案を検討した。**

| 案 | 内容 | 判断 |
|---|---|---|
| socat 中継を追加 | §3.4.1 と同じ方式を api-clean のホスト側ポート 5050 に適用する | **採らない。** 下記のとおり `POST /sql` を無認証で晒すことになる |
| **SSH ローカルフォワード(採用)** | 公開 VM 側から DGX Spark へ SSH を張り、api-clean の loopback ポートを公開 VM 側へ転送する | **採用。** DGX Spark にホスト外向けの待受を増やさず、認証と暗号化が付く |
| 入口 Caddy 経由で公開 | 教員側の入口 Caddy に認証付きのパスを設け、api-clean へ中継する | 採らない。経路は vllm と揃うが、実現がすべて教員側の作業依頼になり時期が読めない |

**socat 案を退けた決め手は、api-clean が無認証であることと、`POST /sql` で DB 全体を読めることである。** `/sql` には読み取り専用のガードが入っており(`SELECT` / `WITH` で始まる1文のみ、書き込み系キーワードを拒否、`LIMIT` を強制。当該リポジトリ `docker/fastapi/app/clean_api.py`)、**書き込みや破壊はできない**。しかし読み取りは DB 全体に及び、テーブルを限定しない。加えて §3.4.1 のとおり **socat の送信元制限は同一ホスト上の VM を区別できない**。両者が重なると、「GW ホストの背後にある全 VM から、無認証でシラバス DB 全体を読み出せる口」を開けることになる。**本サービスが使う3つの読み取りエンドポイント(§6.2)だけを晒すのとは範囲が異なる**ため、この案は採らない。

SSH 案は §3.4.2 で backend について検討したときと同じ方式である。当時は採用しなかったが、**今回は対象が backend(学生プロファイルを受ける公開系)ではなく api-clean(読み取り専用の参照系)であり、トンネルが切れても影響がシラバス参照機能に限られる**点が異なる。

##### 実装

**トンネルは専用コンテナ(ssh-tunnel)に閉じ込め、Podman ネットワーク上にネットワーク別名 `api-clean` で見せる。**

```
[公開 VM]                                              [DGX Spark]
backend ──http://api-clean:5000──> ssh-tunnel ──SSH:22──> sshd
                (Podman ネットワーク)      -L 0.0.0.0:5000:127.0.0.1:5050
                                                              │
                                                              └─> api-clean(ホスト 5050 → コンテナ 5000)
```

- **backend 側の設定は変更しない。** `api_clean_base_url` の既定値 `http://api-clean:5000`(`backend/app/settings.py`)が、ネットワーク別名によってそのまま解決される。公開 VM 上に api-clean が居た場合と同じ宛先で通る
- ssh-tunnel コンテナ内では `ssh -N -L 0.0.0.0:5000:127.0.0.1:5050 <ユーザ>@<DGX の学内アドレス>` を実行する。**転送先の 5050 は DGX Spark のホスト側ポート**であり、コンテナ内の 5000 とは番号が異なる(§3.2.2)。**コンテナ内の `0.0.0.0:5000` バインドは Podman ネットワーク内に閉じる**(コンテナのポートをホストへ公開しないため。§3.4)。待受を 5000 に合わせることで、backend からは `http://api-clean:5000` のまま引ける
- **VM ホスト側で `ssh -L` を直接走らせる形は採らない。** rootless Podman のコンテナから VM ホストの loopback を引くには待受を `0.0.0.0` に置く必要があり、VM 上の他プロセスに api-clean を晒すことになる
- 常駐は **systemd ユーザユニット + lingering** で行い、`Restart=always` / `RestartSec` で断線から自動復帰させる(§3.3)。autossh は使わず systemd に委ねる
- SSH のオプションに `-o ServerAliveInterval=30 -o ServerAliveCountMax=3 -o ExitOnForwardFailure=yes` を与える。**TCP は生きているのに転送だけが死ぬ半死状態**を避け、転送に失敗したら即座に終了して systemd に再起動させるためである
- 鍵は**このトンネル専用にパスフレーズ無しで生成**し、公開 VM 上に権限 600 で置く。イメージには焼き込まず、コンテナへは読み取り専用マウントで渡す
- **DGX Spark 側の `authorized_keys` で用途を限定する。** 当該鍵の行に次を付し、シェルの取得と他ポートへの転送を禁じる

```
restrict,port-forwarding,permitopen="127.0.0.1:5050" ssh-ed25519 AAAA... pr2026-tunnel
```

##### 障害時の挙動

**トンネルが切れると、シラバス参照を伴う機能がすべて失敗する。** 影響範囲は次のとおりで、いずれも学生には一時的な不調として提示する。

| 機能 | 影響 |
|---|---|
| シラバス検索・詳細(§6.1 の `/api/syllabi`) | 失敗する |
| チャットの tool calling(§6.2) | ツール呼び出しが失敗し、モデルが根拠を得られない |
| 履修提案(§7.2) | **候補がゼロになる。** 開講曜日・時限を突合できない科目は候補から外す規定(§7.2.4)のため、api-clean が全滅すると提案が成立しない |

backend の起動時疎通(§3.3)に加え、**トンネルの死活を検知する手当てが要る**(§13)。切断中に履修提案を「候補なし」として返すと、学生には正常な応答と区別がつかない。

**トンネルが生きていても api-clean が落ちれば同じ症状になる。** シラバスバックエンドのデータ再投入手順(`bin/init_clean.sh --reset`)は `docker compose down -v` を含み、api-clean と postgres-clean が作り直される。この間 SSH の転送先が接続を拒否する。**再投入は事前の周知を要する**(§3.5.3)。なお、2026-09-05 に当該リポジトリ側で記録された「`down -v` が `syllabus_backend_syllabus-clean-net` に相乗りしていた本プロジェクトの backend コンテナの接続を切る」事象は、**backend が公開 VM へ移ったことで生じなくなる**(相乗りが解消するため)。

##### 未確認の事項

| 事項 | 内容 |
|---|---|
| **公開 VM → DGX Spark の SSH 到達性** | 本方式の前提。VM の通信は libvirt NAT により GW ホストのアドレスへ SNAT されるため、DGX Spark 側のファイアウォールが GW ホストからの 22 を許可していれば通る。**未実測**(§13) |
| DGX Spark 上のアカウント | トンネル専用のアカウントを立てるか、既存の開発用アカウントに鍵を足すかを決める。`authorized_keys` の編集自体は開発チームの sudo 範囲内である |
| api-clean のバインド | 既存スタックが `127.0.0.1:5050` にバインドしていることの確認(§3.2.2)。当該リポジトリの `docker-compose.clean.yml` では既定であり、変更されていないことを実機で確かめる |
| レイテンシ | 履修提案は `GET /syllabi?year=<年度>` をページ送りで一括取得する(§7.2.4、候補は数百件規模)。ホストを跨ぐことで所要時間が伸びるため、`http_timeout`(既定 30 秒)で足りるかを実測する。必要なら backend 側にキャッシュを置く(§13) |

### 3.5 アクセス制御

#### 3.5.1 公開経路

**frontend は学外から HTTPS で到達できる**(2026-09-09 に外部から確認)。公開 URL は §3.5.2 のとおり `/pr-2026` 配下のサブパスである(実 URL は運用メモ)。

```
学生ブラウザ ──HTTPS──> GW ホストの公開アドレス :443
                          │ DNAT(ホスト自身は待ち受けない)
                          ↓
               Incus コンテナ(Caddy)          TLS 終端・振り分け
                          ↓
               公開 VM :8080(Caddy)
                          ├──✓── frontend :3000
                          └──✓── backend :8000       同一 VM 内(§3.4.2)
                                     │
                                     ├──HTTPS──> Incus コンテナ(Caddy)        ★1
                                     │              └─> トークンゲートウェイ ─> DGX vllm
                                     │
                                     └──HTTP───> ssh-tunnel(別名 api-clean)   ★2
                                                    └──SSH:22──> DGX api-clean(127.0.0.1:5050)
```

**backend からトークンゲートウェイへ向かう通信は、公開アドレスではなく Incus コンテナの私設アドレスへ直接向ける**(§3.4.3)。VM の内側から公開アドレスを叩いても DNAT の対象とならず到達しないためである。

**★2 は公開経路ではない。** 公開 VM 側から DGX Spark へ張るトンネルであり、学生のブラウザからは到達できない。DGX Spark 側で待ち受けるのは SSH(22)のみである(§3.4.4)。

TLS 終端と証明書の管理は GW ホスト側の Incus コンテナが担う。公開 VM の gateway はその後段にあり、HTTP で受ける。

**GW ホストの `ss` に 80/443 は現れない。** DNAT された通信は転送されるだけでホストへローカル配送されないためである。同じ理由で、公開 VM から GW ホストの公開アドレスへ向けた通信は DNAT の対象とならず到達しない。**外部からの到達性を公開 VM の内側から検証することはできない。**

**欠けていたのは backend への到達経路だけである**(§3.4.2)。学外から `/pr-2026/api/healthz` を叩くと **502** が返っていた(2026-09-09 実測)。404 ではなく 502 であることは、**公開入口から公開 VM の gateway までの振り分けが `/pr-2026/api/*` について正しく成立しており、失敗しているのが gateway → backend の1ホップだけである**ことを示す。backend を公開 VM 側へ移し `BACKEND_ADDR` を同一ネットワーク上のコンテナへ向けることで、このホップが解消する(§3.2.1)。

#### 3.5.2 URL 構造

公開 URL は **`/pr-2026` 配下のサブパス配信**とする。frontend は `next.config.ts` の `basePath: "/pr-2026"` でビルドされており、gateway の振り分けもこれに合わせている(§3.2.1)。

| 公開パス | 転送先 | 備考 |
|---|---|---|
| `/pr-2026`、`/pr-2026/*` | frontend | Next.js が `basePath` で受ける |
| `/pr-2026/api/*` | backend | gateway が `/pr-2026` を剥がし、backend には `/api/*` として届く |
| 上記以外 | 404 | gateway が返す |

**内部 API の公開パスは `/pr-2026/api/*` であり、`/api/*` ではない。** Next.js の `basePath` はページとアセットの生成先を変えるだけで、アプリケーションコードが呼ぶ `fetch()` のパスには前置されない。したがって **frontend は自身の呼び出し先に `/pr-2026` を明示的に含める必要がある**(§6.1)。

`/` をルート配信へ寄せる案は採らない。GW ホストは他用途と共用されており、ルートを本プロジェクトが占有できないためである。

#### 3.5.3 権限と責任分界

| 範囲 | 権限 | 変更方法 |
|---|---|---|
| GW ホスト(80/443、TLS、VM フォワード、ファイアウォール、Incus / libvirt) | 教員側 | 依頼 |
| 公開 VM のユーザ権限内(Podman コンテナ、Caddyfile、frontend イメージ) | 開発チーム | 直接 |
| 公開 VM の root 権限(OS 更新、1024 未満のポート、ufw) | **無し**(特定スクリプト1本の実行のみ) | 依頼 |
| DGX Spark のコンテナと compose | 開発チーム(sudo あり) | 直接。ただし **vllm の停止・再起動・起動オプション変更は他の利用者に影響する**ため事前周知を要する(§3.2.2) |
| DGX Spark のホスト外への口(中継の設置、ポートの開放、ホストのファイアウォール) | 所有者(アドバイザー教員) | 依頼。sudo は持つが単独では判断しない(§3.1)。**本構成では新たな口を設けない**(§3.4.2、§3.4.4) |
| DGX Spark の `authorized_keys`(トンネル用鍵の登録) | 開発チーム(sudo あり) | 直接。**新たな待受を設けない変更であり、既存の SSH(22)の範囲内である**。鍵は `permitopen` で api-clean の1ポートに限定する(§3.4.4) |
| トークンゲートウェイ(トークンの発行数、利用ログ、中継先) | アドバイザー教員 | 依頼。トークンの発行自体はセルフサービスだが、**発行本数は流量制御に関わるため判断を仰ぐ**(§3.4.3) |
| シラバスバックエンド(api-clean / postgres-clean)のコードとデータ | シラバスバックエンド担当([ProjectResearch2026/syllabus_backend](https://github.com/ProjectResearch2026/syllabus_backend)) | **本リポジトリでは改修しない**(§1.1.1)。必要な改修は当該リポジトリへ起票する。**本サービスの機能は当該側の改修に依存する**(§13) |
| シラバスバックエンドの配置とバインド | シラバスバックエンド担当 | **移設しない**(§3.4.4)。DGX Spark 上の稼働中スタックをそのまま使う。`127.0.0.1:5050` のバインドを外さないことと、`--reset` を伴う再投入の事前周知を要する |

- **学生がサービスを利用するのに SSH は不要**(学生はブラウザから HTTPS でアクセスするのみ)。SSH は運用者側の管理経路である
- 公開 VM の外向き通信を本プロジェクトの宛先に限定する方針は、root 権限が無いため VM 内では実施できない。必要であれば GW ホスト側での実施を依頼する
- リクエスト/レスポンスのボディはログに記録しない(要件§5.5。詳細は§9)
- 龍谷祭期間を含む常時稼働が前提となるため、公開 VM のコンテナは systemd ユーザユニット化と lingering の有効化を要する(§3.3)。**ssh-tunnel については断線からの自動復帰を兼ねるため必須である**(§3.4.4)
