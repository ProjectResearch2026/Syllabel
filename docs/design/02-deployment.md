## 3. デプロイ構成

> ホスト名・IP アドレス・アカウント名などの環境固有の値は、本書が公開される可能性を考慮して記載しない。実値は運用メモを参照する。未確定の事項は §13 に送る。

### 3.1 配置先

配置は2ホストに分かれ、GW 側はさらにホストとゲスト VM の2層になる。

| 層 | 実体 | 所有 | 運用権限 | 稼働させるもの |
|---|---|---|---|---|
| **GW ホスト** | アドバイザー教員研究室の Web サーバ(x86_64 デスクトップ機、学内アドレスと FQDN を保持) | アドバイザー教員 | **教員側** | libvirt(KVM)と Incus。公開入口の Caddy(TLS 終端)を Incus コンテナで、本プロジェクトの公開 VM を含む複数の VM を libvirt で動かす |
| **公開 VM** | GW ホスト上の libvirt ゲスト(Ubuntu 24.04 LTS / x86_64、libvirt NAT 配下の私設アドレス) | アドバイザー教員 | **開発チーム(root 権限なし)** | 本プロジェクトの gateway(Caddy)、frontend、**backend** |
| **DGX Spark** | 学内。**DGX OS 7.5.0**(Ubuntu 24.04 LTS ベース、カーネル `6.17.0-1021-nvidia`、**arm64**、GB10) | アドバイザー教員 | 開発チーム(sudo あり) | **vllm、api-clean、postgres-clean** |

**公開 VM に置くのは、本プロジェクトが新規開発した要素(gateway / frontend / backend)に限る。** シラバスバックエンドは DGX Spark 上のスタックを使い、移設も改変も行わない。配置の根拠は §3.4.2(backend)と §3.4.4(シラバスデータ層)による。

**本プロジェクトが DGX Spark に固有のものを置くことはない。** vllm・api-clean・postgres-clean はいずれもホストの loopback にバインドし、ホスト外から届く経路は教員側が運用するトークンゲートウェイに限られる(★1・★2 とも。§3.4.3、§3.4.4)。

**2ホストとも所有者はアドバイザー教員であり、開発チームは貸与を受けて運用している。** 運用権限を持つことは、構成を単独で決めてよいことを意味しない。とくにホスト外へ口を開ける変更(中継の設置、ポートの開放、ホストのファイアウォール)は、権限の有無にかかわらず所有者の判断による(§3.5.3)。

**GW ホストの公開経路(公開アドレスでの受け、DNAT、TLS 終端、公開入口の Incus コンテナの設定、ファイアウォール)は教員側の管理範囲である。** ただし開発チームの権限は「何もできない」ではない。GW ホストで sudo は持たないが、`incus-admin` と `libvirt` の各グループに属しており、**Incus コンテナと VM を操作できる**。したがって技術的には入口 Caddy の設定にも手が届く。それでも当該コンテナは他プロジェクトと共用の公開入口であるため、**設定変更は所有者の作業とする**(§3.5.3)。

公開 VM で与えられている sudo は教員側が用意した特定スクリプト1本の実行に限られ、**一般の root 権限は無い**。VM の OS レベルの操作は**依頼**によって行う。

GW ホストには本プロジェクト以外の VM(トークンゲートウェイ用途と見られるもの、および別用途のもの)と Incus コンテナが同居する。本プロジェクトが占有するのは公開 VM 1台である。

学生データを処理する一連の機能は、ブラウザ・公開 VM・DGX Spark で完結する(要件§3.1)。公開 VM とブラウザが学生プロファイルを扱い、DGX Spark は LLM 推論とシラバス参照を担う。**DGX Spark 側の api-clean へ学生プロファイルを渡すことはない**(送るのは科目の検索条件のみ。§6.2)。いずれのホストも学内にあり、成績データが学外へ出ることはない。

### 3.2 コンテナ構成

**2ホストでコンテナ基盤とアーキテクチャが異なる。** 同一のイメージを両ホストで使い回すことはできない。

| | 公開 VM | DGX Spark |
|---|---|---|
| 基盤 | **rootless Podman**(docker 未導入) | **Docker 29.x** |
| アーキテクチャ | x86_64 | **arm64(aarch64)** |
| 定義 | **Quadlet**(`~/.config/containers/systemd/*.container`)。systemd ユーザユニットが生成される(§3.3) | `docker-compose.yml`(vllm)と `docker-compose.clean.yml`(既存スタック) |
| 特権ポート | **1024 未満を待ち受けられない**(rootless のため)。gateway は 8080 を使う | 制約なし(ただし全コンテナを loopback バインドとする。§3.4) |

`vllm/vllm-openai` は DGX 側で **arm64 イメージ**として取得される。frontend(`frontend/Containerfile`)と backend(`backend/Dockerfile`)のイメージは**公開 VM 上で x86_64 としてビルドする**。イメージのアーキテクチャがホストごとに異なるため、一方でビルドしたイメージを他方へ持ち込む運用は取らない。**DGX 上で arm64 としてビルドしていた backend イメージは流用できない**(§3.3)。

シラバスバックエンド(api-clean / postgres-clean)は **DGX Spark 上のスタックを使い、本プロジェクトは移設も改変も行わない**(§1.1.1、§3.4.4)。公開 VM 側に要るのは、api-clean へトークンゲートウェイ経由で到達するための base_url とトークンだけである(§3.4.4、§6.2)。

#### 3.2.1 公開 VM

rootless Podman で3つのコンテナを、Podman ネットワーク `syllabel` 上で名前解決させて動かす。定義は **Quadlet** で、`~/.config/containers/systemd/` に置いた `syllabel.network` と3つの `.container` から systemd ユーザユニットが生成される(§3.3)。

**名前はサービス名 `Syllabel` で揃える。** 名称が決まるまでは `pr2026` を接頭辞にしていたが、ネットワーク `syllabel`、コンテナとユニット `syllabel-{backend,frontend,gateway}`、イメージ `localhost/syllabel-{backend,frontend}:latest` に改めた。**コンテナ名はネットワーク内の名前解決の宛先そのもの**であり、gateway の `BACKEND_ADDR`、frontend の `BACKEND_ORIGIN`、`lib/api_base.ts` の既定値(§6.1)がこの名前を指す。

**稼働中の VM では、リポジトリを更新しただけでは改名は反映されない。** Quadlet のユニットは `~/.config/containers/systemd/` にあり本リポジトリの管理外だからである。次の順で行う。

1. `systemctl --user stop pr2026-{gateway,frontend,backend}.service`
2. Quadlet のファイル名と中身を改める(`pr2026.network` → `syllabel.network`、各 `.container` の `ContainerName=`・`Network=`・`Image=`)
3. gateway の環境ファイルの `BACKEND_ADDR` と frontend の `BACKEND_ORIGIN` を新しいコンテナ名に直す
4. 新しいタグでイメージをビルドし直す(§3.3)
5. `systemctl --user daemon-reload` してから起動する

**古いネットワークとイメージは、新しい構成が上がってから消す。** 先に消すと戻せない。

| コンテナ | イメージ | 公開 | 役割 |
|---|---|---|---|
| gateway | `caddy:alpine` | `0.0.0.0:8080` | 振り分け。`/syllabel/api/*` を backend、`/syllabel`・`/syllabel/*` を frontend へ |
| frontend | 自ビルド(`frontend/Containerfile`) | なし(ネットワーク経由でのみ到達) | Next.js standalone(`PORT=3000`、`NODE_ENV=production`) |
| backend | 自ビルド(`backend/Dockerfile`、x86_64) | なし | FastAPI + PydanticAI。トークンゲートウェイ経由で vllm(§6.3)と api-clean(§3.4.4)を呼ぶ |

**backend コンテナは rootless Podman で動く。** `backend/Dockerfile` は `python:3.12-slim` を基に `pip install .` と `uvicorn --port 8000` を行うだけで、GPU・`ipc: host`・特権のいずれも要さず、待受も 1024 以上である。**`USER` による非 root 化を行っていないことが要件である。** 公開 VM のホームには default ACL(`other::---`)が設定されており、コンテナ内の非 root ユーザはホスト上で別 uid にマップされてファイル所有者から見て「その他」に該当するため、イメージ内の実行ファイルすら読めずに起動に失敗する(`frontend/Containerfile` のコメントに同じ理由の記載がある)。rootless Podman ではコンテナ内 root もホスト上の非特権 uid にマップされるため、ホストの root 権限には繋がらない。

**backend のコンテナ定義は、DGX Spark 用の `docker-compose.yml`(§3.2.2)とは次の3点で異なる。** いずれも公開 VM では成り立たない前提であり、持ち込まない。

| DGX Spark 用の定義 | 公開 VM で成り立たない理由 | 公開 VM での扱い |
|---|---|---|
| `depends_on: vllm (service_healthy)` | 公開 VM に vllm が居ない | 持たない。backend は起動時に vllm へ接続しない(§3.3)ため影響しない |
| `networks: syllabus-clean-net`(external) | 公開 VM に当該ネットワークが無い | 持たない。api-clean へはトークンゲートウェイ経由で到達する(§3.4.4) |
| `ports: 127.0.0.1:8000:8000` | 公開 VM ではホストに公開しない | 持たない。gateway とは Podman ネットワークで通信する |

`curricula/` と `offerings/` の読み取り専用マウントは rootless Podman でもそのまま通る(Ubuntu は AppArmor のため SELinux ラベル `:z` は不要)。ただし**公開 VM 上にリポジトリの clone が要る**。

稼働中の Caddyfile は VM 上のファイルを読み取り専用で bind mount している(パスは運用メモ)。**ファイル単位の bind mount はマウント時の inode を掴むため、`sed -i` や `cp` のように置き換えを伴う編集をするとコンテナ側に反映されない。** 上書き(`>` によるリダイレクト)で編集するか、コンテナを作り直す。

```caddyfile
:8080 {
      # /syllabel/api/* → バックエンド(/syllabel だけ剥がす)
      handle /syllabel/api/* {
              uri strip_prefix /syllabel
              reverse_proxy {$BACKEND_ADDR}
      }

      # Next.js は basePath 使用時に末尾スラッシュ無しを正規とするため、
      # /syllabel と /syllabel/* の両方をフロントへ渡す
      @app path /syllabel /syllabel/*
      handle @app {
              reverse_proxy syllabel-frontend:3000
      }

      handle {
              respond "not found" 404
      }
}
```

`BACKEND_ADDR` は gateway の Quadlet が読む環境ファイルで与え、**同一 Podman ネットワーク上の `syllabel-backend:8000` を指す**。この振り分けが §3.5.2 の URL 構造を決めている。

**Quadlet 管理下のコンテナは、`podman run` で作り直しても定義から作り直される。** 環境変数を変えるときは環境ファイルを直して `systemctl --user restart` を行う。コンテナを直接作り直すと、数秒後に systemd が定義どおりのコンテナへ置き換えるため、変更は反映されない。

**SSE のために読み取りタイムアウトを明示する。** Caddy の `reverse_proxy` は既定でレスポンスをバッファリングしないため逐次配信自体は通るが、チャット系は1回のモデル呼び出しに100秒超かかることがあるため、既定のタイムアウトに委ねない(§13)。

**frontend コンテナには backend の宛先を `BACKEND_ORIGIN` で渡す。** サーバ側描画から backend を引く経路(§6.1)が宛先を解決できるようにするためである。渡さない場合は本番既定の `http://syllabel-backend:8000` にフォールバックするため、コンテナ名を変えたときはこの環境変数で合わせる。

**backend コンテナには、トークンゲートウェイへの接続情報を渡す**(§6.3)。トークンは環境ファイル(パーミッション 600)に置き `--env-file` で与え、イメージには焼き込まない。あわせて、ゲートウェイの FQDN を公開入口コンテナの私設アドレスへ向けるため `--add-host` を与える(理由は §3.4.3)。接続情報は **vllm 向けと api-clean 向けの2組**(base_url とトークン)になる(§3.4.4、§6.2)。

#### 3.2.2 DGX Spark

リポジトリ直下の `docker-compose.yml` が **vllm を定義する**(配置先は運用メモ)。**backend はここでは定義しない**(公開 VM 側に置くため。§3.2.1)。シラバスバックエンドは当該リポジトリの `docker-compose.clean.yml` により DGX Spark 上で稼働する。

| コンテナ | 定義 | ホスト公開 | 役割 |
|---|---|---|---|
| vllm | `docker-compose.yml` | `127.0.0.1:8001` | LLM 推論。教員側の中継経由でトークンゲートウェイから呼ばれる(★1) |
| api-clean(既存) | `docker-compose.clean.yml` | **`127.0.0.1:5050` → コンテナ 5000** | シラバス情報提供 API。トークンゲートウェイ経由で引かれる(★2) |
| postgres-clean(既存) | `docker-compose.clean.yml` | **`127.0.0.1:5433` → コンテナ 5432** | シラバス DB。本プロジェクトは直接触らない |

**ホストをまたぐ通信は backend を起点とする2本である**(★1 = backend → vllm、★2 = backend → api-clean)。**いずれも教員側のトークンゲートウェイを経由する**(§3.4.3、§3.4.4)。**どちらも DGX Spark に本プロジェクト固有のものを置かない。**

**ホスト側の公開はいずれも loopback に限る。** シラバスバックエンド側が CVE-2026-2005 対応の一環として定めた条件であり、本プロジェクトの都合で外さない。**ホスト側のポートはコンテナ内と番号が異なる**(API は 5050→5000、Postgres は 5433→5432)点に注意する。★2 の転送先は `127.0.0.1:5050` である。

**vllm へは、発行されたトークンを用いて教員側のトークンゲートウェイ経由で到達する。** ゲートウェイが中継する先がこの vllm であり、`GET /v1/models` は `--served-model-name` で与えた値・`--model` のパス `/models`・`--max-model-len` をそのまま返す。**したがって `--served-model-name` を変えると、呼び出し側のモデル ID も揃えて変える必要がある**(§6.3)。

vllm の起動オプションは以下とする。

```yaml
    command:
      - --model
      - /models                       # 事前DLしたローカルパス。起動時に HF からは取得しない
      - --served-model-name           # §6.3 の OpenAIChatModel(model=...) と一致させ 404 を防ぐ
      - qwen3.8-27b-fp8
      - --language-model-only         # テキスト専用。ビジョンを省きメモリを KV cache に回す
      - --reasoning-parser            # 思考モデルのため必須。無いと思考が本文に漏れ構造化出力が壊れる
      - qwen3
      - --enable-auto-tool-choice
      - --tool-call-parser            # hermes ではなく qwen3_coder(公式指定の出力書式)
      - qwen3_coder
      - --max-model-len               # 既定262144はメモリ過大。最低128K推奨に沿い131072。OOM時さらに削減
      - "131072"
      - --gpu-memory-utilization      # 同一GPUを共有する他ワークロードがある前提。§3.2.3
      - "0.4"
      # 単GPU構成のため tensor-parallel は指定しない(=1)
```

モデルはイメージ内に持たず、ホスト上に**事前DL**したものを読み取り専用で bind mount する。コンテナ起動時に HuggingFace から取得しないため、Docker 名前付きボリュームは使わない。

#### 3.2.3 GPU の共有状況

GB10 の統合メモリ(121 GiB)上で **vLLM のエンジンが2基動いている**(2026-09-19 実測)。

| プロセス | 用途 | `--gpu-memory-utilization` | GPU メモリ |
|---|---|---|---|
| `VLLM::EngineCore` | 既存の qwen-ocr(本プロジェクト外) | 0.35 | 40,580 MiB |
| `VLLM::EngineCore` | 本プロジェクトの vllm | 0.4 | 46,294 MiB |

**qwen-ocr は Qwen3-VL-32B-Instruct-FP8 である**(イメージ `vllm/vllm-openai:v0.24.0`、`--max-model-len 8192`、KV cache 18,432 tokens、ホストネットワーク、`--served-model-name` を与えていないためモデル ID は `/models`)。本プロジェクトの管理外だが、**本節の取り分の根拠になるため実態を記録する**。

本プロジェクト側の内訳は次のとおり(2026-09-19、Qwen3.8-27B-FP8 + vLLM v0.27.1 の起動ログ)。

| 項目 | 値 |
|---|---|
| 重み | 27.64 GiB |
| CUDA graph | 1.41 GiB |
| KV cache | 15.49 GiB = 247,580 tokens |
| 同時実行(`--max-model-len 131072` に対して) | **1.89 倍** |

**Qwen3.6 → Qwen3.8 で取り分は据え置いた。** `--gpu-memory-utilization 0.4` はこの同居を前提とした値であり、**本プロジェクトが取り分を増やすと qwen-ocr 側に影響するため、変更は単独で判断しない。**

**移行前後で「GPU KV cache size」のトークン数を直接比べてはならない。** 版によって数え方が違う。移行前(Qwen3.6-27B-FP8 + vLLM 0.20.0)は `KV cache 16.77 GiB = 68,208 tokens / 同時実行 2.05 倍`だったが、68,208 は同時実行の倍率と直接対応しない(68,208 × 64層 ÷ full_attention 16層 ÷ 131,072 ≒ 2.05 で辻褄が合い、full attention 層あたりで数えていたとみられる)。v0.27.1 の 247,580 は 247,580 ÷ 131,072 ≒ 1.89 と直接対応する実トークン数である。**比較できるのは同時実行の倍率だけで、2.05 倍 → 1.89 倍と約8%下がっている。**

**この低下はモデルではなく vLLM の版差による。** v0.21.0 以降、CUDA graph の使用量を見込んでから KV cache を割り当てるようになったため、同じ `0.4` でも実効値が `0.3884` 相当に目減りする。vLLM 自身が起動ログで「移行前と同じ実効 KV cache を保つなら `0.4116` にせよ」と助言している。**上げるかどうかは同時実行の要件(§10.2)と qwen-ocr との兼ね合いで決める**(§13)。

### 3.3 起動順序

0. (初回のみ) vllm 用モデルを事前DL(§4.3)
1. (DGX Spark)`docker compose -f docker-compose.clean.yml up -d` で postgres-clean → api-clean を起動する(既存スタック。初回は `bin/init_clean.sh` でデータ投入込みの構築)
2. (DGX Spark)`docker compose up -d vllm`
3. (公開 VM・初回のみ) backend と frontend のイメージを x86_64 でビルドする(§3.2)
4. (公開 VM)Quadlet のユニットが `default.target` から起動する。個別に操作する場合は `systemctl --user start syllabel-{backend,frontend,gateway}.service`

backend は起動時に履修要項 YAML をロードし、api-clean へ疎通する。api-clean へ到達できなくても backend 自体は上がるが、シラバス参照を伴う機能が失敗する(§3.4.4)。**vllm は公開 VM 側の起動順序に関与しない**(トークンゲートウェイ経由で呼ぶため、backend は起動時に vllm へ接続しない)。ただし vllm が停止していると、提案・チャットは `502 upstream_unavailable` で失敗する(§6.3)。

**frontend と backend は揃えて入れ替える。** 両者の間には API の契約があり(§6.1)、片方だけ新しくすると呼び出しが噛み合わない。**実際に事故が起きた** — frontend だけを入れ替えたところ、新しい frontend が呼ぶ `GET /api/course-targets`(§6.1.3)を古い backend が持たず 404 を返し、検索画面が `error.tsx` に落ちた。デプロイは両方を建て直してから両方を再起動する。

```bash
podman build -t localhost/syllabel-backend:latest ./backend
podman build -t localhost/syllabel-frontend:latest ./frontend
systemctl --user restart syllabel-backend.service syllabel-frontend.service
```

**API を足した側だけを先に入れるのは安全側である**(使われない口が増えるだけ)。逆順(呼ぶ側を先)は落ちる。判断に迷うときは backend を先に入れる。

**公開 VM のコンテナは Quadlet で systemd ユーザユニットとして動かし、lingering を有効にする。** rootless Podman のコンテナは lingering が無いとログアウトで落ちるため、常時稼働(§3.5.3)の前提となる。各 `.container` の `[Install] WantedBy=default.target` が自動起動を担うので、**生成されたユニットに `systemctl --user enable` は行わない**(生成ユニットは enable の対象外であり、実行すると `transient or generated` で失敗する)。

### 3.4 ポート割り当てと待受状況

**GW ホスト**(教員側管理)

| ポート | 待受 | 備考 |
|---|---|---|
| 22 | 待受あり | 管理用 SSH |
| 80 / 443 | ホスト自身は待ち受けず、**DNAT で公開入口の Incus コンテナへ転送** | 転送された通信はホストへローカル配送されないため `ss` には現れない(§3.5.1) |

**公開 VM**

| サービス | コンテナ内 | ホスト公開 |
|---|---|---|
| gateway(Caddy) | 8080 | `0.0.0.0:8080` |
| frontend | 3000 | 公開しない(Podman ネットワーク経由で gateway から参照) |
| backend | 8000 | 公開しない(同上) |

**公開 VM でホストに公開するのは gateway の 8080 のみとする。** コンテナ間の通信は Podman ネットワーク経由(サービス名:コンテナ内ポート、例 `http://syllabel-backend:8000`)で行う。

**DGX Spark**

| サービス | コンテナ内 | ホスト公開 | ホスト外からの到達 |
|---|---|---|---|
| vllm | 8000 | `127.0.0.1:8001` | **教員側の中継経由で可**(§3.4.1) |
| api-clean(既存) | 5000 | **`127.0.0.1:5050`** | **トークンゲートウェイ経由のみ**(§3.4.4) |
| postgres-clean(既存) | 5432 | `127.0.0.1:5433` | 不可(本プロジェクトは参照しない) |

**DGX Spark 上のコンテナはすべて loopback にバインドし、本プロジェクトは新たな待受を設けない。** ホスト外から届く経路は、教員側が運用する中継とトークンゲートウェイに限られる(§3.4.1、§3.4.3、§3.4.4)。

#### 3.4.1 socat フォワーダ層

DGX Spark には、**loopback にバインドされたサービスを学内アドレスへ中継する root 所有の socat プロセス**が systemd サービスとして常駐している。

| ユニット | 待受 | 転送先 | 送信元制限 | 用途 |
|---|---|---|---|---|
| `socat-qwen36.service` | `<学内アドレス>:8001` | `127.0.0.1:8001` | **GW ホストの1アドレスのみ**(socat の `range` オプション) | **トークンゲートウェイがこの中継を使って vllm へ届く**(§3.4.3)。本プロジェクトの backend はトークンゲートウェイ越しに間接的にこの経路を通る |
| `socat-qwenocr.service` | `<学内アドレス>:11437` | `127.0.0.1:11435` | 同上 | 既存の qwen-ocr |
| `socat-syllabus.service` | `<学内アドレス>:5050` | `127.0.0.1:5050` | 同上 | **api-clean。トークンゲートウェイがこの中継を使ってシラバス API へ届く**(§3.4.4) |
| `socat-qwen.service` | `0.0.0.0:11436` | `127.0.0.1:11435` | **なし(学内全体)** | 既存の qwen-ocr(本プロジェクト外、2026-04 設置) |

**ユニット名 `socat-qwen36.service` はモデル名に由来するが、Qwen3.8 へ移行しても改名しない。** systemd ユニットは本リポジトリの管理外(root 所有・教員側の運用)であり、名前と実態のずれよりも、設定を触らずに済ませることを優先する。中継しているのは「本プロジェクトの vllm のホスト側ポート 8001」であって特定のモデルではない。

**したがって、コンテナのバインドだけを見て「外部から到達しない」と判断してはならない。** 実態は「コンテナは loopback、その手前で送信元を1アドレスに絞った中継が外向きに開いている」である。この中継は本プロジェクトが管理しないため、設定の変更・停止は教員側の判断による。

**api-clean 向けの中継(`socat-syllabus.service`)は、本プロジェクトの求めにより所有者の合意を得て追加した。** 既存2本と同型で、送信元は GW ホストの1アドレスに限る。

**この層は残余リスクを持つ。** 上記のとおり送信元制限は GW ホスト上の VM を区別しないため、**GW ホストの背後にある VM からは、トークンを持たなくても api-clean に到達できる**。公開経路側のゲート(§3.4.4)が守るのは学外からの経路であって、この区間ではない。api-clean 自身が無認証であることと併せ、**`POST /sql` によるシラバス DB 全体の読み出しは、GW ホスト上の VM からは成立する**。許容したうえで採用している。

公開 VM から DGX Spark の vLLM に到達できるのは、VM の通信が GW ホストのアドレスへ SNAT されるためである(libvirt NAT)。socat の送信元制限は GW ホストのアドレスを許可しており、VM はその背後にいる。

**vLLM 自体に認証は設定されていない。** `docker-compose.yml` の vllm に `--api-key` を与えておらず、**公開 VM から**トークンなしの `/v1/models` と `/v1/chat/completions` がいずれも 200 を返すことを確認した(2026-09-10 実測)。この経路のアクセス制御は socat の送信元制限のみで成立している。

**送信元制限は同一ホスト上の VM を区別できない。** 公開 VM を含む GW ホスト上の全 VM は libvirt NAT で同一のアドレスへ SNAT されるため、`range` から見て互いに同じ送信元になる。この中継の許可範囲は「GW ホストの背後にいるもの全体」であり、特定の VM に絞ることはできない。

#### 3.4.2 backend を公開 VM に置く理由

`POST /api/proposal` と `/api/chat/*` は backend が担うため、**gateway から backend へ到達できなければサービスは成立しない。** 提案プロンプトの組み立て(§7.2.1)・履修要項のマージ(§4.4.3)・要件充足判定(§4.4.5)・構造化出力の検証(§5.3)はいずれも backend 側にあり、クライアントからは行えない。

backend を DGX Spark に置くと、この必須の経路がホストを跨ぐ。DGX Spark 上のコンテナは loopback にバインドするため(§3.4)、gateway から届かせるには**ホスト外向けの口を新たに設けるか、公開 VM 側からトンネルを張る**ことになる。いずれも次の難点を持つ。

| 案 | 難点 |
|---|---|
| 送信元を限定した中継(§3.4.1 と同じ方式) | DGX Spark にホスト外向けの待受が1つ増える。送信元制限は GW ホスト上の VM を区別できないため、開けた口は**その背後にある全 VM から無認証で到達できる**。学生プロファイルを受ける口をこの条件で晒すことは許容しない |
| SSH ローカルフォワード | 待受は増えないが、**サービスの根幹の経路がトンネルの生存に依存する**。切れれば提案もチャットも全面停止する |

**backend を公開 VM に置けば、gateway → backend が同一ホスト内に収まり、この判断自体が不要になる。** 加えて、ローカル LLM へは教員側のトークンゲートウェイを経由する方針であり(§3.4.3)、**backend がどちらのホストにあっても LLM への経路は変わらない**。backend を DGX Spark に置く利点は無い。

公開 VM に置くことで、**学生プロファイルを扱う処理(gateway・backend)とブラウザ内処理が、公開 VM とブラウザに収まる**。要件§3.1 の「学内で完結させる」は、公開 VM と DGX Spark の2台で担保する(§3.1)。

#### 3.4.3 vllm への到達経路(トークンゲートウェイ)

**backend は教員側のトークンゲートウェイ経由で vllm を呼ぶ。** 直接 `<学内アドレス>:8001` を叩く経路も公開 VM からは到達可能だが、これは教員側がトークンゲートウェイのために設けた中継であり、本プロジェクトが直接利用する前提のものではない。API の詳細は §6.3。

公開 VM からの実測に基づき、この経路の性質を次のとおり前提とする。

| 事項 | 実測結果 |
|---|---|
| **公開 URL への直接到達** | **不可。** ゲートウェイの FQDN は公開アドレスへ解決されるが、GW ホストは当該ポートを待ち受けず、外部インタフェース経由の流入のみを転送しているため、VM の内側からは接続が拒否される(§3.5.1) |
| **公開入口コンテナへの直接到達** | **可。** 公開 VM と公開入口コンテナは同一のセグメントにあり、FQDN の名前解決だけを当該コンテナへ向ければ TLS ごと通る(`http 200`)。IP を直接指定すると SNI が送られず TLS が成立しないため、**名前解決を差し替える形をとる**(コンテナには `--add-host` で与える。§3.2.1) |
| **モデル一覧** | `GET /v1/models` が 200。返るモデル ID は本プロジェクトが `--served-model-name` で与えた値と一致する(§3.2.2) |
| **ストリーミング** | 2段のリバースプロキシを越えて逐次到達する(バッファリングされない)。思考は本文とは別のフィールドで流れる(§6.3.1) |
| **リクエスト単位の推論設定** | `chat_template_kwargs.enable_thinking` がそのまま透過する。**履修提案で思考を切る設定(§6.3.1)がこの経路でも有効である** |
| **同時実行** | **同一トークンで生成が進行中の場合、後続は `503 busy` で即座に拒否される**(待たされない)。同時に成立するのは1トークンあたり1リクエストである。**ゲートウェイの実装を確認済み**(2026-09-19) — 進行中のトークンを集合に持ち、そこに含まれるトークンからの生成要求を拒否する形であり、**制約はトークン単位である**ことが確定している |
| **モデル名の指定** | 接続先ごとに1つのモデル名が固定されており、**本文の `model` がそれと違えば `400 model_mismatch` で弾かれる**(期待値が応答に入る)。**省略すれば固定値に差し替えられる**が、PydanticAI は常に `model` を送るため本プロジェクトでは省略できない(§6.3) |
| **宛先とモデルの分離** | ゲートウェイの宛先(dest)は**モデル名を含まない**。したがって **vllm のモデルを差し替えてもトークンの再発行は不要**である(§3.4.3.1) |
| **トークンの有効期間** | 発行から **90日**(2026-09-19 時点の設定)。期限切れは `401` となり全機能が停止する(§6.3、§13) |

**制約が3つ、設計に影響する。**

1. **同時実行数がトークン数で決まる。** 履修提案は1回あたり4〜5分を要する(§7.2)ため、1トークンのままでは、その間の他の利用者がすべて `503` になる。要件§6・§7(龍谷祭での同時利用)を満たすには、**トークンを複数発行して backend 側で使い分けるか、待ち行列を設けて待ち時間を提示する**必要がある。**制約がトークン単位であることは実装で裏付けられている**(上表)ため、複数発行は確実に効く。ただしトークンの発行数は教員側が置いた流量制御に関わるため、**本数を含めて所有者の判断による**(§13)
2. **利用ログが100日間保存される。** プロンプトと応答が記録されるため、プロンプトに載せる学生データを最小化する(要件§5.5、§9、§7.2.1)。**保存期間はゲートウェイの設定値であり、100日であることを確認済み**(2026-09-19)。**なお ★2(api-clean)の中継は記録を行わない設定であり、プロンプトも応答も持たないため、学生データの記録は ★1 の経路に限られる**(§6.2、§9)
3. **モデル名を3箇所で一致させる必要がある。** 下記 §3.4.3.1 による

##### 3.4.3.1 モデル名の一致

**backend・ゲートウェイ・vllm の3箇所が同じモデル名を持っていなければ、経路は通らない。** モデルを差し替えるときは3つを揃えて動かす。

| 箇所 | 設定 | 不一致のときの症状 |
|---|---|---|
| backend | `LLM_MODEL_ID`(環境変数。§6.3) | — |
| トークンゲートウェイ | 接続先ごとに固定されたモデル名 | **`400 model_mismatch`**(期待値が応答に入る) |
| vllm | `--served-model-name`(§3.2.2) | **`404`** |

症状で切り分けられる。`400` ならゲートウェイまでは届いており backend 側の設定ずれ、`404` ならゲートウェイは通って vllm 側とずれている。**トークンはモデル名に紐づかない**ため、この作業で再発行は要らない。

**一方、ゲートウェイの宛先(dest)がモデル名を含む名前だと、モデル差し替えのたびにトークンを配り直すことになる。** 実際、かつてはモデル名入りの宛先が使われていたが、モデル名を含まない名前へ寄せ替えられている(2026-09-19 時点で移行済み)。本プロジェクトはモデル名非依存の宛先を使う。

公開入口コンテナのアドレスが固定である保証は得られていない。変動した場合 backend の名前解決が失敗するため、§13 の未確定事項とする。

#### 3.4.4 シラバスデータ層の配置と api-clean への到達経路

**api-clean・postgres-clean は DGX Spark に置き、公開 VM の backend からはトークンゲートウェイ経由で到達する。** ★1(vllm)と同じ機構であり、経路の実体は §3.4.3 に従う。

##### DGX Spark に置く理由

1. **役割の分離。** DGX Spark は「計算サーバ(vllm)＋ DB サーバ(シラバス)」とし、本プロジェクト固有の処理は公開 VM に集約する。DGX Spark は本プロジェクト以外の用途にも使われる共用機である(§3.2.2)
2. **公開 VM の資源が足りない。** 3.8GiB / 2 vCPU で、**swap が無く root も無いため swap を足せない**。postgres-clean と api-clean は常時メモリを占有する一方、`next build` はピークで数GB を使う。両者を同居させると、frontend の再ビルドに他コンテナの停止が要る状態が常態化する(§13)
3. **シラバスバックエンドは他の担当が運用する資産である。** DGX Spark 上のスタックをそのまま使えば、再構築・データ投入・移設の合意がいずれも不要になる(§1.1.1、§3.5.3)

##### 経路の選定

api-clean は DGX Spark の loopback にあり、そのままでは公開 VM から届かない。到達させる案は3つある。

| 案 | 内容 | 判断 |
|---|---|---|
| socat 中継を追加 | §3.4.1 と同じ方式を api-clean のホスト側ポート 5050 に適用する | **採らない。** 下記のとおり DB 全体を無認証で晒すことになる |
| SSH ローカルフォワード | 公開 VM 側から DGX Spark へ SSH を張り、api-clean の loopback ポートを転送する | **採らない。** DGX Spark 上に本プロジェクト専用のアカウントと鍵を置くことになり、役割の分離に反する |
| **トークンゲートウェイに載せる(採用)** | 教員側のトークンゲートウェイにシラバス用の口を追加し、backend はトークンを付けて呼ぶ | **採用。** ★1 と同じ機構に揃い、DGX Spark には本プロジェクト固有のものを置かない |

**socat 案を退ける理由は、api-clean が無認証であることと、`POST /sql` で DB 全体を読めることである。** `/sql` には読み取り専用のガードが入っており(`SELECT` / `WITH` で始まる1文のみ、書き込み系キーワードを拒否、`LIMIT` を強制)、**書き込みや破壊はできない**。しかし読み取りは DB 全体に及び、テーブルを限定しない。加えて §3.4.1 のとおり **socat の送信元制限は同一ホスト上の VM を区別できない**。両者が重なると、「GW ホストの背後にある全 VM から、無認証でシラバス DB 全体を読み出せる口」を開けることになる。

**採用案はこの問題を2重に解く。** トークンによる認証が前段に入り、かつ**ゲートが通すパスを本サービスが使う3つに限る**ため、`/sql` はそもそも到達不能になる(下記)。

##### ゲートに求める仕様

**通すパスを許可制とし、`POST /sql` を通さない。**

| パス | 認証 | 用途 |
|---|---|---|
| `GET /syllabi` | 要 | 検索(§6.2) |
| `GET /syllabi/{code}` | 要 | 詳細(§6.2) |
| `GET /masters` | 要 | 値マスタ(§6.2) |
| `GET /healthz` | 不要 | 死活監視 |
| **上記以外(`POST /sql` を含む)** | — | **拒否** |

**この3つにインジェクションの余地はない。** api-clean の `GET /syllabi` は WHERE 句の断片を固定のテーブルから引き、利用者の値はプレースホルダ(`%s`)とパラメータ配列で渡している(文字列連結をしない)。加えて FastAPI 側で型と値域を検証しており、`day` は曜日1文字の正規表現、`period` は 1〜7、`grade` は 1〜4、`limit` は上限つきである。**インジェクションの surface は `/sql` に集中しており、これを通さないことが対策になる。**

##### 障害時の挙動

**api-clean へ到達できないと、シラバス参照を伴う機能がすべて失敗する。** 影響範囲は次のとおりで、いずれも学生には一時的な不調として提示する。

| 機能 | 影響 |
|---|---|
| シラバス検索・詳細(§6.1 の `/api/syllabi`) | 失敗する |
| チャットの tool calling(§6.2) | ツール呼び出しが失敗し、モデルが根拠を得られない |
| 履修提案(§7.2) | **候補がゼロになる。** 開講曜日・時限を突合できない科目は候補から外す規定(§7.2.4)のため、api-clean が全滅すると提案が成立しない |

**切断中に履修提案を「候補なし」として返すと、学生には正常な応答と区別がつかない。** 到達不能を検知して明示的に失敗させる(§13)。

**シラバスバックエンドのデータ再投入中も同じ症状になる。** 再投入手順(`bin/init_clean.sh --reset`)は `docker compose down -v` を含み、api-clean と postgres-clean が作り直される。**再投入は事前の周知を要する**(§3.5.3)。

##### 未確定の事項

| 事項 | 内容 |
|---|---|
| 公開パス | **`/spark/syllabus/*`**。入口 Caddy が `handle_path` で prefix を剥がし、tokens VM の `:8024` へ渡す |
| トークン | dest `spark:syllabus` として ★1 とは**別に発行する**。ゲートウェイが dest を照合し、不一致は `401 dest_mismatch` |
| 許可パス | 上表のとおり。`POST /sql` は許可リストに無いため `404` で拒否される |
| **同時実行の制限** | **★2 には掛からない。** ゲートウェイの排他は生成系のパス(`chat/completions` 系)に限られ、参照系は対象外である。加えて接続先ごとにプロセスが分かれるため、★1 の生成と ★2 の参照は競合しない |
| 利用ログ | ★2 は記録しない。本文に prompt / answer を持たず、履修提案1回で数百リクエストになるためである(§9.1) |
| レイテンシ | 履修提案の一括取得(§7.2.4、数百件規模)がホストを跨ぐ。`http_timeout`(既定 30 秒)で足りるかを実測し、必要なら backend 側にキャッシュを置く(§13) |

### 3.5 アクセス制御

#### 3.5.1 公開経路

**frontend は学外から HTTPS で到達できる。** 公開 URL は §3.5.2 のとおり `/syllabel` 配下のサブパスである(実 URL は運用メモ)。

```
学生ブラウザ ──HTTPS──> GW ホストの公開アドレス :443
                          │ DNAT(ホスト自身は待ち受けない)
                          ↓
               Incus コンテナ(Caddy)          TLS 終端・振り分け
                          ↓
               公開 VM :8080(Caddy)
                          ├──✓── frontend :3000
                          └──✓── backend :8000       同一 VM 内(§3.4.2)
                                     │
                                     └──HTTPS──> Incus コンテナ(Caddy)
                                                    └─> トークンゲートウェイ ─┬─> DGX vllm       ★1
                                                                              └─> DGX api-clean ★2
```

**backend からトークンゲートウェイへ向かう通信は、公開アドレスではなく Incus コンテナの私設アドレスへ直接向ける**(§3.4.3)。VM の内側から公開アドレスを叩いても DNAT の対象とならず到達しないためである。

**★1・★2 はいずれも backend からトークンゲートウェイへ向かう通信であり、学生のブラウザは使わない。** ブラウザが触れるのは `/syllabel` 配下だけである(§3.5.2)。

TLS 終端と証明書の管理は GW ホスト側の Incus コンテナが担う。公開 VM の gateway はその後段にあり、HTTP で受ける。

**GW ホストの `ss` に 80/443 は現れない。** DNAT された通信は転送されるだけでホストへローカル配送されないためである。同じ理由で、公開 VM から GW ホストの公開アドレスへ向けた通信は DNAT の対象とならず到達しない。**外部からの到達性を公開 VM の内側から検証することはできない。**

`/syllabel/api/*` の振り分けは公開入口から公開 VM の gateway まで成立しており、gateway → backend は同一 Podman ネットワーク内で閉じる(§3.2.1)。

**死活確認には `/syllabel/api/healthz` を用いる。** gateway が `/syllabel` を剥がすため、backend には `/api/healthz` として届く。backend はルート直下の `/healthz` も持つが、`/syllabel/*` は frontend へ振り分けられるため、**公開経路からは到達しない**。

#### 3.5.2 URL 構造

公開 URL は **`/syllabel` 配下のサブパス配信**とする。frontend は `next.config.ts` の `basePath: "/syllabel"` でビルドされており、gateway の振り分けもこれに合わせている(§3.2.1)。

**パスの名はサービス名 `Syllabel` から採る。** 名称が決まるまでは `/pr-2026` を使っていたが、決定に伴い `/syllabel` に改めた。本書は `/syllabel` だけを正とし、旧パスを残すかはゲートウェイ側の設定の問題として扱う(§13)。

| 公開パス | 転送先 | 備考 |
|---|---|---|
| `/syllabel`、`/syllabel/*` | frontend | Next.js が `basePath` で受ける |
| `/syllabel/api/*` | backend | gateway が `/syllabel` を剥がし、backend には `/api/*` として届く |
| 上記以外 | 404 | gateway が返す |

**内部 API の公開パスは `/syllabel/api/*` であり、`/api/*` ではない。** Next.js の `basePath` はページとアセットの生成先を変えるだけで、アプリケーションコードが呼ぶ `fetch()` のパスには前置されない。したがって **frontend は自身の呼び出し先に `/syllabel` を明示的に含める必要がある**(§6.1)。

`/` をルート配信へ寄せる案は採らない。GW ホストは他用途と共用されており、ルートを本プロジェクトが占有できないためである。

#### 3.5.3 権限と責任分界

| 範囲 | 権限 | 変更方法 |
|---|---|---|
| GW ホスト(80/443、TLS、VM フォワード、ファイアウォール、Incus / libvirt) | 教員側 | 依頼 |
| 公開 VM のユーザ権限内(Podman コンテナ、Caddyfile、frontend イメージ) | 開発チーム | 直接 |
| 公開 VM の root 権限(OS 更新、1024 未満のポート、ufw) | **無し**(特定スクリプト1本の実行のみ) | 依頼 |
| DGX Spark のコンテナと compose | 開発チーム(sudo あり) | 直接。ただし **vllm を止めるとトークンゲートウェイ経由の呼び出しが `502 upstream_unavailable` になる**(§6.3) |
| DGX Spark のホスト外への口(中継の設置、ポートの開放、ホストのファイアウォール) | 所有者(アドバイザー教員) | 依頼。sudo は持つが単独では判断しない(§3.1)。**本構成では新たな口を設けない**(§3.4.2、§3.4.4) |
| トークンゲートウェイ(トークンの発行数、利用ログ、中継先、シラバス用の口) | アドバイザー教員 | 依頼。トークンの発行自体はセルフサービスだが、**発行本数は流量制御に関わるため判断を仰ぐ**(§3.4.3)。**シラバス用の口の追加は当該ゲートウェイへの変更であり、作業の可否と範囲は所有者の判断による**(§3.4.4) |
| シラバスバックエンド(api-clean / postgres-clean)のコードとデータ | シラバスバックエンド担当([ProjectResearch2026/syllabus_backend](https://github.com/ProjectResearch2026/syllabus_backend)) | **本リポジトリでは改修しない**(§1.1.1)。必要な改修は当該リポジトリへ起票する。**本サービスの機能は当該側の改修に依存する**(§13) |
| シラバスバックエンドの配置とバインド | シラバスバックエンド担当 | **移設しない**(§3.4.4)。DGX Spark 上の稼働中スタックをそのまま使う。`127.0.0.1:5050` のバインドを外さないことと、`--reset` を伴う再投入の事前周知を要する |

- **学生がサービスを利用するのに SSH は不要**(学生はブラウザから HTTPS でアクセスするのみ)。SSH は運用者側の管理経路である
- 公開 VM の外向き通信を本プロジェクトの宛先に限定する方針は、root 権限が無いため VM 内では実施できない。必要であれば GW ホスト側での実施を依頼する
- リクエスト/レスポンスのボディはログに記録しない(要件§5.5。詳細は§9)
- 龍谷祭期間を含む常時稼働が前提となるため、公開 VM のコンテナは systemd ユーザユニット化と lingering の有効化を要する(§3.3)

#### 3.5.4 公開に向けて必要なもの

RINS への申請は**外部公開のためのファイアウォール制限解除申請1件**であり、アドバイザー教員が代行する。申請対象は GW ホストである。

**GW ホスト側の前提**(教員側が整えるもの)

- 公開ホスト名の DNS 登録と、GW ホスト公開アドレスから公開入口コンテナへの転送
- TLS 証明書の取得と終端
- 公開入口から公開 VM の gateway への振り分け

**本プロジェクトが公開までに整えるもの**

1. **frontend のサーバ側描画から backend を引く経路の解消**(§6.1、§13)
2. gateway 経由での SSE 中継の確認(§13 の読み取りタイムアウトと併せて)
3. **★1 の同時実行の扱いの決定**(§3.4.3)— トークンの発行本数か待ち行列か
4. **要件§5 の改訂内容の反映**(確認ウィンドウの文言とプライバシーポリシー。§9)
5. RINS への申請状況の確認(下表。§13)

**申請の内容**

| 項目 | 内容 |
|---|---|
| 対象ホスト | GW ホスト(アドバイザー教員研究室) |
| 開放ポート | 443/tcp(必須)、80/tcp(証明書の HTTP-01 認証および HTTPS へのリダイレクトに使用。可否は要確認) |
| 利用目的 | 履修登録支援AIチャットボットの公開ゲートウェイ。画面配信と履修提案ロジックは公開 VM 側、LLM 推論とシラバス DB は DGX Spark 側 |
| 公開範囲 | 学外を含む(在学生が自宅からも利用するため) |
| 実務管理担当 | 運用メモを参照 |

学生データの処理を学外へ出さないこと(要件§3.1)は、アクセス経路を学外に公開することとは別概念であり、引き続き担保する(処理はブラウザ・公開 VM・DGX Spark で完結し、いずれも学内にあり、学外クラウドへ送信しない)。
