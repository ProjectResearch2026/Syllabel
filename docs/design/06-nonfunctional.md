## 9. プライバシー設計

要件§5の実装方針を以下にまとめる。

| 要件 | 実装 |
|---|---|
| §5.2 ブラウザ上のメモリにのみ保持 | Zustand store(永続化機能オフ) |
| §5.2 リロード/タブクローズで消去 | Zustand 初期状態(モジュール再ロード時に初期化) |
| §5.2 サーバへの永続保存禁止 | backend に学生データ用の DB 接続なし(履修要項 YAML はリードオンリー。シラバス DB は科目情報のみで学生データを持たない) |
| §5.2 認証なし | 認証機構を実装しない |
| §5.3 学外通信なし | 学内 vllm を学内のトークンゲートウェイ経由で利用。**学外への通信は書影の openBD だけ**で、送るのは ISBN のみ(§6.4)。成績情報の経路は学内に閉じる |
| §5.3 HTTPS | GW ホスト側で TLS 終端(§3.1、§3.5.1)。backend → トークンゲートウェイも HTTPS(§3.4.3、§3.4.4) |
| §5.5 本サービスのログ非記録 | backend のロガー設定でリクエストボディの中身をログ出力しない。ゲートウェイ(Caddy)もアクセスログにリクエスト/レスポンスボディを残さない設定とする |
| §5.5 プロンプトに載せる範囲 | 氏名・学籍番号・成績の評価・GPA をプロンプトに載せない。修得済み科目の一覧も載せず、要件枠ごとの充足状況と未修得(不合格・履修辞退)の科目名を渡す(§7.3.1、§7.4.1) |
| §5.6 確認ウィンドウ | PDF取り込みボタン押下時にモーダル表示。**利用ログが残る事実を含む文言とする**(要件§5.6) |
| §5.6 プライバシーポリシー | `/privacy` で要件§5.4のデータフロー図を含む解説を表示。利用ログに残るもの・残らないものを明記する |

TLS は GW ホスト側で終端する。**学生データが平文で流れる区間は公開 VM 内のコンテナ間に限る**(§3.4.2)。GW ホスト内の TLS 終端点から公開 VM の gateway までの区間も平文だが、同一ホスト内に閉じている。

**ホストを跨ぐ2区間はいずれも暗号化される。**

| 区間 | 暗号化 | 流れるもの |
|---|---|---|
| backend → vllm(★1) | HTTPS(+ Bearer トークン) | プロンプトと応答。**学生プロファイルの一部を含む**(範囲は §7.3.1、§7.4.1) |
| backend → api-clean(★2) | HTTPS(+ Bearer トークン) | 科目の検索条件と検索結果。**学生プロファイルは含まない**(§6.2) |

**書影(openBD)は学外への通信だが、学生データの経路には乗らない(§6.4)。** 送るのは ISBN だけであり、誰が見ているかに依存する値を含まない。**ただし画像はブラウザが直接引くため、学生の端末から学外へ通信が出る。** 閲覧中の講義を推測されないよう `referrerPolicy="no-referrer"` を付ける(渡るのは IP アドレスと ISBN に限られる)。この経路は要件§5.3・§5.4 と `/privacy` に記す。

★2 をトークンゲートウェイ経由とするのは、認証と暗号化を得つつ DGX Spark に本プロジェクト固有のものを置かないためである(選定理由は §3.4.4)。ゲートウェイは許可した3つの読み取りパスと `/healthz` だけを通し、`POST /sql` を拒否する。

### 9.1 利用ログの扱い

**backend が LLM へ送るプロンプトと、その応答は、経路上のトークンゲートウェイに100日間記録される**(§3.4.3)。ログの保存は学内サーバの運用上必要な措置として所有者が決めたものであり、**本プロジェクトの側で止めることはできない**。

**api-clean への問い合わせ(★2)も同じゲートウェイを通り、検索条件と結果が100日間記録される**(§3.4.4)。学生プロファイルは送らない(§6.2)が、検索条件には学生が検索欄に入力した教員名や、アシスタントが会話から拾った講義内容の語(`topic`。§7.2.4)が含まれ得る。

**記録されない経路を選ぶことはできない。** 次の3点で対応する。

1. **記録される内容を要件§5.5 の範囲に限る**(§7.3.1、§7.4.1)。氏名・学籍番号・成績の評価・GPA は渡さない。渡すのは課程・入学年度・学年・対象学期・要件枠ごとの修得済み単位と不足単位・登録できる単位・未修得(不合格・履修辞退)の科目名・今の時間割と条件・ツールの結果(検索した科目がその学生にとってどの区分で、どの要件枠に入り、修得済みか)・学生が入力した文章である。**修得済み科目の一覧は載せない**(組み立てと検索が backend の手元で使う)。時間割の画面だけでなく、シラバスチャット・講義単位チャットでも課程コード等が揃えば同じ範囲を渡す
2. **残る事実を学生に明示する**(要件§5.6)。成績表取り込み時の確認ウィンドウとプライバシーポリシーに、学内の AI サーバへ送る内容と100日間記録される旨を書く。シラバスの検索条件が記録されることはプライバシーポリシーに書く。「消去される」「どこにも残らない」といった表現は用いない。**AI の会話の入力欄(時間割・シラバス一覧・講義詳細の3つ。`lib/ai.ts` の `CHAT_LOG_NOTE`)にも同じ旨を添える** — デモの学生は確認ウィンドウを通らないので、デモで使う来場者にはここが記録を知る場所になる。また 取り込み時の確認ウィンドウが同意を得ているのは成績表についてであり、**学生がその場で自由に書く文章までは覆わない。** 書いた内容は項目1のとおりそのままプロンプトに入って記録される
3. **学外には出さない**という担保は維持する(要件§5.3)。記録先は学内であり、学外のクラウド AI 事業者に送信・保存されることはない

**残存リスクを明記する。** 上記1を講じてもなお、課程・入学年度・学年と未修得科目の組合せから個人が推定される可能性は残る。直接的な識別子は含まれないが、「匿名である」とは説明しない。

**入口 Caddy のアクセスログにも記録が残る。** サイト全体で `log` が有効であり、リクエストの URI・クエリ文字列・クライアントの実 IP が記録される。★2 のシラバス参照は `/spark/syllabus/syllabi?year=...&day=...` の形でゲートウェイへ向かうため、**検索条件がクエリ文字列ごと残る**。学生の成績・氏名・学籍番号は含まないが、記録先として本節の対象に含める。このログも本プロジェクトの管理外である(§3.5.1)。

**未確認事項が2つある**(§13)。ログを閲覧できる範囲(アドバイザー教員のみとされているが未確認)と、100日経過後に記録が削除されるか(根拠となる記述は「100日間保存される」に留まる)。**いずれも学生への説明文に関わるため、確認が取れるまでは消去や限定的な閲覧を前提とした記述を置かない。**

## 10. 非機能設計

### 10.1 ストリーミング表示(要件§6)

- vLLM の `stream=true` を有効化
- backend は受信した chunk をそのまま SSE で配信
- frontend は受信した chunk を React state に逐次反映

### 10.2 同時利用(要件§6)

- 龍谷祭での展示を想定し、数〜十数人程度の同時利用を目標
- **同時実行数はトークンゲートウェイの制約で決まる。** 同一トークンで生成が進行中の場合、後続は `503 busy` で**即座に拒否される**(§3.4.3)。時間割のアシスタントの1回の応答はツール呼び出しを挟んでモデル呼び出しが2回以上になる(§7.3)ため、**1トークンのままでは目標を満たせない**(組み立てだけの「希望条件なしで提案する」はモデルを呼ばない。§7.2)
- **トークンの発行本数は所有者の判断を要する**(§3.5.3、§13)
- 最終的には vLLM の並列処理性能に依存する(`--max-num-seqs` 等)。ただし当該 vllm は他の利用者と GPU を共有しているため(§3.2.3)、同時実行を増やすと1件あたりの生成速度は落ちる
- 負荷試験は開発後半に実施。**展示前に、想定人数での同時実行を実機で計測する**

### 10.3 対応環境(要件§6)

- 主要ブラウザ(Chrome / Firefox / Safari / Edge)の最新版
- Tailwind CSS の breakpoint を活用し、スマートフォン・タブレット幅でも崩れないレイアウトを実装
- 画面部品は自前実装であり(§2)、レスポンシブ対応も自前で行う

## 11. 龍谷祭展示時の構成

要件§7に対応する実装方針。

| 要件 | 実装 |
|---|---|
| 自端末からのアクセス | サービスは公開 URL(`/syllabel` 配下。§3.5.2)で誰でもアクセスできる状態にあり、当日は会場でその QR コードを掲示する。来場者は自分の端末で開き、自分の成績表を取り込んで使える(学内 Wi-Fi・学外回線のいずれからでも可) |
| 展示用端末でのデモ | 会場に PC を置き、サービスを開いた状態で来場者に操作してもらう。この PC ではダミーデータ(デモの学生)を使う |
| ダミーデータ | `frontend/lib/dummy/profiles.json` に課程6 × 提案を受ける学年4 × 提案する学期2 の48件を置き、来場者は学年・課程・学期を選んで読み込む(学期の初期値は今日の日付。成績表の公開に合わせて3〜8月は前期、9〜2月は後期)。提案する学期はすべて 2026年度(開講科目データが 2026年度分だけ)で、成績はその直前の学期まで付く。1年前期は入学直後で成績が無く、取り込み確認・完了の画面は「取り込み」と言わず「新入生として始める」とする。PC では選ぶ欄を画面中央のダイアログで開く(取り込みのカードの下に開くと、画面の外に出て「この学生で試す」までスクロールが要った)。データは `backend/scripts/generate_dummy_profiles.py` が履修要項と api-clean の開講実績から生成し(おおむね3人に1人が不合格の科目を、5人に1人が履修辞退を持つ)、`backend/tests/test_dummy_profiles.py` が履修要項との整合(科目名・単位・CAP・必修の履修)を確かめる。科目は評価ではなく履修状態(`passed` / `failed` / `withdrawn` / `registered`)で持つ(§5.2.1。点数は生成の中で合否を決めるのにだけ使う)。**成績表を使わずに試す手段も兼ねる**(要件§4.1。手入力のフォームは置かない)ので、読み込んだデモの学生もマイデータで訂正できる(§8.4) |
| 実成績表の取り扱い | 実成績表は来場者自身の端末でのみ利用する。展示用端末ではデモの学生を使う |
