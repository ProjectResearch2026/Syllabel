## 9. プライバシー設計

要件§5の実装方針を以下にまとめる。

| 要件 | 実装 |
|---|---|
| §5.2 ブラウザ上のメモリにのみ保持 | Zustand store(永続化機能オフ) |
| §5.2 リロード/タブクローズで消去 | Zustand 初期状態(モジュール再ロード時に初期化) |
| §5.2 サーバへの永続保存禁止 | backend に学生データ用の DB 接続なし(履修要項 YAML はリードオンリー。シラバス DB は科目情報のみで学生データを持たない) |
| §5.2 認証なし | 認証機構を実装しない |
| §5.3 学外通信なし | 学内 vllm を学内のトークンゲートウェイ経由で利用。**学外への通信は書影の openBD だけ**で、送るのは ISBN のみ(§6.4)。成績情報の経路は学内に閉じる |
| §5.3 HTTPS | GW ホスト側で TLS 終端(§3.1、§3.5.1)。backend → トークンゲートウェイも HTTPS(§3.4.3、§3.4.4) |
| §5.5 本サービスのログ非記録 | backend のロガー設定でリクエストボディの中身をログ出力しない。ゲートウェイ(Caddy)もアクセスログにリクエスト/レスポンスボディを残さない設定とする |
| §5.5 プロンプトの最小化 | 氏名・学籍番号・評語・GPA・修得済み科目一覧をプロンプトに載せない(§7.2.1) |
| §5.6 確認ウィンドウ | PDF取り込みボタン押下時にモーダル表示。**利用ログが残る事実を含む文言とする**(要件§5.6) |
| §5.6 プライバシーポリシー | `/privacy` で要件§5.4のデータフロー図を含む解説を表示。利用ログに残るもの・残らないものを明記する |

TLS は GW ホスト側で終端する。**学生データが平文で流れる区間は公開 VM 内のコンテナ間に限る**(§3.4.2)。GW ホスト内の TLS 終端点から公開 VM の gateway までの区間も平文だが、同一ホスト内に閉じている。

**ホストを跨ぐ2区間はいずれも暗号化される。**

| 区間 | 暗号化 | 流れるもの |
|---|---|---|
| backend → vllm(★1) | HTTPS(+ Bearer トークン) | プロンプトと応答。**学生プロファイルの一部を最小化して含む**(§7.2.1) |
| backend → api-clean(★2) | HTTPS(+ Bearer トークン) | 科目の検索条件と検索結果。**学生プロファイルは含まない**(§6.2) |

**書影(openBD)は学外への通信だが、学生データの経路には乗らない(§6.4)。** 送るのは ISBN だけであり、誰が見ているかに依存する値を含まない。**ただし画像はブラウザが直接引くため、学生の端末から学外へ通信が出る。** 閲覧中の講義を推測されないよう `referrerPolicy="no-referrer"` を付ける(渡るのは IP アドレスと ISBN に限られる)。要件§5.4 のデータフロー図はこの経路を含んでいないため、`/privacy` の記述とあわせて要件側の更新が要る(§13)。

★2 をトークンゲートウェイ経由とするのは、認証と暗号化を得つつ DGX Spark に本プロジェクト固有のものを置かないためである(選定理由は §3.4.4)。ゲートウェイは許可した3つの読み取りパスと `/healthz` だけを通し、`POST /sql` を拒否する。

### 9.1 利用ログの扱い

**backend が LLM へ送るプロンプトと、その応答は、経路上のトークンゲートウェイに100日間記録される**(§3.4.3)。ログの保存は学内サーバの運用上必要な措置として所有者が決めたものであり、**本プロジェクトの側で止めることはできない**。

**記録されない経路を選ぶことはできない。** 次の3点で対応する。

1. **記録される内容を最小にする**(§7.2.1)。氏名・学籍番号・評語・GPA・修得済み科目の一覧を渡さない。渡すのは課程・入学年度・学年・要件枠ごとの不足単位・再履修の対象となる科目名・学生が入力した希望条件に限る
2. **残る事実を学生に明示する**(要件§5.6)。成績表取り込み時の確認ウィンドウとプライバシーポリシーに、学内の AI サーバへ送る内容と100日間記録される旨を書く。「消去される」「どこにも残らない」といった表現は用いない。**希望条件の入力欄(§8.3.1)にも同じ旨を添える** — 取り込み時の確認ウィンドウが同意を得ているのは成績表についてであり、**学生がその場で自由に書く文章までは覆わない。** 書いた内容は項目1のとおりそのままプロンプトに入って記録される
3. **学外には出さない**という担保は維持する(要件§5.3)。記録先は学内であり、学外のクラウド AI 事業者に送信・保存されることはない

**残存リスクを明記する。** 上記1を講じてもなお、課程・入学年度・学年と未修得科目の組合せから個人が推定される可能性は残る。直接的な識別子は含まれないが、「匿名である」とは説明しない。

**入口 Caddy のアクセスログにも記録が残る。** サイト全体で `log` が有効であり、リクエストの URI・クエリ文字列・クライアントの実 IP が記録される。★2 のシラバス参照は `/spark/syllabus/syllabi?year=...&day=...` の形でゲートウェイへ向かうため、**検索条件がクエリ文字列ごと残る**。学生の成績・氏名・学籍番号は含まないが、記録先として本節の対象に含める。このログも本プロジェクトの管理外である(§3.5.1)。

**未確認事項が2つある**(§13)。ログを閲覧できる範囲(アドバイザー教員のみとされているが未確認)と、100日経過後に記録が削除されるか(根拠となる記述は「100日間保存される」に留まる)。**いずれも学生への説明文に関わるため、確認が取れるまでは消去や限定的な閲覧を前提とした記述を置かない。**

## 10. 非機能設計

### 10.1 ストリーミング表示(要件§6)

- vLLM の `stream=true` を有効化
- backend は受信した chunk をそのまま SSE で配信
- frontend は受信した chunk を React state に逐次反映

### 10.2 同時利用(要件§6)

- 龍谷祭での展示を想定し、数〜十数人程度の同時利用を目標
- **同時実行数はトークンゲートウェイの制約で決まる。** 同一トークンで生成が進行中の場合、後続は `503 busy` で**即座に拒否される**(§3.4.3)。履修提案は1回あたり4〜5分を要する(§7.2)ため、**1トークンのままでは目標を満たせない**
- 対応は次のいずれか、または併用とする。**トークンの発行本数は所有者の判断を要する**(§3.5.3、§13)
  - **トークンを複数発行し、backend 側で空いているものに割り当てる**(同時実行数＝トークン数)。**この対策が効くことは裏付けが取れている** — ゲートウェイは進行中のトークンを集合に持って判定しており、制約がトークン単位であることを実装で確認済み(2026-09-19。§3.4.3)
  - **待ち行列を設け、待ち人数と目安時間を学生に提示する**(`503` をそのままエラーとして見せない)
- 上記を満たしたうえで、最終的には vLLM の並列処理性能に依存する(`--max-num-seqs` 等)。ただし当該 vllm は他の利用者と GPU を共有しているため(§3.2.3)、同時実行を増やすと1件あたりの生成速度は落ちる
- 負荷試験は開発後半に実施。**展示前に、想定人数での同時実行を実機で計測する**

### 10.3 対応環境(要件§6)

- 主要ブラウザ(Chrome / Firefox / Safari / Edge)の最新版
- Tailwind CSS の breakpoint を活用し、スマートフォン・タブレット幅でも崩れないレイアウトを実装
- 画面部品は自前実装であり(§2)、レスポンシブ対応も自前で行う

## 11. 龍谷祭展示時の構成

要件§7に対応する実装方針。

| 要件 | 実装 |
|---|---|
| 自端末からのアクセス | 来場者の端末から、ゲートウェイの公開 URL(`/syllabel` 配下。§3.5.2)でアクセス可能とする(学内 Wi-Fi・学外回線のいずれからでも可。ホスト名は§3.5.4・§13の DNS 登録と併せて決定) |
| 展示用端末でのデモ | 展示会場に別端末を設置し、サービスを開いた状態で来場者に操作してもらう |
| ダミーデータ | `frontend/lib/dummy/` に複数パターンのダミー学生プロファイル(成績上位 / 平均的 / 再履修あり等)を用意し、「デモモード」ボタンから読み込めるようにする |
| 実成績表の取り扱い | 展示用端末では「PDF取り込み」を無効化し、ダミーデータ専用とする。実成績表は来場者自身の端末でのみ利用 |
